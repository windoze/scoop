# M58 生产性能记录

状态：仅完成 M58-A 的本机 runtime 对照。B／C／D、Linux、多个 mutator 的 stop-wait 与实际 GUI 帧循环尚未完成，不作为 M58 整体验收。

## 1. 方法与口径

2026-10-20，Apple M4 Pro、macOS 27.0.1（26A434）、Clang／LLVM 22.1.8。对照 runtime 为 `c3b8942db` 与 `8df65ae17`，后者包含 A 的四项生产改动。同一组本机 `target/debug` 编译工具、同一预编译 sysroot、应用 `--release`、runtime 默认 O2，只替换 `--runtime-root`。不修改工作仓库来构建基线；从 Git 导出 runtime 到仓库外，编译缓存、原始结果和临时源码均位于 `/Users/chenxu/repos/scoop-work/m58-validation/perf`，测量结束后清理。

复用 `tests/benchmarks/parallel/mark-graphs.scoop` 与 `mark-phase.c`；C companion 以 `-O2 -DSCOOP_BENCH_PARALLEL_METRICS` 构建，读取真实 collector 阶段统计。每格五个独立进程，旧／新顺序逐轮交替。full 每进程 22 事件、舍弃前两次后合并 100 事件；minor 每进程 52 事件、舍弃前两次后合并 250 事件。报告 nearest-rank p95；同进程事件相关，不能当成全部独立样本。计时期间没有并行构建或本任务的其他测试，未固定 affinity。

以下暂停均为 runtime `pause_ns` 的事件差值：world 停稳之后至解锁／恢复之前，边界见 [GC-PAUSE-WORK.md](GC-PAUSE-WORK.md#1-先区分三个时间)。单 mutator，stop-wait 中位数低于本机 1 µs 计时粒度；不能据此声称多线程握手或 GUI 响应尾部已改善。

## 2. Full 暂停

单位 ms，单元格为 p50／p95。`SCOOP_BENCH_GRAPH=array|chain|compact`；workers 通过 `SCOOP_GC_WORKERS=1|4` 固定。

| 图与规模 | worker | M58 前 | M58-A 后 |
| --- | ---: | ---: | ---: |
| 1,048,576 节点引用数组，全部存活 | 1 | 36.601／37.741 | 32.126／33.448 |
| 同上 | 4 | 18.120／18.578 | 13.460／13.977 |
| 1,048,576 节点单链 | 1 | 22.698／23.726 | 18.296／18.635 |
| 同上 | 4 | 22.851／23.723 | 18.219／18.783 |
| 900,000 节点引用数组，单 source 容量不足 | 1 | 36.678／37.780 | 27.122／28.089 |
| 同上 | 4 | 20.788／21.569 | 11.729／12.793 |
| 1,048,576 对 Node／Leaf，保留 1/16，实际压缩 | 1 | 33.444／34.379 | 26.336／27.191 |
| 同上 | 4 | 27.764／28.591 | 20.480／21.402 |
| 262,144 对 Node／Leaf，保留 1/16，本轮无搬迁 | 1 | 4.886／5.191 | 3.544／3.811 |
| 同上 | 4 | 4.255／4.487 | 2.869／3.054 |

阶段解释：

- 百万节点数组四 worker：reclaim 中位数 7.912 → 3.369 ms；mark 10.077 → 9.937 ms，plan 约 0.038 ms，两版均无搬迁。主要收益来自 starts 位图枚举。
- 90 万节点数组四 worker：plan 5.495 → 0.074 ms，reclaim 6.812 → 2.903 ms。两版最终搬迁数均为零，但旧版先做了失败的压缩准备；容量早判省掉这部分工作。
- 实际压缩四 worker：两版均为三个 source、一个 target，搬迁 93,793 个对象，追踪 131,074 个对象，收集后 managed mapping 约 32.56 MiB。plan 6.473 → 4.547 ms、reclaim 13.575 → 8.204 ms，copy／update 基本保持；没有通过减少必要搬迁获得加速。
- 单链 mark 仍约 14.8 ms，多 worker 没有明显缩短依赖链。实际压缩的四 worker 暂停也仍约 20.5 ms。A 减少了无效工作，没有解决所有大图的长暂停，更不能将 16.67 ms 全部当作 GC 可用时间。

## 3. Minor 与无引用大数组

复用 `minor` 模式，`SCOOP_BENCH_NODES=4096`：旧引用数组持有 4096 对年轻 Node／Leaf，连接环并 pin 一个对象，继续分配至触发一次 minor。每事件均追踪 8192 个年轻对象、扫描 4096 个旧引用槽、晋升 229,376 bytes、实际搬迁 7027 个对象。显式设置四 worker 时 runtime 报告实际使用四 worker，不能与默认 minor 策略混淆。

大数组对照只在临时源码的 main 中额外保活 `Array<Long>(16777216L) { index -> index }`，即 128 MiB 无引用 payload；在最后检查首尾元素，以保证存活。初始化发生在计时事件之前，其他源码相同。单位 µs，单元格为 p50／p95。

| 旧无引用 payload | worker | M58 前 | M58-A 后 |
| --- | ---: | ---: | ---: |
| 0 MiB | 1 | 729／769 | 472／512 |
| 0 MiB | 4 | 686／753 | 413.5／495 |
| 128 MiB | 1 | 873／929 | 465／497 |
| 128 MiB | 4 | 814／933 | 413／454 |

单 worker、0 MiB 时 reclaim 290 → 25 µs；带 128 MiB 数组时为 290 → 23 µs，update 263 → 192.5 µs。必要旧引用扫描、晋升和 pin 结果一致；无引用数组不再额外扫描其卡表。本期没有省掉卡表分配或清零，不能将这项收益称为 footprint 缩减。

## 4. 连续分配与 footprint

将 `tests/benchmarks/allocation.scoop` 的循环次数在仓库外副本中从 40,000 调整为 2,000,000，校验输出 `3999998000000`。同一 release 编译器、单 worker；每版先运行一进程预热，再七对交替运行。端到端时间包含进程启动和输出，不是每次分配的指令成本。

| 指标 | M58 前 | M58-A 后 |
| --- | ---: | ---: |
| 程序总耗时中位数，ms | 105.234 | 67.775 |
| 总耗时范围，ms | 104.453–105.713 | 66.762–68.226 |
| 总分配量，bytes | 208,000,112 | 208,000,112 |
| minor 次数 | 199 | 199 |
| 累计 GC 主体暂停中位数，ms | 37.412 | 0.524 |
| 每进程最大暂停的中位数，µs | 216 | 14 |
| RSS／峰值 RSS 中位数，MiB | 12.69／12.69 | 12.70／12.70 |

总时间减少约 35.6%，约 1.55 倍吞吐，基本可由暂停减少解释；扣除暂停后的 mutator 时间相近，不能说分配快路径本身快了 1.55 倍。最初未预热的一轮出现一次旧版约 701 ms 的启动离群值，因此另行做了两版同样预热的完整七对测量；上表来自后者，不混用两组样本。

图用例的 managed mapping 在同负载两版间保持，RSS 没有显示出稳定的大幅下降：百万节点数组四 worker 约 86.89／86.97 MiB，128 MiB ballast 的 minor 四 worker 两版约 141.91 MiB。A 不新增常驻对象索引，也没有改变现行 region／metadata 格式；目前证据支持暂停改善，尚不支持显著 footprint 收益。后续 B／C 的动态分配与支持产物消除应独立测量。
