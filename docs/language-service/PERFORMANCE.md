# 公共语言服务基础性能记录

日期：2026-10-23。宿主为 Apple M3 Ultra、512 GiB 内存、macOS 27.0.1，Rust 1.99.0；服务和解析测量程序均使用 release 构建。原始采样、脚本和逐次结果保留在仓库外，不作为兼容性门槛或固定延迟承诺。

## 真实项目与方法

| 生产项目 | Scoop 文件 | 源码大小 | 行数 | 打开的文件 |
| --- | ---: | ---: | ---: | --- |
| `scoop.cli` | 10 | 39,982 byte | 933 | `src/help.scoop` |
| `scoop.http.client` | 139 | 456,386 byte | 10,354 | `src/request.scoop` |

每个项目启动独立 stdio LSP 进程，读取真实 Cone 和已准备的预编译 sysroot。打开文件并等到当前版本诊断发布；查询真实 receiver 的成员和声明引用。在字符串字面量内交替插入／删除一个字符，共五次，每次等到同版诊断后再次补全。源码文件、工具和原产物始终保留，编辑仅存在于该进程的文档缓冲区。

计时使用客户端单调时钟，包含协议往返和 worker 排队。打开及编辑的结束点由诊断和随后的一次 documentSymbol 响应确认；两者相差小于 0.02 ms。五次补全与重复引用取中位数；首次引用为本次进程第一次构建项目引用索引，五次编辑后再次测量重建。CLI 和 HTTP 的查询分别返回 5 与 78 个引用，优化前后数量相同。峰值内存使用 macOS 子进程 `ru_maxrss`，换算为 MiB。

## 实测优化

优化前为 `f8dfb85bb`，优化后为 `59f2aad7e`。采样发现已有 selector 的补全反复重建全 Cone 正文范围，引用索引的正文检查还为每个 selector 提前枚举全部成员与扩展候选。

当前实现先按源码／包含范围定位正文，批量枚举共用该次区域集合；正文检查只保存 receiver 的真实类型、原泛型作用域及 smart cast／安全导航的类型视图，实际补全才计算所选 selector 的候选。查询完成后缓存结果，取消时不提交候选的部分语义状态。独立的诊断、导航和引用查询不再触发无关成员枚举。

| 指标 | CLI 优化前 | CLI 优化后 | HTTP 优化前 | HTTP 优化后 |
| --- | ---: | ---: | ---: | ---: |
| 首次打开至诊断／结构查询完成 | 127.8 ms | 95.0 ms | 2,762.4 ms | 2,411.9 ms |
| 单字符编辑至诊断更新，中位数 | 57.6 ms | 17.7 ms | 420.7 ms | 104.4 ms |
| 补全，五次请求中位数 | 1.15 ms | 0.07 ms | 213.88 ms | 0.32 ms |
| 每次编辑后的首次补全，中位数 | 1.24 ms | 0.93 ms | 221.31 ms | 2.94 ms |
| 首次引用索引查询 | 289.1 ms | 106.6 ms | 16,298.1 ms | 4,507.5 ms |
| 重复引用查询，中位数 | 0.09 ms | 0.10 ms | 0.21 ms | 0.21 ms |
| 编辑后的引用索引重建 | 300.0 ms | 104.5 ms | 16,513.8 ms | 4,599.7 ms |
| 进程峰值 RSS | 111 MiB | 106 MiB | 1,117 MiB | 1,091 MiB |

大项目首次打开和引用索引仍包含完整依赖视图与普通声明／正文分析，不能用缓存命中的亚毫秒查询代替这些成本。当前语法只重解析变化文件，未变化文件复用原结果；同 Cone 的任一文本变化仍保守失效声明、正文与引用索引，未变化的预编译输入和源码依赖结果分别复用。此批没有实现正文级增量类型检查或局部重解析。

## 取消

再次编辑后先完成诊断，再启动尚未缓存的引用查询；10 ms 后发送取消通知。两个项目都返回 `RequestCancelled`（`-32800`）。

| 优化后的观测 | CLI | HTTP |
| --- | ---: | ---: |
| 取消通知至取消响应 | 0.07 ms | 0.12 ms |
| 取消通知至下一次 documentSymbol 响应 | 0.28 ms | 0.67 ms |

第二行包含后续请求本身的处理成本，用于观察 worker 恢复处理请求；不能只把协议取消响应时间当成计算退出时间。取消仍沿原文件、声明、正文和表达式的实际边界检查，不以耗时配额决定源码是否有效。

## 严格 parser 成本

实施基线为 `033dd9e1d`。两个独立测量程序调用相应版本的 `scoop_parser::parse`，使用上表同一批源码；先将文本读入内存并预热三轮，再测七组、每组完整解析项目 25 轮，报告组内每轮耗时的中位数。计时包含 lexer、grammar、严格 AST 结果及其释放，当前版本还包含 CST 和恢复记录；两版均成功解析，并得到相同的 68／568 个顶层声明。

| 严格解析一轮项目 | 实施前 | 当前 | 比例 |
| --- | ---: | ---: | ---: |
| `scoop.cli` | 0.69 ms | 1.36 ms | 约 2.0 倍 |
| `scoop.http.client` | 6.89 ms | 15.58 ms | 约 2.3 倍 |

这是完整解析入口在实施前后的差异，不能分离为 rowan 单独的成本，也不代表整个原生编译流水线的耗时比例。HTTP 项目的额外解析成本约 8.7 ms；此次编辑与引用的主要热点位于查询编排和无关成员枚举，优化针对实测热点，保留同一 grammar、完整 CST 与严格 AST 的共同入口。
