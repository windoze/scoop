依据：[语言规范](../specs/SCOOP-SPEC.md)、[运行时规范](../specs/SCOOP-RUNTIME-SPEC.md)、[实现规范](../specs/SCOOP-IMPL-SPEC.md)、[仓库测试约定](../../AGENTS.md)和 [fixture schema 1](../../tests/fixture_runner/README.md)。实施前记录实际基线，不假定其他进行中的里程碑已经完成。

本次实施仅收敛测试职责；不以 M38/M39 的未实施设计作为前置能力。

## 0. 已确定的决策与交付范围

普通语言功能 fixture 只验证编译结果和运行行为；HIR、MIR、LIR 的结构快照集中到少量专门的代表用例。每个阶段有结构覆盖，不等于每个功能用例都要保存全部阶段输出。

M40 交付包括：

- 移除普通功能用例的 AST/HIR/MIR/LIR、完整符号表及其他无关的全量快照，同时移除仅为生成这些快照而存在的命令参数和步骤。
- 为各阶段保留几组小而可读的结构专测，明确每组负责的转换或数据关系。
- 保留语言规则的独立用例、组合用例和准确的负向诊断，以及产物、ABI、GC、链接、优化等专测中不可由运行输出替代的断言。
- 修订测试约定与新增用例的默认写法，防止后续里程碑重新产生全量快照。

本次不改变语言语义、IR 的完备性要求、产物格式、实体身份、runtime ABI 或 GC 契约，不重写测试框架，不新增测试注册表、通用查询语言或覆盖证明体系。精简测试期望不能成为删除生产校验的理由。

## 1. 现状与问题

以下是 Git 跟踪的 `tests/fixtures/` 文件内容大小，GB/MB 使用十进制；不包含 Git 历史、对象压缩或运行工作区：

| 项目 | 基线统计 | 含义 |
| --- | --- | --- |
| 全部 fixture 文件 | 32,779 个，8.24 GB | 包括源码、声明、诊断和快照 |
| 完整符号表 | 2,068 个，4.39 GB | `symbols.*` 与 `strong_symbols.*`，约占总量 53% |
| HIR 快照 | 3,210 个，3.05 GB | 约占总量 37% |
| Scoop 测试源码 | 4,930 个，约 2.12 MB | 体积主要来自测试期望而非语言用例源码 |
| 内容完全相同的额外副本 | 7,158 个，约 2.10 GB | 按 Git blob 身份统计；与上述分类重叠，不能相加 |

### 1.1 期望范围远大于被测行为

[泛型 equality 用例](../../tests/fixtures/m23-cli-generics/generic-equality-payload/fixture.toml) 为 provider、consumer、downstream 分别保存 AST/HIR/MIR/LIR，并为最终 executable 保存三个 target 的完整符号表及 strong symbol 表。这同时冻结了 core、runtime 和 native 库的无关定义。

[core layout 用例](../../tests/fixtures/m23-cli-core-layouts/shared-dispatch-combined/fixture.toml) 保存整个改造后 core 的阶段输出。core 中无关声明变化也会使这些期望失效。

相同 provider 的完整 HIR 在多个 consumer 用例中重复保存；基线中存在同一份约 1.24 MB 的 provider HIR 被保存 35 次的情况。这些副本并未增加 provider 结构覆盖。

### 1.2 原始 Debug 展开不适合长期作为 golden

[container encoding HIR](../../tests/fixtures/m29-container-encoding/values/program.hir.txt) 大约 24 MB，其中 CrossCone 部分约 18.5 MB，最长单行超过 3 MB。[CrossCone dump](../../compiler/hir/src/dump/cross_cone.rs) 和 [LocalConcrete dump](../../compiler/hir/src/dump/local.rs) 直接输出记录的 Rust `Debug` 表示，把内部编号、来源位置、身份记录及嵌套数据展开到期望中。

快照变化不必然表示语言结果或阶段合同变化。局部编号、依赖内容或 Rust 数据表示的调整，可能产生远超过人工可审查范围的差异。基线最近一次 Darwin 快照刷新提交 `22dee6b14` 修改 360 个文件，新增 134,592 行、删除 49,708 行；这说明现有审查负担，并不单独证明其中每个差异都无意义。

快照只有在断言范围明确、期望可理解、差异可审查时才有回归价值。不能把“重新运行编译器并接受全部新输出”当作变更正确性的证据。

## 2. 测试职责

| 用例类别 | 保留的验证 | 默认移除的内容 |
| --- | --- | --- |
| 普通正向语言用例 | 编译成功、完整诊断期望、退出码或信号、stdout/stderr；必要的程序内断言 | 全阶段 golden、完整符号表、无关链接计划和固定指纹 |
| 普通负向语言用例 | 编译失败、准确错误位置、code/message/notes；原用例需要的无输出或原子输出断言 | 准备阶段 provider/core 的全量快照 |
| 阶段结构专测 | 被测转换的类型、调用目标、控制流、布局、ABI、roots 等结构 | 无关依赖正文和整个 core 的展开 |
| 产物与构建专测 | `.slib` 读写、跨 Cone 消费、缓存命中/失效、确定性、源码不可用时的独立链接 | 与被测格式、依赖或链接关系无关的固定全量期望 |
| 后端、FFI 与 runtime 专测 | ABI 互操作、符号绑定/ODR、机器码性质、GC 保活/搬迁、异常与线程行为 | 无关函数、符号和运行库实现的全文 |

普通程序必须实际计算或执行被测行为，并通过输出、退出码或程序内断言观察结果。只接受源码、只打印固定成功文本、或只检查进程没有崩溃，不能替代原来有意义的行为断言。

删除某个快照前，如果它是某条必要合同唯一的覆盖，应先将对应断言收敛到结构专测、现有 Rust 测试或行为用例。不能为了减少文件数直接丢掉覆盖，也不能把整份快照换成几个宽泛的关键词后宣称覆盖等价。

## 3. 少量阶段结构专测

### 3.1 按阶段职责选择代表用例

优先从现有最小用例中选择，集中说明用途。每个阶段保留几组，不按每个语言特性、每个历史里程碑或每种 consumer 再复制一套。

| 阶段 | 建议的代表组 | 必须能看出的关系 |
| --- | --- | --- |
| HIR | 类型与调用决议；泛型/默认参数的本地和跨 Cone 具体化；closure 与动态分派 | 完整类型、选中实体、实参映射、捕获与分派目标 |
| MIR | 分支/循环与值合流；异常/finally 与跳转清理；协程挂起恢复 | CFG 边、求值顺序、返回值、清理路径及跨挂起存储 |
| LIR | 值布局与 ZST；Scoop/C ABI 与分派；GC roots、safepoint 和 relocation | 大小/对齐、参数和结果 carrier、调用边界、根位置及更新关系 |

这些是职责分组，不是要求构造一个覆盖全部特性的巨大程序。组内用最小输入隔离真正不同的转换。以后出现无法被现有组表达的新结构合同，再增加相应专测；不设置任意的文件数上限或快照大小配额。

AST 快照采用同样原则，只在 parser 结构专测中保留。已有必要的 Rust 单元测试继续承担局部结构、格式和算法检查，不为迁移而再复制一套文件 fixture。

### 3.2 Golden 的表达方式

结构期望应使用面向该阶段的可读表示，或直接对 typed IR 字段作明确断言。优先复用已有 dump 和测试入口；只有保留的专测确有需要时，才局部改进 dump。

- 输出被测实体与理解它所需的引用关系，避免通过 `Debug` 递归打印整个元数据记录或依赖世界。
- 测试中的局部编号可按确定的遍历顺序显示为简短标签，保留同一实体复用、不同实体区分及引用目标；这只是显示方式，不改变编译器的 typed/persistent identity。
- 普通结构测试不锁定无关源码 byte offset、内部 arena 分配序号或依赖摘要。源码位置、身份编码、确定性等本身是测试目标时，在相应专测中保留精确断言。
- 不用通用正则将所有 ID、hash、ABI 或 target 差异抹去。target 无关结构共用期望，ABI 等实际存在平台差异的结构明确保存差异。
- 专测只生成其实际检查的阶段输出，不默认要求一份输入同时冻结全部阶段。

不为测试修改生产语义，也不建立第二套 HIR/MIR/LIR 语义验证器。完整调试 dump 可以继续用于问题排查，不要求把调试输出全部提交为测试期望。

## 4. 符号、链接、产物与执行矩阵

### 4.1 移除普通用例的完整符号表

普通语言 fixture 移除 `nm` 全量输出快照，以及仅为这些快照存在的步骤。符号/ODR/链接专测按实际问题检查相关定义、引用、强弱绑定、唯一性、归档成员选择或动态绑定关系。

例如 ODR 用例应证明两个 consumer 最终共享所需定义，并保留运行验证；不能只凭“出现一个符号名字”判断成功，也不需要冻结整个 executable 的其他符号。原生输入选择和归档解析的专测可以保留小而受控的完整计划。

固定产物摘要仅留给编码或指纹规则的受控专测。缓存、重复构建和源码构建/独立链接的一致性继续比较本次实际生成的值，并保留独立的预期行为断言，避免两条路径同时出错却因相等而通过。

### 4.2 保留真正不同的执行路径

去掉快照不等于去掉跨 Cone、artifact-only、debug/release、GC stress 或平台运行覆盖。迁移首先保留这些执行路径，再根据实际验证的不同合同判断是否存在重复。

- 普通语言语义通过源码编译和运行验证；涉及导出模板、依赖身份、默认参数等跨 Cone 行为的用例继续使用真实 provider/consumer。
- 源码缺失、编译器不可用时的链接能力由专门的 artifact-only 用例验证，不要求每个无关语言用例都复制隔离环境与重链接流程。
- debug/release 继续覆盖优化前后的行为；只有优化或阶段结构本身不同的专测才需要分别保存结构期望。
- 含引用存储、捕获、协程、异常、FFI 等依赖 GC 正确性的用例保留必要的 moving/stress 运行；不为纯语法负向用例增加运行矩阵。
- 现有 Darwin/AArch64、Linux/amd64 GNU 和 musl 的适用行为继续验收。不能通过取消 target 声明来掩盖失败，也不因为去掉平台快照就停止平台运行。

共享源码与已有缓存可继续复用；同一个 provider 的结构仅由对应专测锁定。不要为消除声明中的重复增加通用 fixture 工厂、插件、依赖调度系统或逐 case 编排脚本。

## 5. 实施顺序

1. **先修订测试约定。** 更新 `AGENTS.md` 与 runner README，明确普通功能用例、结构专测及产物/后端专测的职责。语言和 runtime 合同保持原样；若实施涉及对外 dump 合同，先同步实现规范的相关说明。
2. **确定保留的代表组。** 检查现有用例，记录各结构专测负责的转换，优先保留小用例。将仅由巨大快照覆盖的必要事实转为明确断言；这是一份简短迁移说明，不建立强制注册表。
3. **清理完整符号表。** 先处理体积最大的普通功能套件；同步移除 snapshot 引用、`nm` 步骤和文件。专门的 ODR/native/link 测试保留有针对性的符号与绑定验证。
4. **移除普通 IR 快照。** 按套件迁移 HIR/MIR/LIR/AST 检查和仅为 dump 存在的参数，保留编译、诊断、运行及必要的产物操作；删除无引用的 golden。不得删除语言源码来满足精简目标。
5. **收敛残余重复。** 处理专测中重复的 provider/core 期望、无差异的 profile/target 副本，以及与被测行为无关的准备断言。优先删除重复断言而不是压缩、外置或改存整份输出的 hash。
6. **按新职责完成验收。** 分批运行受影响套件，最后执行全量验收，记录各 target 的实际结果及体积变化。已有失败单独说明，不能靠更新期望消除未知差异。

不要先执行全库 `--update-snapshots` 再开始精简。新增或修改保留的 golden 时，应先说明预期的结构变化，再生成并审查对应小范围差异。

## 7. 验收标准

### 7.1 覆盖与可审查性

- 普通功能 fixture 不再依赖 IR、完整符号表、整个 core 或其他无关实现输出的快照；编译诊断和运行期望仍明确且严格。
- HIR/MIR/LIR 各有少量职责明确的代表组；必要的跨 Cone、ABI、GC、优化、产物与链接合同仍有实际断言。
- 负向用例继续检查错误位置与信息；不能以删掉整个用例或只检查非零退出码替代精简。
- 保留的 golden 差异能直接解释为所测结构的变化；不含为了显示单个关系而展开的多 MB 单行或整个依赖世界。
- 测试期望来自明确的语言行为或阶段合同。运行结果、关键类型/调用目标、ABI 或 roots 真正出错时，相应测试必须失败，不能由宽泛匹配、过度归一化或自动刷新放过。
- 被测行为没有变化时，普通功能 fixture 不应需要更新期望。内部布局、dump 格式或编号调整只影响其确实相关的专测；core 无关改动不再要求批量刷新语言用例。

### 7.2 验证与记录

按仓库约定先格式化、lint，再运行测试。fixture 迁移运行公共 runner 规则测试和受影响套件；runner 或 dump 的实现变更补做相应 Rust/Python 检查。最终在三个现有 target 的适用环境完成正式文件 fixture 验收；`cargo test` 不能替代 CLI 验收。

验收记录给出实际基线、命令、target、通过/失败/不适用数量，并使用相同口径比较文件数、快照数与内容字节数。若比较耗时，注明机器、并发度和缓存冷热状态。本次设计未运行精简后的测试，不预先承诺缩减百分比或运行加速倍数。

完成的依据是职责收敛与必要覆盖保留，而非达到任意体积指标。降低体积不能依靠压缩快照、移到其他目录或仓库、冻结摘要、停止平台测试，或关闭正确性断言。
