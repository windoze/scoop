# Scoop 实现大纲

版本：0.7（草案）

配套文档：`SCOOP-SPEC.md`（语言规范）、`SCOOP-RUNTIME-SPEC.md`（运行时规范）。本文引用其章节号。

## 1. 总体技术路线

- 编译器实现语言为 **Rust**，LLVM 绑定使用 **inkwell**（feature `llvm22-1`）；个别 inkwell 未覆盖的 LLVM 子系统（statepoint / stackmap 等）可降落到 `llvm-sys`；
- 固定使用 **LLVM 22.1** 作为编译器后端，因为它与项目采用的当前stable Rust后端版本一致；M15及当前路线不包含LLVM升级。构建与driver启动必须确认实际链接的LLVM major/minor恰为22.1，不能接受PATH中另一个版本或在不匹配时继续生成目标文件；
- 使用 **LLVM stackmap** 生成 GC 所需的 metadata；
- 使用 **LLVM landingpad** 作为 exception 的基础设施；M25起Itanium target由Scoop自有personality与异常记录直接建立在Level I `_Unwind_*`接口上，不依赖C++ ABI（Windows / catchpad 留待后续）；
- runtime library 使用 **C 语言**，M15基线包含一个单代、STW、单线程collector的moving **Immix GC** 以及其他必须的 runtime 功能；分代及parallel/concurrent collector留待后续；
- Scoop永久不支持执行managed代码、访问对象图或允许对象复活的GC finalizer。M15 collector在不可达判定、evacuation和reclaim中不调用用户代码；未来只能按runtime spec 3.8增加typed GC-free release hook；
- M15首个可执行target固定为macOS/AArch64（Mach-O、LLVM stack map v3）。M22进一步把data pointer与code pointer恰为64位、两类AS0 null的内部carrier全零、且合法非null data/code地址可经各自内部64位carrier逐bit往返设为target-profile必需能力；它只限定pointer representation，不产生`ULong ↔ FunPtr`源码conversion。M22不引入platform-native integer：当前64位pointer/size source surface暂以`Long`/`ULong`表示，`Ptr`的raw往返使用`ULong`、元素offset使用`Long`，`sizeOf`/`alignOf`返回`ULong`；以后讨论native integer时再逐项决定这些surface是否及如何迁移。profile在生成任何IR前验证，不满足者明确诊断，未来开放其他宽度/表示须先修订语言与FFI/runtime契约。target profile必须在driver/codegen入口完整选择；其他target在拥有自己的platform adapter前明确诊断，不允许以M13保守扫描或非移动collector回退。section发现、frame/location解释、线程栈边界、arena reservation与虚拟内存保护均隔离在runtime platform层。

## 2. 编译器 pipeline

**模块边界**：stage 之间只通过 IR / meta crate 交换数据——AST、HIR、MIR、LIR 的定义（含各自的 `.slib` meta 格式）独立成 crate，作为 stage 之间的通道。每个 stage crate 只负责把输入变成输出，只依赖其输入/输出的 IR crate，不了解、不依赖上游 stage 的实现；stage 之间的编排由 driver 负责（见 2.7）。

### 2.1 parser / AST

解析源代码，为每个源文件生成语法树。

lexer 对坏字符及可恢复的字面量错误继续扫描；parser 分别以顶层声明、类型成员、块内语句为同步边界，在一次解析中收集同一文件的多个独立诊断。诊断按源码顺序输出；只要存在任一诊断，恢复得到的残缺 AST 必须整体丢弃，不得进入 HIR。

M19起class/struct body使用保留源码顺序的typed member sum，而不是把method单独抽成列表后丢失property initializer与`init`的交错位置。AST分别表示普通/`val`/`var` primary parameter、secondary constructor、`this`/`super` delegation、stored body property、`init`和`super.method()`；supertype列表逐项保留constructor argument list是否出现，不能在parser按“有括号即class、无括号即interface”提前分类。`super`不解析成普通name expression，constructor/init/property恢复以type body item为同步边界。

M20起call/constructor显式type-argument entry用`Explicit(TypeRef)`与`Infer(span)`的封闭sum区分普通类型与`_`。nominal type application仍只保存参数完整的普通`TypeRef`列表；parser不把`_`伪装成名称或缺失type，malformed显式列表在当前`<...>`恢复，不能吞掉后续value argument list或比较运算符。type parameter declaration或type application中的`in`/`out`/`*`不属于语言语法，按所在声明/type list产生稳定诊断。

M21起AST以封闭property body sum表示initializer+accessor、Option omitted、computed、delegated、abstract、const与extern/raw storage候选形态，并完整保留property/accessor/constructor visibility、annotation、modality、extension receiver/type parameter、setter parameter及span；不能用`initializer: Option<_>`、`delegate: Option<_>`和若干bool拼出非法组合。所有可带visibility的AST节点以`VisibilitySyntax::{Explicit, Omitted}`保留来源，不能用缺失值表示待后续猜测；setter omission另由专用variant表示继承property。class/object body继续保留property/delegate/`init`的源码顺序；object、companion与static nested declaration保存typed owner语法关系。`lateinit`只产生稳定诊断，成功AST没有对应flag；`super<I>`使用专用qualified-interface-super节点，不降级成普通generic name/call。

M22起integer literal AST保存无符号magnitude、radix、suffix与span，不在lexer压成`i64`；magnitude超过`2^64 - 1`的token产生可恢复诊断。普通表达式、annotation argument及其他受限常量语法必须引用同一literal syntax payload，不能保留平行的`AnnotationArg::Int(i64)`入口。AST以独立节点保存top-level非generic typealias、`StatementKind::For { pattern, iterable, body }`、`StatementKind::Break`、`StatementKind::Continue`与`Expr::CopyUpdate { base, NonEmpty<FieldUpdate> }`。Break/Continue只在spec第5章规定的statement/body位置成功解析，不得建立对应Expr variant或伪造`Nothing`类型；一般jump expression产生稳定未支持诊断。字段pattern保存字段标识符加boxed完整subpattern，不再用`rename: Option<Ident>`限制语义。range/rest/copy-update按表达式、pattern与postfix位置消歧；label、do-while与generic/nested alias只产生稳定未支持诊断，不能进入成功AST的半成品variant。

M23起每个AST输入对应一个带`ConeIdentity`与normalized Cone-relative path的source file。`SourceFile`以非可选`RootPackage | QualifiedPackage`保存至多一个文件头`package`，随后保存零个或多个`ImportSyntax::{Exact { public, path, alias }, Star { public, path }}`，最后才是declaration；package/import/declaration各有独立恢复边界。qualified path只保存非空identifier sequence，package、nested owner与entity的分界由HIR的typed namespace解析，parser不得把连接后的字符串当FQN。star import不能带alias；manifest、source discovery和依赖图不属于AST，由driver提供typed输入。

### 2.2 HIR

负责 desugaring、type check 和 overload resolution；综合上游 Cone 的 HIR export representation；解析每个表达式/子表达式的 type，解析每个 callable 的 target。输出不是一个同时容纳parameterized与concrete节点的`Module`，而是按消费者严格隔离的两个IR：

- **`ExportHir`**：只供下游Cone的HIR阶段消费，并在结构上区分普通public/re-export lookup surface、公开owner跨Cone继承所需的protected inheritance/slot surface、以及exported generic template的hidden support closure；后两者不能枚举为普通import binding。它还包含非generic concrete声明的签名/成员/属性、导出的`const val`、non-generic typealias及作为callable接口在调用处展开的hygienic typed default template。default template节点只能使用带非可选调用域覆盖证明的kind-specific export-interface reference，不携带private/internal hidden dependency closure；普通`Export*Id`仍可能索引generic hidden dependency，不能直接代替这种refined reference。它不包含本Cone局部产生的concrete实例体；
- **`LocalConcreteHir`**：只供本Cone的MIR阶段消费。它包含本Cone需要发射的全部local non-generic及fully instantiated type/function/body，并以封闭typed ref保存body实际使用的imported param-free external target；其中不允许出现type parameter、parameterized type/body、待完成的实例化请求或上游param-free implementation body。

二者必须是不同的Rust输出类型，并使用互不兼容的实体id家族，例如`ExportTypeId`/`ExportFunctionId`与`ConcreteTypeId`/`ConcreteFunctionId`。禁止用同一个arena index、type alias、共享`TypeId`或运行期tag区分两侧实体。一个源码声明同时需要导出语义接口和本地实现时，HIR显式生成两个实体并保存类型化映射；不能让两个消费者读取同一节点的不同字段。

`ExportHir`中的param-free导出声明不等于`LocalConcreteHir`实体：前者是跨Cone语义接口，后者是本地可执行实例。下游HIR确实需要前者来完成非generic调用、继承/接口检查、构造、重载、默认参数和const求值，但绝不能读取或重新发射origin Cone的concrete实例body；winner必须成为携带persistent origin与完整signature的external target。反之，本Cone MIR不得读取generic template；HIR必须先对实例化需求做固定点闭包、完成类型替换并生成结构完备的本地`LocalConcreteHir`实例体。

所有**源码语义错误**必须在parser/HIR结束；之后的stage不再补做名称、visibility、generic inference、import或其他源代码错误处理。manifest/source discovery/dependency错误由driver报告，`.slib`结构/兼容错误由reader报告，ODR、native link与最终artifact错误由link orchestration报告；这些构建期错误不能伪装成HIR诊断。

编译诊断以封闭的`DiagnosticSeverity::{Error, Warning}`携带severity，renderer不得从message文本猜测类别。parser恢复得到的诊断当前全部是`Error`；HIR把已提交的错误与warning保存在两个独立journal中，候选事务现有的`diagnostics.len()`基线只观察错误journal。probe只有winner整体commit时才提交其中的warning；失败候选只提交其选中的错误原因，clone-only分类probe则两者都不提交。HIR只有在错误journal为空时才输出结构完备的`ExportHir`与`LocalConcreteHir`，但warning无论多少都不阻止该输出；成功`HirOutput`另行携带按source span稳定排序的warning。warning不是语义IR，不进入任一HIR module、meta、dump、fingerprint或MIR输入；发生错误时，只报告真实已提交路径上的warning，不得泄漏被拒候选或分类probe中的warning。

第5章规定的enum `when`疑似variant拼写warning在pattern完成typed resolution时产生：对每个实际提交的裸binding occurrence，若它位于`when`模式、当前递归匹配列的exact静态类型是enum且该enum没有同名variant，则该pattern仍正规化为catch-all binding，并在该identifier的精确span发出一条warning。该规则不扫描其他enum、不按大小写或相似度猜名称；已解析variant、qualified variant、`_`/`else`、非enum列及`when`之外的irrefutable binding均不发出。递归子pattern按自己的exact匹配列独立应用同一规则。

HIR负责解析所有type parameter：每个generic调用确定全部具体类型实参（含对上游Cone `ExportHir` template的实例化请求），随后对调用图和类型依赖做固定点闭包，并在`LocalConcreteHir`中生成完成替换的concrete实例体。MIR不接收template、推断变量或待处理实例化需求，也不读取template后自行替换`TypeParam`。

每个`ConcreteTypeId`索引的实体都必须携带非可选的`gc_free: bool`。concrete enum实体还必须为声明顺序中的每个concrete variant携带非可选的`gc_free: bool`，enum自身的flag恒等于全部variant flag的逻辑AND。不存在“未知”的concrete类型，也不得使用`Option<bool>`、默认false、延迟回填或MIR/LIR递归字段来补齐该属性。尚未特化的generic template不是concrete type，可以在`ExportHir`中携带类型化GC-free条件，但该条件不是flag。导出的param-free concrete语义类型可在`ExportHir`中复制同样完备的属性供下游类型检查；它使用export侧id，不与本Cone的`ConcreteTypeId`共享身份。

M16起，所有命名调用、成员/扩展调用、generic nominal构造、enum variant构造、operator调用和callable reference resolution共用一个HIR调用决议内核；M18把property-like `invoke`作为同一内核的新typed candidate组合。词法/receiver/import层内还要执行function-like与property-like的c-level分区。每个最终分区先做显式type-argument arity、receiver与调用形态等不依赖表达式类型的预过滤，再逐候选检查applicability并选择第一个至少含一个可应用候选的分区；每个候选独立拥有source-argument mapping、fresh inference variables、constraint set、postponed arguments及失败原因。single-candidate调用也必须进入同一可应用性管线，不能保留一条按元数直接lower的捷径。

M23把import层具体化为typed binding source。无显式receiver的顺序为lexical/local → implicit `this` member → 当前文件exact import → current package → star import → core prelude → expected enum application的contextual variant fallback；显式receiver的真实member先于extension，而extension依次使用exact import → current package → star import → core prelude。相同persistent origin在同层合并为一个target并union其非空、canonical排序的`CurrentCone | DirectDependency { provider ConeIdentity, export binding id, witness hops }` source集合；不同origin保持候选。public import要求source全部是DirectDependency，菱形路径不能按first-loaded丢弃。每层仍遵循上一段的candidate-local applicability与“首个存在适用候选的层”，不得按dependency顺序、`.slib`来源或re-export路径增设tie-break。

调用与值构造的泛型推导对整组已映射实参执行constraint固定点求解，不得按从左到右的一次遍历决定成败。constraint递归穿过invariant nominal application与function type variance，并同时检查kind/class/interface bound；显式`_`只创建与整组省略时相同的candidate-local fresh variable。lambda、callable reference、裸enum variant（包括`None`）、空数组及依赖expected type的嵌套构造可以postpone到其他约束推进后检查。MSC使用与本次actual inference隔离的pairwise fresh-variable forwarding system，不能比较两个候选已经推断出的concrete arguments。solver内部可以暂存未固定变量，但winner commit必须原子地产生全部concrete arguments、完整实参映射、coercion和唯一typed target；未解、多解或bound失败只能形成HIR诊断/候选失败，不能输出给下游补齐。

M17起，AST保留位置、命名、spread及尾随lambda的源码顺序；HIR按候选分别映射而不先公共重排。目标选定后，receiver先求值，所有显式实参各自保存独立desugaring sink并按源码顺序拼接；随后按形参声明顺序构造vararg值及实例化实际使用的缺省表达式，最后才产生按形参顺序排列的call arguments。类型检查/constraint求解顺序不得改变这套运行期顺序。若这些temporary/sink位于`while`条件，HIR必须把它们保存在随条件重复执行的typed condition-setup区域，MIR在每次条件检查前执行该区域；不得把它提升到循环外，也不得因sink非空而拒绝普通调用或空安全脱糖。跨挂起点存活的已求值显式实参和部分物化参数使用普通M10 frame规则，不能在恢复后重新求值。

默认表达式在定义方HIR环境中完成名称解析、overload选择和类型检查，成为callable source interface中的hygienic typed template。HIR在const folding/desugaring前收集其直接绑定实体，并结构化检查`CallDomain(callable) ⊆ AccessDomain(entity)`；exported `public` default只能引用export/re-export实体，不能通过携带private/internal实体、保留未解析名称或调用方重查overload来绕过。成功结果为callable/type/property等每种实体分别生成refined export-interface reference；该reference非可选地携带目标typed id及`ExportDefaultAccessWitness`，普通`Export*Id`不能无检查转换为它。generic function body仍可按既有规则拥有自身的private/internal typed dependency closure；该能力不扩展到default template。

导出default使用`ExportDefaultExprId`及逐节点definition origin，非导出callable使用类型不兼容的`LocalDefaultExprId`；HIR内部只能通过封闭的`DefaultExprTemplateRef::{Local, Export}`把二者交给同一个实例化器，任何一类id都不得进入`LocalConcreteHir`。导出callable的参数metadata以封闭sum区分required、default template、vararg-empty与vararg-default，不用`Option<Expr>`加旁路布尔值拼出状态。template尚未对应一次具体求值，因此template类型不含可选evaluation origin；winner commit后的每个concrete expression则必须携带由不同类型组成、两个字段都不可缺失的`ConcreteExpressionOrigin { definition, evaluation }`。普通表达式的evaluation来自自身源码求值点；default实例保留template节点的definition，并统一使用发生缺省的call expression已有的evaluation。若该call也来自default实例，这一规则自然沿实例化链传播；进入独立callee或延后执行的lambda/local-function body时恢复该body自身的普通来源。

默认template实例化器只在winner与完整type arguments已经确定后执行完整type substitution、前置parameter value绑定与上述通用origin构造，然后把展开结果作为调用处普通concrete expression交给统一lowering；它不得重新做名称/import/extension/overload决议，也不得依赖intrinsic registry、匹配callee identity或按expression kind建立专用分支。需要观察求值位置的语言设施统一读取所在concrete expression的evaluation origin。`current_source_location`只是普通HIR intrinsic consumer之一，不是default实例化协议的一部分；definition/evaluation也不能以覆盖节点span、`Option`缺失后回退或consumer反推的方式互相冒充。

`LocalConcreteHir`中的函数/构造签名只保留callee执行所需的实际参数类型；每个call具有唯一concrete target、完整concrete type arguments及按形参顺序排列的全量参数表达式。命名参数、遗漏参数、source spread、default template、未物化vararg、`_`和inference variable一律不得进入`LocalConcreteHir`，因此MIR不知道也不重新实现源码调用协议。函数值调用从一开始就是函数类型元数对应的精确位置参数调用，不经过default/vararg declaration metadata。

M19起primary与每个secondary constructor都是独立typed callable entity，但不能用普通`FunctionId`表示：class/struct source constructor id、带完整host type arguments的constructor application id、LocalConcrete initializer id分别使用kind-specific id家族。M17的parameter source interface、default template key与调用域证明引用具体constructor id，不再用`ClassId`/`StructId`代替primary owner。primary parameter、class declared field与layout field也使用不同id；只有写`val`/`var`的primary parameter显式关联field，普通primary parameter没有field relation。constructor不声明自己的type parameter，其application只携带exact nominal owner arguments。

HIR在模板定义阶段把primary与secondary一起送入M16/M17 candidate-local constructor resolution，完成duplicate signature、`this`/`super`唯一target、primary/base形态与delegation graph termination/cycle检查。class common initialization按源码顺序保存body property initializer与`init`；lowering时以typed `InitializedFieldSet`检查self/forward access，并用不能转成普通expression的`InitializingThis` capability限制receiver只做已就绪field direct read/write。失败candidate或无效declaration不得分配永久constructor application、default实例、graph edge或初始化body。generic nominal的constructor、delegation、initializer与init body在exact owner application确定后由HIR一并具体化。

`LocalConcreteHir`必须把class construction表示为exact class allocation target加唯一initializer，把base/`this` delegation表示为same-receiver typed initializer direct call；terminal constructor结构上携带恰好一份primary store/common initialization，`this`-delegating constructor不能携带第二份。abstract class保留供derived `super`使用的initializer但没有合法allocation expression。struct secondary constructor是独立的typed value-returning callable，先取得delegated完整value再执行body。`InitializingThis`、field readiness、source member order、未验证delegation及“是否运行common init”的布尔flag都不得进入LocalConcrete输出。

普通member body中的`super.method()`在HIR只收集direct base application的class member candidate，winner同时保存具体callable与强制direct证明；extension、property-like与interface default不进入候选。它可以在LocalConcrete中正规化为direct method call，但不得只保留virtual family或method name让MIR重新判断分派。

M21把field/global读取统一到logical property模型。Export HIR中的每个property非可选地保存owner、name、type、read-only/read-write capability、`DeclaredVisibility`、`EffectiveLookupDomain`、可能的`SlotContractDomain`、getter/可能的setter typed ref、override/interface slot relation及互斥implementation representation；三种access类型不能互换，read-write capability也不能用`mutable + Option<setter>`表示。implementation以stored/accessor-only/delegated/const/extern-raw为外层sum；accessor-only的每个required getter/setter再使用`AccessorImplementation::{Body, AbstractSlot}`，从结构上表达interface混合default/abstract，不能用body `Option`加`is_abstract`。各分支只允许构造对应的`BackingFieldId`、`DelegateStorageId`、`InitializationUnitId`或const/native identity。property、getter、setter、backing field、delegate storage、global storage及interface accessor slot均使用不同typed id。

HIR按spec 9.1.1在Option-omitted分支验证outer exact `Option`与`var`后生成普通typed `None` initializer；任何其他缺失initializer都必须落入computed/abstract/extern的合法结构或诊断。不存在late-init state、hidden bit或专用exception。stored accessor中的`field`直接绑定backing id且不进入nested closure scope；initializing receiver只能direct访问已就绪backing field，computed/delegated accessor仍不能成为绕过M19 readiness的调用路径。

property read/write分别进入M16候选与M18 c-level/place管线，winner原子产生唯一getter/setter target、receiver evaluation与effect。generic extension property的type parameter只由receiver求解；M23允许generic delegated extension，并以origin property persistent id与完整exact receiver arguments形成program-wide specialization key。delegate的`provideDelegate/getValue/setValue`在声明处验证成三种独立typed role，在property定义处按普通candidate-local规则选择；每个consumer在LocalConcrete前完成template substitution，产生lazy exactly-once的effective delegate storage、root、init cell/failure slot、initializer/ensure和descriptor的完整ODR组，不保留role name、`by`节点、KProperty或反射metadata。相同specialization经不同Cone使用时必须链接为同一组地址，不能各自登记一份storage/unit。

M21的access domain是typed set/domain结构，不是可按枚举大小比较的visibility数字。HIR首先把每个普通`Omitted`正规化为typed Internal；override/constructor/interface member没有继承或隐式public特例，setter omission才继承property。随后分别计算owner intersection后的`EffectiveLookupDomain`、owner modality/access决定的`InheritanceDomain`和override声明承担的`SlotContractDomain`：override coverage比较最后一种，候选可见性比较第一种，abstract obligation要求slot覆盖inheritance domain，signature exposure覆盖lookup与slot的并集，不能拿一种witness代替另一种。HIR再对protected receiver、public-interface contract、setter narrowing、const folding和M17 default witness统一执行集合包含检查；成功candidate/accessor/default/export ref携带用途专属的access witness。private/internal实体不能因存在link symbol、core身份或被频繁使用而进入public Export候选，public member也不能扩大narrower owner的直接查找域；internal/private owner中的显式public override仍可合法填充public slot。entry-point检查可接受internal top-level `main`，但不把它改写成public声明。

object type、singleton value、companion relation、published root与initialization unit使用不同id；generic host companion结构上不含host argument。object复用M19 allocation/common initialization，但LocalConcrete只在完整初始化成功后产生typed publish operation。top-level runtime property/delegate和singleton各自拥有generated initializer及typed unit；HIR只对unit自有、脱糖后的initializer/delegate/base-argument/`init`body中的直接unit ref建图并诊断结构环，普通call/constructor/default/dynamic/FFI造成的re-entry交给runtime gate。LocalConcrete的typed ensure operation非可选地携带unit及已解析的`IllegalStateException(message)` concrete constructor；MIR才把它展开为`RunInitializer`/`Ready`/`Failed(rooted Throwable)`/`Cycle(GC-free stable path)`结果与对应CFG，LIR/runtime不得按core名称补目标。core exception contract验证“可用的零实参调用”而不是源码parameter count，使带default message的constructor仍满足既有compiler-generated调用。const在HIR完成visibility、依赖环和常量求值后成为普通typed value，不生成getter/storage/unit。

interface function/property accessor按slot保存abstract/default body。HIR对每个exact owner先应用class-hierarchy实现，再选择唯一most-specific interface default；未实现与互不相关default冲突在定义处诊断。`super<I>`只接受direct superinterface上的concrete default并保存强制direct typed target。LocalConcrete/后续itable已明确为class/value implementation、interface default或adjust thunk，不保留候选集合或“以后选择default”的flag。

generic nominal的HIR类型只表示参数完整的exact application，class/struct/enum/interface继续使用kind-specific application id。实现/继承列表同样保存exact application；所有nominal参数固定invariant，HIR在声明/type位置拒绝`in`、`out`与`*`，并在subtyping、LUB与推导中要求同template实参逐项相等。MIR为每个实际使用的exact application建立独立单态化实体/TypeDescriptor；不得把不同实参擦除到裸template id。

M14起，class/struct/enum/interface全部进入统一generic nominal单态化管线，并且每个declaration kind使用独立id家族：`ExportGenericClassId`/`ExportClassApplicationId`/`ConcreteClassId`、`ExportGenericStructId`/`ExportStructApplicationId`/`ConcreteStructId`、`ExportGenericEnumId`/`ExportEnumApplicationId`/`ConcreteEnumId`、`ExportGenericInterfaceId`/`ExportInterfaceApplicationId`/`ConcreteInterfaceId`。template、带完整exact argument的export application与fully specialized local entity三层id在Rust类型上互不兼容。禁止恢复`Type::Struct(StructId, Vec<TypeId>)`、`Type::Enum(EnumId, Vec<TypeId>)`、`Type::Interface(InterfaceId, Vec<TypeId>)`或`ClassId + Option<Vec<TypeId>>`等混合表示。每个concrete entity非可选地携带local-concrete侧kind-specific origin、全部concrete arguments及已替换的field/variant/base/parent/interface/member闭包；origin与export template/application id类型不兼容，显式映射只属于HIR concretizer。class使用ordinary/intrinsic representation sum且`gc_free=false`，struct/enum按exact payload生成完整`gc_free`与scan，interface exact application以`gc_free=false`形成独立TypeDescriptor/itable identity。class/struct/enum构造与普通调用使用同一固定点。M20起所有nominal application保持invariant；裸application、少写参数、声明点`in`/`out`及type argument中的projection/star均在HIR诊断。

M20起，`ExportHir`为每个type parameter保存互斥的kind bound或结构化nominal bound set；后者以`None | One(ExportClassBoundId)`表达至多一个class bound，并携带零个或多个interface bound，每个bound保存exact application typed id与来源span。generic template中对有界receiver的调用保存typed `BoundCallableRef`；本Cone或下游Cone实例化必须把它解析为完整direct/virtual/interface信息。`LocalConcreteHir`不得含bound placeholder、未验证constraint或runtime dictionary。`ToString` / `Hash`只使用源码显式conformance；conditional equality仍由HIR证明并生成具体成员，不能把未知交给MIR。

M14起，non-interface generic method使用独立的`ExportGenericMethodId`与`ExportGenericMethodApplicationId`；application结构化地携带kind-specific owner host（param-free nominal declaration或generic nominal application）与method自身实参，不能用一个无分组的type-argument Vec同时冒充两组参数，也不能假设generic method必然属于generic owner。HIR在声明处拒绝generic method的open/abstract/override/interface-slot形态；exact owner完成宿主substitution、method实参推导与全部bound检查后生成direct `ConcreteCallableId`。`LocalConcreteHir`中的每个origin非可选地保留独立的`ConcreteGenericMethodOriginId`、kind-specific `ConcreteClassId`/`ConcreteStructId`/`ConcreteEnumId` owner和非空method arguments，宿主实参只从该complete owner实体读取，不再平行保存一个可能为空或错位的Vec。generic宿主上的普通成员另有`ConcreteOwnerParameterizedMethodOriginId`，不能借方法名或owner origin代替方法自身来源。两类origin都不能表示或索引export template；HIR concretizer显式完成两侧identity映射。MIR再次建立本stage的generic free function、owner-parameterized method与generic method三组互不兼容的source id；每个instance结构化携带exact concrete owner、owner arguments与method arguments，禁止重新压平成单个Vec或用display name充当provenance。callable reference仍必须先形成单一concrete application，不能输出polymorphic closure或让MIR从expected function type补实参。

HIR concretizer必须在模板图上分别维护nominal/callable/predicate的typed instantiation state。generic callable递归SCC中，每个环组合后的owner+callable参数替换必须为identity；合法普通递归在exact concrete key处复用已经intern的`InProgress`实体，非identity环作为polymorphic recursion在HIR诊断，不得凭深度、实例数或超时截断。`is`/`as`/`as?`目标必须引用参数完整的exact nominal application及其TypeDescriptor，不能擦除type argument或制造template-only通配descriptor。

M14还允许registry批准的core struct/class使用`@Intrinsic`省略源码representation。registry声明同时区分fixed representation与generic representation family，并完整规定declaration kind、type-parameter arity/bound及声明contract；全部参数固定invariant。HIR必须把这类声明正规化为封闭typed `IntrinsicTypeKind`，把每个generic intrinsic application正规化为携带完整concrete参数的typed family representation，并在`ExportHir`/`LocalConcreteHir`各自的id家族中显式携带；不能表示为空字段普通类型。除下述`Ptr`封闭特例外，implements、成员与用户可见constructor都来自源码语义表面；literal、boxing、allocation等hidden construction entry使用独立compiler entity，不进入overload候选。`Array<T>`/`MutableArray<T>`使用普通generic class application identity，旧的独立built-in array type identity必须删除；数组专用expression可以保留，但直接引用concrete class及element type。intrinsic kind/application同时确定GC-free/representation classifier所需的语义输入，具体layout仍由LIR按target生成。M22把`Ptr<T>`/`FunPtr<F>`分别登记为以exact GC-free value pointee type/ordinary function type参数化的data/code-pointer representation family；二者都没有普通field或primary constructor，不能进入普通字段访问、解构或copy-update路径。`core_ptr`的源码kind bound之外另有typed `RequiresGcFreePointee` application predicate：Export template保存并沿generic调用/type构造传播，LocalConcrete application必须已证明，不能以`T : value`或默认bool代替。`Ptr`另有registry封闭规定的`@NoGC @Unsafe` nonzero-ULong construction entry，winner立即正规化为typed `PtrFromNonZeroULong`；可证明的零值诊断且失败candidate不产生节点。`FunPtr`没有任何源码construction entry，任意`FunPtr<F>(...)`都不能进入成功HIR。两者内部全零pointer只由对应`Option.None`等niche lowering产生，不是裸pointer值。

M22把整数intrinsic fixed representation统一扩为`Integer { signedness, width }`封闭族；每个实体仍是core nominal struct identity，不把表示kind当作源码type id。八个canonical声明固定为`Int8`/`Int16`/`Int`/`Long`的i8/i16/i32/i64与`UInt8`/`UInt16`/`UInt`/`ULong`的u8/u16/u32/u64。`Byte = Int8`、`Short = Int16`、`Int32 = Int`、`Int64 = Long`及`UByte = UInt8`、`UShort = UInt16`、`UInt32 = UInt`、`UInt64 = ULong`均通过普通transparent alias解析到对应唯一identity；`Int`/`UInt`不再是64位type或`Long`/`ULong`的alias。alias声明使用与type id不同的`ExportTypeAliasId`/resolver内`SourceTypeAliasId`，保存visibility、origin、typed target与M21 signature-exposure witness；展开图在HIR检查无环，完整target type tree的access domain必须覆盖alias domain，展开后的签名参与重复声明检查。alias不进入LocalConcrete type arena、layout、RTTI或mangling。真实跨Cone序列化由M23消费Export接口。

integer intrinsic registry把每个源码name一对一正规化为`IntegerType(IntegerKind)`、`IntegerOperation::{NoGc { kind, operation: NoGcIntegerOperation, target: NoGcCallableRef }, Managed { kind, operation: IntegerDivRem, target: ManagedCallableRef }}`或`IntegerConversion { source, target_kind, target: NoGcCallableRef }`；不同variant直接持有不同Rust类型的call target，不能表达operation/effect互相矛盾的状态。八个kind的登记key固定为`int8`/`int16`/`int`/`long`与`uint8`/`uint16`/`uint`/`ulong`：type、member与conversion name分别使用`core_<key>`、`<key>_<operation>`、`<source-key>_to_<target-key>`。完整operation集合为全kind的unary-plus/minus、inc/dec、add/sub/mul/div/rem、compare-to/equals、and/or/xor/inv/shl/shr与signed-only ushr；`IntegerDivRem`只含div/rem，`NoGcIntegerOperation`含其余项，全部conversion也只能产生NoGc target。registry同时验证零/一参数、owner exact operand/result、shift的`Long`（I64）count、compare-to的`Long`（I64）结果、equals的Boolean结果及源码`@NoGC` presence与variant精确一致。`core_int`/`int_*`从M22起表示i32 `Int`，i64使用独立`core_long`/`long_*`；unsigned对应为表示u32 `UInt`的`core_uint`/`uint_*`与表示u64 `ULong`的`core_ulong`/`ulong_*`。任何kind都不能复用另一kind的provider。provider唯一性在结构化key与对应唯一源码name上验证，LocalConcrete以后不得保留annotation字符串或未类型化effect。

integer literal在M16 solver内使用candidate私有`IntegerLiteralConstraint`，同时覆盖argument与receiver定型；receiver probe只枚举total `IntegerTypeCore`的八个owner，并只对已验证integer intrinsic或普通core range member继续普通member resolution，不能全局扫描用户/extension member。winner commit原子产生exact nominal type与HIR crate自有的`HirIntegerConstant::{Signed8(u8), Signed16(u16), Signed32(u32), Signed64(u64), Unsigned8(u8), Unsigned16(u16), Unsigned32(u32), Unsigned64(u64)}`之一。raw payload恰为W位且kind由variant派生，不能用平行`kind + u64 bits`表示高位/width可矛盾状态；nominal owner由total `IntegerTypeCore` map取得。无exact expected type时，无后缀literal按`Int`（i32）→`Long`（i64）选择首个可表示type，`u`/`U`按`UInt`（u32）→`ULong`（u64）选择；`l`/`L`只能提交为`Long`，`uL`/`UL`等组合只能提交为`ULong`。带exact expected type的无后缀或单`u`字面量仍可提交到同符号族的其他可表示固定宽type。由magnitude/suffix得到的default exact kind tie-break只在普通MSC及M17附加规则仍并列后运行；失败candidate不得写入literal/type/application arena。literal constraint、radix和suffix不进入`LocalConcreteHir`。const folding输出同一HIR typed constant，并与运行期wrapping/division/shift规则共享语义实现或测试向量；HIR/MIR/LIR中的const、annotation/default metadata、global/static initializer和constant image必须分别携带各自IR crate拥有、由相邻lowering穷尽转写的同构typed constant，不能跨crate type-alias或保留任一裸`i64`旁路。

M22的source-visible宽度迁移在HIR core-contract验证中是封闭inventory：Array的size/index、`Hash.hash()`、所有integer及String的`compareTo`、integer shift count、`SourceLocation.line/column`、`@CLayout(aligned/packed)`参数及foreign callback `contextIndex`均必须是`Long`（I64）；`Ptr(raw: ULong)`及`toULong(): ULong`与`sizeOf`/`alignOf`使用`ULong`，pointer load/store/plus/minus的元素offset使用`Long`。ROADMAP排在M24的String length/index/slice尚未进入M22实现子集；M24增加这些surface时必须直接使用`Long`并把它们加入同一封闭core-contract inventory，不得先引入`Int`过渡签名。这些是为保留64位API语义做的源码类型迁移，不表示同宽的compiler/runtime metadata或raw pointer carrier获得`Long`/`ULong`身份。HIR IR crate自己拥有封闭`HirCLayoutValue::{Natural, A1, A2, A4, A8, A16}`与`HirCLayoutContract { aligned: HirCLayoutValue, packed: HirCLayoutValue }`；annotation的`Long`常量在进入成功HIR时立即正规化为该sum，不能把任意`u8/u64`对齐值交给下游。`LocalConcreteHir`中的compiler-owned static storage同样使用HIR自有的`HirStaticInitialState::{ZeroedForRuntimeUnit, EncodedStaticValue { payload: HirConstantImage }}`；`HirConstantImage`的integer leaf使用本节的`HirIntegerConstant`，pointer null携带provenance，aggregate leaf携带HIR exact type/id。Export HIR中需要传播的C-layout contract也只引用HIR侧类型，不能引用MIR/LIR crate的同名类型。

M22在HIR一次验证并输出非可选`IterationCore`：core Iterator template、`next` exact interface slot、Option template与Some/None typed variant。source `for`先按M18选择唯一iterator operator，再验证winner返回type去重后的exact `Iterator<T>` conformance；协议不参与回退选择另一个operator。每个使用点提交结构完备的`ForIterationPlan`，至少原子保存iterator call/result type、exact Iterator application、conformance/boxing witness、specialized next slot、exact Option application/variants、element type、binding plan与LoopId；全局`IterationCore`不能代替use-site witness。generic bound中的conformance在template阶段保存typed witness，不能留到单态化后按名称重查。HIR为每个循环分配不可跨callable的typed `LoopId`；Break/Continue直接引用目标。进入lambda、匿名函数或局部函数时重置loop stack。

val/var、lambda与for共享由Export HIR crate拥有的typed `IrrefutableBindingPlan`数据模型，并由HIR lowering构造。val/var与lambda在提交Export HIR前消费该plan并展开为普通typed statement；source `for`把同一plan保存在完整`ForIterationPlan`中，generic concretization只映射其中既有typed ref，source `For`最迟在LocalConcrete HIR结束前连同binding plan一起展开，MIR不接收source plan。除`_`及内建`Unit` literal写法外，binding位置的普通裸标识符直接形成新binding，不查询subject enum、import或既有value；`Unit`/`()`仍是literal并在binding plan中拒绝。显式`E.V`、`V()`、`V(...)`或`V { ... }`等shape只有按subject exact enum解析成功时才作为refutable variant拒绝，解析为struct的同形pattern继续按积类型处理。每个plan原子保存一个typed subject、immutable subject/投影/component temporaries、声明序完整field shape mapping、源码序depth-first runtime actions、typed component winner与叶binding mutability；没有投影、component或后续action的单一根binding允许把subject storage与该叶binding合并，这不改变求值次数、mutability或ABI。class component只通过M18 typed `Component { index }` role，写出的N个位置精确解析`component1..N`且不接受rest。lambda的一个composite pattern仍是一个logical source/function-type parameter，并只对应一个typed ABI classification entry；不得按叶binding flatten，物理`ElidedZst`/`Direct`/`Indirect`以及closure environment/suspend continuation保持独立。component抛出时跳过后续action但不回滚既有外部副作用；挂起前由普通coroutine liveness保存恢复后仍活跃的subject与已完成temporary，不为已经dead的wildcard/投影结果增加hidden keepalive；正常恢复后保存本次结果再继续，异常恢复等价于原call点throw并跳过后续action。plan构造的名称、field、component、effect与type检查在同一事务中完成，成功只提交到紧邻拥有者；嵌套于overload candidate的lambda plan保持candidate-private直到外层winner，失败只保留该路径选定的稳定诊断并回滚全部暂存实体。

match pattern另行正规化字段/rest并进入递归constructor matrix。parser在binding/match位置都保留同一完整pattern syntax，二者只在结合subject type后的HIR分类不同。`Unit`/`()`优先形成内建Unit literal；其他enum subject裸名再查询同名variant：unit variant形成constructor，payload variant缺少显式shape时报错，仅名称未命中才形成带warning的catch-all binding，enum同名`Unit` variant必须限定或写出payload shape。字段shorthand精确等价于`field: field`，展开后的RHS始终重新执行所在上下文的完整分类；因此binding中的`{ Unit }`也按Unit literal拒绝而不创建binding，须写`Unit: value`，match则在相同Unit特例之后才执行其他名称的variant-first分类。struct与enum payload字段分别使用不可混用的checked field ref，声明序完整shape vector与源码序runtime action list共享ref而不共享裸index。constructor至少区分enum variant、Boolean、Unit、tuple/struct product、fixed-integer literal partition、open String literal与wildcard。integer partition以u128等能表达`2^64`的内部cardinality和去重singleton/interval表示`OtherInteger`是否有实例，不能枚举值域或无条件要求wildcard；negative literal在subject expected kind下复用普通literal commit/unary-minus折叠。guard行不贡献coverage；成功检查产出missing-witness-free proof与typed decision plan。只有proof允许`Impossible` default edge，不能按最后arm或variant名称计数。

source CopyUpdate与contextual bare variant分别使用事务式typed plan/candidate。CopyUpdate先lower base并解析其exact type；若不是具有声明字段的struct，特别是任何enum，则在建立字段candidate、lower或求值RHS、以及commit plan之前产生稳定诊断并退出。合法struct winner把base按值保存到不可变typed temporary；成功plan原子保存exact struct application、经definition检查的`AppliedStructFieldRef`、源码顺序RHS及声明顺序重建mapping。winner/typecheck整体commit后、Export HIR提交前只展开为普通typed field projection与compiler-only raw `StructConstruct`，不经过任何源码constructor、initializer或default，也不产生`VariantTest`、`VariantPayloadProject`、`VariantConstruct`或compiler-generated throw。Export→LocalConcrete只穷尽具体化这些struct field ref；LocalConcrete拥有自己的checked concrete ref，且不包含CopyUpdate、字段字符串、Option短名、物理tag假设或待定expected type。MIR不得重新选择struct或字段。

M22同时封闭全部compiler-owned enum producer identity。Export HIR的variant constructor parameter owner、nominal constructor source及default source owner保存经`EnumDecl`检查的declaration-local variant ref；需要exact generic application的`VariantConstruct`与`HirConstantImage::EnumUnit`保存applied variant ref。LocalConcrete、MIR与LIR各自拥有只能由本stage enum definition store检查构造的variant/field ref，相邻lowering逐variant映射，不能平行携带enum id与裸ordinal。Export/Concrete/MIR `OptionCore`原子保存Some payload field ref与None variant ref，并在各stage自行证明exact-two、单一type argument与specialized payload type，module/enum definition不再保留另一套`option_variants` pair。MIR enum definition保存该单态实例的canonical type arguments；structured MIR与CFG MIR的`VariantConstruct`以及LIR `EnumWrap`直接携带stage-local checked variant ref，各自边界validator检查完整result enum type（含arguments）、payload arity与逐字段exact type，codegen在统一LIR validation门完成检查后才发射。`HirConstantImage`/`MirConstantImage`/`LirConstantImage`的unit enum leaf同样携带对应stage的checked variant ref；MIR与codegen module validation在发射前按global exact type递归验证aggregate leaf、ref owner及payloadless约束。

foreign callback同属该封闭producer集合。HIR core-contract验证必须一次性把`Reusable`/`OneShot` mode、`Registered`/`Active`/`Completed`/`Failed` state，以及`Option<Throwable>`的Some payload/None关系固化为exact checked variant/field refs；registration保存所选mode ref并按core中这两个ref比较，不能读取local ordinal。LocalConcrete、MIR与LIR family逐stage重建并原子保存mode/state/failure全部ref，bridge与operation只引用该family及其中已验证的身份。runtime ABI的mode/state整数是非nominal wire code：codegen只能通过family中角色到variant的封闭映射把mode ref编码为C值，或把state C值穷尽解码为对应LIR variant；未知state code必须进入fatal/trap路径，禁止把任意`i32`直接写成语言enum tag。failure结果只可使用同family验证的managed-reference `Option<Throwable>` payload/null关系，不得按nullable形状或字段零号重新猜测。

compiler-generated `CoroutineStep<R>`与frame `CoroutineSlot<T>` metadata分别保存完整的`Completed` payload field/`Suspended` variant和`Value` payload field/`Empty` variant typed identity；所有生成expression从metadata accessor取得ref。为迁移兼容保留的coroutine `EnumTag`/`EnumField` reader仍是表示相关内部读取，但其ordinal只能由上述typed metadata accessor导出，producer不能写死`0`/`1`，也不能据名称或默认顺序重建identity。这个兼容reader不改变`VariantPayloadProject`必须由同stable value/variant test真边支配的验证规则。

M22的range core合同包含四个独立nominal identity：`IntRange`、`UIntRange`、`LongRange`与`ULongRange`，后两者不得作为前两者的transparent alias。`Int8`/`Int16`/`Int`的range操作形成`IntRange`，`Long`形成`LongRange`；unsigned对应分别形成`UIntRange`与`ULongRange`。每个range/iterator计数器使用其element exact integer type，HIR不能在`Int`降为i32后仍把64位endpoint投影到`IntRange`。

此外归属 HIR 的语义工作：

- 字符串插值脱糖（spec 6.2）、`?.`/`?:`脱糖（spec 7.3）、完整operator/infix及只求值一次的place展开（spec 9.3）、`for`与struct copy update展开（spec 4.5、11.8）等。安全方法调用的实参/default sink必须只位于`Some`分支；若callee返回`Option<R>`不得展平为单层Option。复合赋值与自增/自减先产生包含typed read/write能力的临时place plan，再正规化为普通call/assignment；MIR不能接收source operator token、候选、copy-update字段名或待重放operand；
- 把普通/挂起函数类型正规化为全局唯一的类型化 `FunctionTypeId`，完整保留挂起性、参数与返回类型；每个 lambda、匿名函数、局部函数及 managed callable reference 都有独立的类型化实体 id。AST 的 `::name` / `receiver::name` 保持中性的函数声明引用表达式，不提前编码 managed/native 运行时类别；HIR 完成双向类型检查、局部函数可见性、重载目标选择与捕获分析，再由期望类型类别直接构造 managed callable reference 或 `FunctionAddress`，不能先构造前者再转换为后者。capture 列表只允许不可重新绑定的 binding，对外层词法局部 `var` 的任何引用直接诊断。captured value type保持 concrete layout并内联进入 closure environment，不生成 hidden box/shared cell，也不把 closure 擦除为 `Any`、裸函数符号或无类型代码指针；
- 所有成员方法/计算属性 getter 的 `this` 及扩展函数的 extension receiver，在 HIR 中都是隐含的、不可重新绑定的按值参数（spec 3.3），不得用指向调用方 binding 的 place 表示其语义。value receiver 复制完整值，ref receiver 复制 ref value；后者的 HIR 类型仍是完整 ref type，不降级成 raw pointer。捕获 `this` 时捕获的就是该参数值；对 value-type `this` 执行 `addressOf(this)` 则对该 method activation 内物化的私有副本取址；
- 函数值调用解析为独立的 callable-value call target；非函数值的任意表达式调用与property-like name call则选择唯一typed `operator invoke`并正规化为普通成员/extension call，两者不得混为“看名称像invoke”的分支或递归套用invoke convention。命名调用、函数声明引用表达式的 managed resolution 与 `FunPtr` native-address contextual resolution 是不同的决议入口。没有期望类型时只允许进入 managed 分支；只有 spec 13.10 允许的顶层 `@NoGC` 普通函数引用能在明确的 `FunPtr<F>` 期望类型下直接解析为 `FunctionAddress`，普通函数值之间的型变转换则保留为显式 typed coercion；
- 在 callable 签名、调用目标与 override / interface 实现关系中保留 `suspend` 标志；以显式、可嵌套的上下文状态检查挂起调用只出现在挂起函数或已登记的协程构建器中，不能把“当前无函数”当作默认允许。进入顶层属性、object/companion、实例属性、delegate、`init`、构造函数/构造委托及普通属性访问器等声明自身拥有的初始化/访问体时，必须压入带原因的 forbidden context；离开后恢复调用者上下文，所以 suspend caller 的显式构造实参仍可挂起。MIR 不为这些初始化入口或属性访问器生成 frame / continuation ABI；
- 完成FFI注解的目标与共存检查：`@Extern` function必须是top-level、non-generic、non-suspend且无body；member/local、generic或suspend extern无论`abi`取值为何都在HIR声明检查报编译错误，不能让多个concrete ABI共用一个native symbol。函数声明引用表达式的`FunPtr` contextual resolution同样拒绝挂起函数及一切只能产生managed closure的形态。每个合法extern声明在同一步产生target-independent `SourceNativeExternalContract`，非可选地保存解析后的symbol bytes、逻辑lib/default-namespace、function/data/TLS与mutability、C/Scoop ABI、normalized calling convention、alias展开后的完整source signature和definition origin；`HirOutput`以独立`DeclaredNativeExternalContractSet`保存当前Cone全集，public/re-export binding只携带指向原contract的typed ref。该检查必须发生在单态化、closure转换、协程变换及extern符号发射之前；
- FFI 类型检查必须按 ABI 分流：`classify_c_ffi_type` 只接受具有稳定 C 表示的 GC-free 类型；`classify_scoop_abi_type` 复用普通 Scoop typed ABI，并允许规范支持的 direct ref。`String` 等 ref出现在 C ABI 是诊断，出现在 Scoop ABI 不能被偷偷改写为 `PinnedPtr`、handle或 byte storage；两种 classifier及 `is_gc_free` 使用不同缓存/结果类型，不能合并成一个布尔值。extern global 只进入 C data ABI 分支，不能伪装成 Scoop ABI direct call；
- 每个fully concrete value type在HIR输出非可选`ZstStatus::{ZeroSized, NonZero}`；`ZeroSized`只可由`Unit`或元素/字段全部为ZST的ordinary tuple/struct产生，enum沿用现有非零representation，并同时证明`gc_free == true`。两个status都不允许下游从“字段为空”或`size`默认值重算。HIR即使知道结果为ZST也必须保留构造/call/getter/RHS/array-element求值；C classifier只接受`Unit`作为void result，拒绝其他ZST C参数/result/global、空或含ZST字段的`@CLayout`，并仅把`Ptr<Unit>`作为`void *`例外。generic `@CLayout`的字段若依赖binder，Export HIR必须保存typed `CLayoutFieldRequirement::CFieldSafeAndNonZst { signature_type: SignatureTypeRef, declaration_field_path }`；provider只立即拒绝无字段或不依赖binder且已失败的声明，consumer在每个fully concrete application替换后重放同一predicate并在concretization点诊断，不能只导出一个已丢失条件的`is_c_ffi_safe`布尔值；
- M13 的 managed callback registration是独立的类型化决议入口，不复用 `FunPtr` native-address resolution：HIR验证唯一`ForeignCallbackCore`，并仅在该core contract内部允许其deferred callback-signature参数`F`出现在`FunPtr<F>`字段/辅助签名；每个实际应用仍要求native函数类型显式、ordinary、非suspend且完全具体化，不形成通用`function` kind bound。`contextIndex: Long`和`Reusable`/`OneShot` mode必须为编译期常量，context index还必须非负且可索引该native signature，被选参数精确为`Ptr<Unit>`，全部native参数/返回值C-FFI-safe。删除context参数后得到的ordinary concrete `FunctionTypeId`是closure的真实expected type；core声明中的`callback: Any`不产生装箱。输出使用独立 `ForeignCallbackRegistrationId`，不能把 closure改写成 `FunPtr`、`Ptr<Unit>`或无类型 runtime call；
- `const val` 在 HIR 做常量表达式求值与依赖环检查；其值进入可供下游 Cone 使用的 HIR meta，不生成 runtime initializer。普通/挂起 call、构造、分配及普通属性读取均不能进入 const expression IR；唯一的 call 例外是通过 typed integer intrinsic registry 精确解析到 representation-level `NoGcIntegerOperation`、`ManagedIntegerDivRem` 或 integer conversion 的封闭整数常量运算。该入口按 exact callable identity 与 effect-specific target 区分，不按源码名称回退；其参数与结果保留 exact integer kind，常量 `div`/`rem` 除零在定义处诊断，其余结果与普通执行的 wrapping/边界语义相同；
- 执行target-aware组合式控制流分析，结果为`ControlOutcome::{Fallthrough, Return, Throw, Break(LoopId), Continue(LoopId)}`集合而非bool。sequence只向后传Fallthrough，分支取union，每个loop消费自己的Break/Continue，finally只有实际离开当前finally的新outcome才替换旧outcome；据此同时检查非Unit callable无Fallthrough、分支结果合并与后续可达性（spec第8章）。该HIR分析sum不改变M25异常表示：Throw在MIR仍沿typed unwind edge而不进入normal `PendingTransfer`；
- 按上述M16/M17、M18及M19契约完成候选独立的调用/构造/委托决议、property-like c-level分区、统一的默认template调用处实例化、vararg物化与源码求值顺序；为所有concrete expression及compiler-generated allocation/field-store/delegation edge完备地产生definition/evaluation origin，source-sensitive设施只通过普通expression lowering读取evaluation origin（spec 8.5、8.6、9.1、9.3）；
- 装箱/拆箱的插入（spec 4.4.4 的 O(1) 规则）；
- 以递归pattern matrix完成`when`穷尽性与稳定missing witness，并输出保持源码first-match/guard顺序的typed decision plan（spec第5章）。

### 2.3 MIR

只接收**本Cone**的`LocalConcreteHir`以及由HIR `CrossConeUseSet`选出的**上游Cone MIR meta**（见下）。其输入类型签名不得接受`ExportHir`或未筛选的`.slib`reader结果，负责：

- 为HIR已经生成的每个concrete function/type建立MIR实体并做name mangling；MIR不执行generic type substitution，不接受`TypeParam`，也不从template生成实例体；
- 每个MIR expression（包括desugared及MIR synthetic节点）直接携带非可选`MirTypeId`；创建节点与填入类型是同一操作。LIR只能消费该类型，不得按expected/context、operand、使用点或目标storage反向重建expression type；
- 原样传播`LocalConcreteHir`中每个concrete type及enum variant的非可选`gc_free` flag。MIR自身创建closure/frame/adapter等synthetic concrete type时，创建该实体的同一操作必须同时生成完整flag；不能先留下缺失值再由全模块扫描补齐。后续enum布局、NoGC边界与FFI classifier消费这些已定稿flag，不得分别重做一套“是否间接含ref”的递归判断；
- MIR同样原样传播非可选`ZstStatus`。ZST value node仍携带exact `MirTypeId`并保留其producer CFG/effect，只允许删除payload copy/load/store；ZST constructor、argument、assignment、MutableArray set RHS与spread的求值顺序不可因“没有结果bytes”消失。boxing仍是一次普通managed allocation；address-taken parameter/local/`this`产生独立place需求，而不是把所有ZST binding折成同一空值地址；
- 为每个call标注direct/virtual/interface typed target；target已经引用完整concrete callable/slot id，并以封闭local/external target ref携带完整signature与persistent origin，MIR不重新运行overload或generic inference，也不以symbol字符串代替缺失external callable；
- M19的class construction必须替换旧的flattened-constructor捷径：先对exact concrete class分配一次并建立initializing receiver root，再direct调用HIR指定的`Unit` initializer；base / `this` initializer以同一receiver direct调用，不分配、不改写最派生TypeDescriptor。primary/body property使用普通typed field store，base-before-derived、common sequence一次及secondary body内到外顺序已经由LocalConcrete结构给出，MIR不得递归拼接base argument/field或按constructor symbol重建。任一allocation/call后只使用relocated receiver；异常路径不产生construction result，失败对象由普通可达性回收；
- abstract class initializer仍生成普通hidden callable供derived使用，但不存在该class的allocation入口。struct secondary constructorlower为value-returning hidden callable，先调用typed delegated constructor得到完整值，执行body后按值返回。所有constructor initializer都是non-suspend，不进入coroutine transform；
- `super.method()`的target在输入中已经携带强制direct证明，MIR不能因callee属于open/override virtual family而再次选择vtable。初始化receiver相关非法调用/逃逸已在HIR拒绝，MIR不保留运行期“正在初始化”flag；
- M21 property read/write在输入中已经是concrete field/global operation或唯一accessor call；default/custom accessorlower为普通callable但保留getter/setter origin。delegate access已经是hidden storage read加普通operator target；MIR不读取source property name、accessor syntax或delegate role重新决议；
- interface default/property slot的实现目标已经唯一，MIR机械建立vtable/itable及typed adjust thunk。qualified `super<I>`始终保持direct target，不能再进入itable；
- object/companion与top-level runtime property生成独立initializer callable和`InitializationUnitId`。MIR把typed ensure展开为封闭init-enter结果及run/ready/failed/cycle CFG；cycle分支调用输入中已有的concrete exception constructor。singleton initializer按M19普通allocation/root/common sequence执行，成功边才写published root并完成unit；异常边必须在native catch仍active时把异常物化为managed `Throwable`，结束catch后才向coordinator发布rooted failure并从managed对象重新抛出。ordinary property/global访问携带ensure target，MIR不能假定“通常已在main前初始化”而删除gate；
- 方法/扩展调用必须先以 receiver value 初始化完整类型的隐含 receiver 参数；MIR 不得让方法体持有调用方 binding place。该规则对 value/ref receiver 相同，只是参数值的类型与 layout 不同。后续可以做 copy elision，但若 value receiver 的 `@InteriorMutable`、`addressOf(this)` 或其他 unsafe 操作可观察存储，则必须保留独立的 method-local storage；
- 为每个具体类型建立vtable/itable。本Cone类型实现上游exact interface application或继承上游exact class application时，表结构、TypeDescriptor符号与concrete target取自上游MIR meta；
- 把结构化HIR降为类型化CFG：调用从嵌套表达式中按源码求值顺序正规化出来，控制边与异常unwind边显式化，`try`/`catch`/`finally`的cleanup路径在MIR固定。M22的integer div/rem在这里使用输入中已有的typed `ArithmeticException` constructor展开除零throw，并把signed `MIN/-1`直接分流到规定常量；安全路径才保留primitive operation。shift count在这里按width mask，并在窄左operand上显式缩到LLVM要求的同宽标量。每个loop建立显式header/body/exit；while condition setup只存在于header，for header执行next/Option branch，普通回边与Continue均进入同一header，Break进入exit。不能继续把condition setup复制到body尾。LIR只负责机械映射这些边；
- M22把return专用cleanup泛化为normal abrupt-transfer routing。每个typed loop target同时保存break block、continue header和建立时cleanup depth；Return/Break/Continue只执行当前位置到目标之间被退出scope的cleanup suffix。普通Throw/Rethrow继续沿既有typed unwind、catch dispatch与cleanup edge传播，不能改写为词法goto或丢失M25 native record identity。每条正常离开active catch的edge恰好产生一次M25 EndCatch；跨finally的正常路径以`PendingTransfer::{Fallthrough, Return, Break, Continue}`保存动作及已进入cleanup cursor。finally内部完成的throw/catch或指向其内部loop的break/continue保留旧pending；只有实际离开当前finally的新动作才替换并从cursor之后继续，不能重入当前cleanup。目标仍在同一外层try/catch内时不得误执行其cleanup；
- **concrete HIR输入 → closure转换 → foreign callback adapter → 协程变换**：输入中的所有callable与type都已concrete。MIR把lambda、匿名函数和callable reference转为显式closure类、invoke body与按值capture字段，把函数类型型变转为typed adapter closure；局部函数的direct call仍可使用带显式不可变capture参数的lifted function，取得callable reference时才物化closure。普通concrete captured value按其layout内联，不能把captured value或closure environment统一擦除为`Any`/opaque environment。每种synthetic closure/adapter都有独立实体id、TypeDescriptor、完整`gc_free`属性与递归scan；
- closure 的首字段语义上是由编译器控制的 invoke entry，其余字段按确定顺序保存 capture。普通 closure invoke 使用 `(closure, source args...) -> R` 的 managed ABI；绑定 virtual/interface reference 的 invoke body 必须在调用时执行动态分派。已知不逃逸或立即调用的 closure 可以在后续优化中消除，但 MIR 的未优化基线必须先有完整、可扫描的结构；
- 对每个实际使用的 `ForeignCallbackRegistrationId`，MIR在closure conversion之后生成独立的 typed storage adapter：输入为closure ref、删除context后的C-FFI-safe args storage、result storage与exception root slot，内部按 concrete `FunctionTypeId` 调用closure。adapter在返回C前catch-all、物化managed异常并返回typed status；adapter、registration和M12静态NoGC callback bridge使用三类不同实体/id；前者是可分配、可GC、内部可抛但对C nounwind的managed入口，不能误标为NoGC；
- 对 closure 转换后的每个 concrete suspend callable，把 CFG 在挂起调用后切分为恢复状态，计算跨挂起点活跃的值并生成堆上 frame；每个挂起点生成与其结果类型精确匹配的 `Continuation<T>` 实际类型。frame、continuation adapter 与内部完成结果均有独立的类型化 id、TypeDescriptor 与递归引用扫描描述，不允许用 FQN 或 `Any` 作为实体/结果回退；
- suspend callable 的内部 ABI 是 `(source args..., Continuation<R>) -> CoroutineStep<R>`，其中编译器内部值 enum `CoroutineStep<R>` 只有 `Completed(R)` / `Suspended` 两个变体。立即完成走 `Completed`；返回 `Suspended` 后只能由传入的 continuation 恢复。该 ABI 只用于编译器生成的 Scoop 托管调用，不用于 extern 声明或 `FunPtr`，MIR 不生成 FFI wrapper。变换完成后 MIR output 不再含源码级 suspend callable 或 suspend call；
- extern call/global use保留指向`SourceNativeExternalContract`的typed ref及类型化ABI/effect：C ABI进入独立native bridge实体；Scoop ABI直接保存普通Scoop typed signature、`NativeBorrowed` protocol及direct-ref参数，不生成C storage bridge。两类实体id不能混用，也不能在MIR后续通过symbol string重新猜ABI；从上游选择的extern target必须把原contract加入`SelectedNativeExternalContractSet`，re-export或本地alias不得另造一份contract；
- HIR→MIR lowering把`HirIntegerConstant`、`HirCLayoutValue`/`HirCLayoutContract`、`HirConstantImage`及`HirStaticInitialState`穷尽转写为MIR crate自己拥有的`MirIntegerConstant`、`MirCLayoutValue`/`MirCLayoutContract`、`MirConstantImage`与`MirStaticInitialState`，并通过显式mapping把每个HIR exact type/id重映射为对应MIR typed id；这些HIR类型不能作为共享type alias泄漏进MIR。`MirCLayoutValue`保持同一封闭`Natural/A1/A2/A4/A8/A16`值域，`MirStaticInitialState`保持`ZeroedForRuntimeUnit | EncodedStaticValue { payload: MirConstantImage }`外层sum；lowering不得从constant bits、initializer是否存在或任意数值对齐重新分类；
- `LocalConcreteHir`交给MIR的intrinsic已经是封闭typed kind，compiler-generated异常已经通过完备`CompilerExceptionCore`给出类型与constructor callable；MIR不得按intrinsic/runtime symbol、class short name或FQN检索实体，也不得以panic/fallback补齐缺项；
- 恢复失败在对应恢复状态入口重新注入为`throw`，沿原调用点的unwind/cleanup边传播。挂起不是作用域退出，不能触发`finally`；跨挂起的pending fallthrough/return/break/continue动作必须作为有判别的frame字段保存，target使用编译器封闭的typed resume/loop target。只有按M10/M25先物化并结束native catch的异常，才进入额外`Throw(ManagedThrowable)` frame variant；不能把普通Throw/Rethrow塞入该variant，也不能保存native block address、源码label、未初始化槽或原生EH状态；
- M13 将编译器生成的safe continuation adapter和frame lifecycle改为类型化原子状态机：MIR显式表示claim/completing/latched/consumed及`running/suspended/completed`转换，使用独立的64位对齐internal atomic-state scalar与acq_rel CAS取得唯一完成/驱动权，并保留payload store-before-release、acquire-before-read关系；该scalar不是源码`Long`属性，不得把这些操作伪装成普通integer/字段读写或按函数名留给codegen猜测；
- 把HIR已经证明并类型化的`when` decision plan降为表示无关的`VariantTest`/literal test、`VariantPayloadProject`/field projection与跳转序列；保持arm/guard源码顺序，不重做exhaustiveness。只有带proof的Impossible edge可删除运行期fail，不能把最后arm擅自无条件化；具体tag/niche检查由LIR在取得layout后机械选择；
- MIR以本crate专有的`MirVariantRef`（或结构同构的封闭类型）保存stage-local enum id与已经对该定义检查过范围的variant index，并以`MirVariantFieldRef`封闭保存该variant ref与已经对同一payload检查过范围的field index；两者只能经需要enum definition的checked constructor取得，不能让expression调用点平行保存裸enum id/index/field，也不能按variant名称或FQN回退。`VariantTest { operand, variant }`的operand必须是该exact enum且result固定为canonical Boolean；`VariantPayloadProject { operand, field }`的result type由typed field ref所指field的exact `MirTypeId`唯一导出。MIR module validation还必须用稳定value identity与CFG支配关系证明projection位于对同一operand与同一variant所做test的true-edge支配区域，不能按表达式文本或block名称推断；MIR不读取tag值、niche、null编码、slot或offset；
- source `for`、struct copy update、bare variant、alias和literal constraint在进入MIR前已经消失；MIR只接收typed loop/control transfer、表示无关的variant/literal test与payload projection、普通aggregate构造/投影、exact integer constant/operation与唯一call/variant target；
- 输出 MIR type/function list，其中不再包含任何 generic 和 suspend（诊断信息除外）。

`docs/milestone23/DESIGN.md`第3.3节定义的persistent-identity mangler（本文及artifact compatibility record称为`persistent-v1`）落地前，M22使用的过渡compact mangler固定为独立的`compact-v2` schema。两者分别对应封闭`ManglingSchemaIdentity::CompactV2`与`ManglingSchemaIdentity::PersistentV1`，不是同一family中的数字版本。`compact-v2`的integer type code直接消费`IntegerKind`，不从source短名、alias拼写或物理LLVM type反推：

| `IntegerKind` | canonical owner | compact-v2 code |
| --- | --- | --- |
| `Signed, W8` | `Int8` | `I8` |
| `Signed, W16` | `Int16` | `I16` |
| `Signed, W32` | `Int` | `I32` |
| `Signed, W64` | `Long` | `I64` |
| `Unsigned, W8` | `UInt8` | `V8` |
| `Unsigned, W16` | `UInt16` | `V16` |
| `Unsigned, W32` | `UInt` | `V32` |
| `Unsigned, W64` | `ULong` | `V64` |

`compact-v1`的裸`I` / `V` code废止且不能当作任一宽度的fallback；transparent alias在进入mangler前已展开，因此`Int32` / `Int64` / `UInt32` / `UInt64`等拼写不另造code。compiler/runtime internal machine scalar不是source signature type，没有compact source type code；compiler-generated实体使用自身的typed role/identity symbol。`compact-v1`与`compact-v2` object、cache或artifact不兼容，driver必须读取manifest/cache key中的完整`ManglingSchemaIdentity`并在不相等时拒绝混用或重建，不能靠linker选择，也不能只比较末尾版本数字。M23的`persistent-v1`整体取代compact family；其symbol形态与linkage合同以`docs/milestone23/DESIGN.md`第3.3节为准。

**MIR meta**：每个Cone的MIR同时输出一份metadata，随`.slib`导出（见2.6），内容包括：persistent HIR source id到external callable/global/constructor/accessor的typed bridge；各单态化实例的symbol、specialization key、ODR group、generic来源与具体类型实参；各导出exact类型的vtable/itable schema、slot/adjust thunk、exact generic ancestry/conformance与TypeDescriptor symbol。类型布局不在其中——布局由LIR生产、经LIR meta导出（见2.4）。`ExportHir` template、`LocalConcreteHir` concrete实例与MIR实体使用不同typed id；跨层关系只能通过显式mapping表达，不能由name mangling反推。

### 2.4 LIR

接收**本 Cone** 的 MIR output、**上游 Cone 的 LIR meta**与driver从opaque target registry取得的typed `LirTargetProfile`投影（见下），负责：

- 为每个 type 生成布局信息（struct/enum/tuple 布局、typed intrinsic fixed/family representation、`@CLayout` 的 pack/align、`Option` 同构形态的 niche 编码——spec 7.4），并生成布局完备的递归引用扫描描述：普通引用偏移、同起点 sequence、自包含`Array { length_offset, first_element_offset, stride: NonZeroU64, element: NonEmptyRefScan }`。所有scan在输出/哈希前必须化为runtime spec 2.2的normal form，使用同一五项资源预算；LIR wire保存canonical tree而非待codegen排序/去重的任意children。`LirTargetProfile`非可选地提供data layout、ABI classifier、pointer widths、`maximum_managed_alignment`与`maximum_managed_object_size`；它的identity/fingerprint进入layout fingerprint与LIR/cache key，任何fixed object、box或array超过alignment上限都在本stage报错，codegen/allocator不能降级。intrinsic type按typed representation sum穷尽lower，不按FQN、空字段或使用它的operation识别；generic Array/MutableArray分支直接消费representation携带的concrete element type，并在函数lowering前为每个application建立唯一typed `ArrayTypeId`及完备的kind、element storage、stride/alignment、element scan和TypeDescriptor记录。含ref array的object scan固定写入length offset 16及实际对齐后的data offset，不能默认为24；所有数组指令显式携带该id，LIR/codegen不得扫描allocation、按layout/scan去重descriptor，或从operand/result type反推element/kind。variable allocation严格降低为String `alignUp(24 + len, 8)`、Inline array `alignUp(data_offset + count * stride, instance alignment)`或ZST array `data_offset`，所有算术checked且受object-size capability约束。M23 array入口不接收任意signed length：literal/assembly/vararg由非负component count checked求和；clone/互转则携带已验证source exact array/side-metadata witness并从`0..=INT64_MAX`的source size取得target count，再使用target refined TD分配。负值是invariant failure而不是编译器按名称构造异常。tagged enum直接消费MIR已定稿的逐variant `gc_free` flag：pure-value variant复用一个payload区，每个非GC-free variant分配独立连续slot；LIR不得重新递归判定“是否含ref”。完整值的构造先清零再写active payload，所有独占slot中的ref leaf可直接合并为固定偏移，LIR/runtime不得保留按tag分派的扫描路径；codegen必须把这些固定ref offset发射为LLVM aggregate中的AS1 pointer field，禁止用覆盖整个payload的byte array擦除managed provenance。需要上游布局的场景：本 Cone 的类继承上游类（继承字段的偏移）、跨 Cone 嵌套的值类型（上游 struct/enum/tuple 嵌入本地类型、作为数组元素、按值传参的 ABI）；
- layout输出是封闭`ValueStorageLayout::{ZeroSized { alignment: NonZeroPow2 }, NonZero { size: NonZeroU64, alignment: NonZeroPow2, scan }}`；ZST分支结构上只能携带`RefScan::None`。aggregate中的ZST field可以共享offset且不增加size。TypeDescriptor是独立的managed-instance契约：LIR内部必须以封闭`TypeInstanceShape::{FixedObject { ... }, BoxedValue { value: ValueStorageLayout, ... }, InlineBytes, InlineArray { element: ArrayElementStorage, ... }, AbstractRef}`表达五类instance，并由私有checked constructor保证offset/minimum/alignment与派生object scan一致；只有codegen/runtime ABI adapter可把它机械编码成M23的C product，reader必须验证后解码回该sum，不能让任意`instance_kind + inline_storage_kind + size/stride/scan`组合进入普通IR。allocation instruction只接受排除`AbstractRef`的`AllocatableTypeDescriptorRef::{FixedObject, BoxedValue, InlineBytes, InlineArray}`，各专用operation再要求对应refined variant；AbstractRef只可参与RTTI relation，runtime拒绝它只是防御而非普通控制流。exact ZST使用`BoxedValue { value: ZeroSized, nonzero minimum allocation }`，不能把value size 0直接写成可分配object size。boxing/unboxing operation以`BoxPayload::{ZeroSized, NonZero { source_place }}`和`UnboxResult::{ZeroSized, NonZero { destination_place }}`封闭，constructor验证它与exact value layout及`BoxedValueDescriptorRef`一致；ZST不需要伪payload pointer，non-ZST不携带第二份size/scan。`ArrayType`不保存可能为0的裸stride，而保存`ArrayElementStorage::{ZeroSized { alignment }, Inline { stride: NonZeroU64, alignment, scan }}`；只有`Inline`且scan非空时生成array scan node。ZST array allocation大小为对齐后的data offset，get/set/assembly/clone按logical count和整数index工作，clone仍分配新对象但不发`memcpy`，iterator不得从pointer差或end pointer判断完成；
- 每个materialized exact type必须从已验证`ExactTypeRecord`生成非可选`CanonicalExactTypeDiagnosticName`。printer严格使用M23设计3.1的ASCII tag/delimiter/percent-escape grammar：先展开transparent alias，nominal只取canonical origin coordinate/package/typed owner/name，application、tuple、ordinary/suspend function、raw pointer与native function pointer递归打印exact key；不得读取import/re-export alias、使用点qualifier、mangle或通用pretty-printer。producer/reader在分配或写出前以memoized checked subtree byte cost按每条展开路径重计共享type DAG，复用`.slib`单个text/bytes语义字段16 MiB上限，并在cycle、溢出或超限时拒绝；不得先指数展开再检查长度。该byte span进入TypeDescriptor的canonical LIR definition；descriptor `ObjectDefinition`直接依赖该semantic leaf，span relocation只能指向内容相同的typed diagnostic atom，所以descriptor fingerprint与ODR member/object fingerprint都覆盖name bytes。reader从exact key重算，codegen只能机械发射；
- 上述nominal source atom与compiler-generated atom是封闭两分支：closure/adapter/coroutine等generated nominal以M23设计3.1冻结的`GeneratedNominalRole + PersistentTypeId`打印，禁止使用source-name分支、arena ordinal、临时display name或mangle；
- Scoop ABI参数分类以`AbiArgument::{ElidedZst { exact_type }, Direct, Indirect}`表达，return convention至少区分`UnitVoid`、`ElidedZst { exact_type }`、`Direct`与`Indirect`；source signature、mangling、callable identity仍含所有exact type。callee仅在`addressOf`需要时为elided参数物化place token。raw `Ptr<ZST>`算术产生零byte displacement，load/store保持operand求值与unsafe validity contract但不访问payload；这些分支必须在typed LIR中显式，不能让codegen看到`stride == 0`、空LLVM aggregate或void后猜语义；
- 每个LIR `RegisteredCallableBody`都取得`PersistentCallableBodyId`并输出callable registration计划，即使该body没有safepoint。该集合精确覆盖当前Cone `code.o`中由LIR定义的普通managed/NoGC Scoop body、compiler-generated adapter/trampoline与root/init gateway；只有声明的native extern、runtime archive函数及由C compiler生成到`bridge.o`的storage bridge使用不同typed identity且不进入该集合。callable body canonical key是封闭`Strong { owner } | Odr { member } | RootGateway { root_cone, main_body_id } | InitializationStartupGateway { unit_id }`，v1 tag分别为1..4且字段按声明序编码；id为`SHA-256(ByteSpan("scoop-callable-body-v1") || canonical(key))`。main、initializer、ensure及两个no-throw gateway是不同body；每个safepoint site key非可选地引用其owner body id。root/init entry、failure-root、cell与普通init storage还必须使用owner绑定的refined LIR ref，不能退化为可互换的function pointer或static-storage ref；
- M22的source integer value使用`I8/I16/I32/I64`精确scalar type；canonical source owner的对应为`Int8`/`Int16`/`Int`/`Long` = I8/I16/I32/I64，`UInt8`/`UInt16`/`UInt`/`ULong`共享对应宽度但携带unsigned `IntegerKind`，固定宽`Int32`/`Int64`/`UInt32`/`UInt64`等alias在进入LIR前已展开。constant非可选地携带该type，不再由`IntConst`默认I32或I64。signedness随typed integer operation与FFI classifier携带，因为LLVM integer type本身不编码signedness。layout/constant global/boxing/array/enum/CLayout/callback/C bridge/mangling都消费同一`IntegerKind`；C ABI精确降为`int8_t`/`int16_t`/`int32_t`/`int64_t`与`uint8_t`/`uint16_t`/`uint32_t`/`uint64_t`。compiler/runtime内部enum tag、coroutine/init state、source span坐标、array/String count、layout size/offset、callback slot/generation、runtime type/safepoint id等均使用各自不同的internal typed scalar kind；即使物理上同为I32/I64/u32/u64/`size_t`，也不能伪装成源码`Int`/`UInt`/`Long`/`ULong`或互相混用；
- MIR output中尚未布局的结构化constant image只使用2.3节规定的`MirConstantImage`，其integer leaf是对2.2节`HirIntegerConstant`合同穷尽转写后由MIR crate拥有的`MirIntegerConstant`；它不存在通用`Zero`或裸`i64`分支，pointer null必须携带provenance，aggregate leaf递归携带MIR exact type/id，integer零、pointer null与aggregate全零分别以各自exact typed leaf表达。MIR→LIR lowering穷尽消费`MirConstantImage`，通过显式typed-id mapping与已完成layout产生`CanonicalAllocationExtentBytes + Sorted<StaticImmortalRelocation>`；成功的LIR output不再保存一份可与canonical bytes矛盾的结构化image。对应LIR storage使用本crate自有的`LirStaticInitialState::{ZeroedForRuntimeUnit, EncodedStaticValue { template, relocations }}`，而不是复用或type-alias HIR/MIR的sum。即使encoded image的bits全为零也不能改写为前一variant，unit/root descriptor与owner-bound storage ref也不能从零bits反推；
- integer arithmetic/Boolean compare、安全div/rem、已正规化shift与conversion以封闭typed operation进入LIR；`compareTo`必须是同时携带operand `IntegerKind`与固定I64（source `Long`）结果的独立variant（或等价结构），不能从lhs LLVM type构造`-1/0/1`。shift operation同样必须携带固定I64/source `Long` count契约，再由MIR按operand width显式normalize到同宽有效值。wrapping add/sub/mul/neg不携带`nsw`/`nuw`；MIR已保证div/rem路径不会触发LLVM signed overflow或除零，LIR/codegen不得重新发现这些语义边界。C type tree包含八个stdint classifier及正确的窄ABI extension，不能退回旧Int/UInt两项或按operand猜signedness；
- C bridge的storage shape与C spelling/classifier使用下列封闭type tree（或Rust中结构同构的sum）：

  ```text
  CDataPointerStorage = DirectRaw
                      | NullableEnum(NullableDataPointerEnumRef)
  CCodePointerStorage = DirectCode
                      | NullableEnum(NullableCodePointerEnumRef)
  CDataPointee = OpaqueVoid | Object(Box<CType>)
  CType = Integer(IntegerKind)
        | Boolean
        | DataPointer { storage: CDataPointerStorage,
                        pointee: CDataPointee }
        | FunctionPointer { storage: CCodePointerStorage,
                            signature: CFunctionType }
        | Struct(CStructRef)
  CFunctionType = { params: Vec<CType>, result: CReturnType }
  CReturnType = Void | Value(CType)
  LirCLayoutValue = Natural | A1 | A2 | A4 | A8 | A16
  LirCLayoutContract = { aligned: LirCLayoutValue,
                         packed: LirCLayoutValue }
  ```

  `CType`不包含`Unit`；只有function result可以构造`CReturnType::Void`，因此parameter、callback argument、extern global/TLS或struct field在结构上无法使用void。data pointer必须同时保存storage shape与完整pointee：只有`Ptr<Unit>`能由checked constructor建立`CDataPointee::OpaqueVoid`并拼写为`void *`，其他合法`Ptr<T>`使用`Object(Box<CType>)`保留递归C object type，且constructor必须拒绝Unit以外的ZST或任何没有portable C object representation的`T`。这个递归tree始终有限；C-layout struct以fully concrete、non-ZST的refined `CStructRef`叶引用，不内联展开其field tree。struct definition间的by-value dependency必须无环，pointer edge只依赖forward declaration，因此允许`struct Node`通过data pointer指回自身，却不能构造无限size的by-value递归struct。

  `DirectRaw`/`DirectCode`与两个`NullableEnum`分支由各自typed constructor建立；`NullableDataPointerEnumRef`与`NullableCodePointerEnumRef`是互不兼容的refined LIR ref，分别指向已经验证为携带对应Raw/Code payload、fully concrete且采用合法niche representation的enum，不能用通用`EnumDefId`或template id代替。前者还必须非可选地绑定该exact `CDataPointee`，后者非可选地绑定该exact `CFunctionType`；同一enum identity的绑定由LIR definition store exactly once建立，之后不能以另一pointee/signature重新取得ref。外层`CType`与ref内绑定不一致、当前module store没有该ref声明的同形绑定或同一enum被重复绑定为不同exact tree，均是malformed LIR并在任何renderer/classifier消费前拒绝。`CStructRef`同样只能由已经验证的fully concrete C-layout struct definition建立。每个`CType`都能total派生唯一storage `LirType`与唯一canonical C spelling/classifier；C extern/callback/native-global不得再平行保存可矛盾的`LirType` / `CType`参数或结果列表。C-layout struct的field以exact `CType`携带integer signedness、data pointee与pointer storage kind，ordinary Scoop struct的field以`LirType`携带；声明struct/layout必须用`Scoop { fields } | C { contract, fields }`等价的封闭representation或`PlainAbi::{Scoop, C(contract)}`区分，不得保留`fields: Vec<LirType> + Option<CLayout>`的矛盾状态。MIR→LIR lowering把`MirCLayoutValue`/`MirCLayoutContract`逐variant转写为LIR crate自有的`LirCLayoutValue`/`LirCLayoutContract`；两个stage不能共享type alias，后续IR也不携带任意`u8/u64`对齐值。C bridge按“header → C struct forward declaration → function-pointer typedef → 依赖拓扑序的C struct definition → extern/global/callback bridge”发射，不能用偶然的arena遍历顺序解决递归type tree的声明可见性；
- MIR的typed `VariantTest`/`VariantPayloadProject`由LIR消费已完成的concrete enum layout，穷尽降低为tagged discriminant或niche/null test与对应payload projection；for的Option分流与when不得各自实现一套按名称或默认tag的旁路。LIR以本crate专有、只能从enum definition经checked constructor取得的`LirVariantRef`封闭保存`EnumDefId + valid variant index`，并以`LirVariantFieldRef`封闭保存前者与valid field index；MIR→LIR只穷尽映射两个stage的typed ref，不重新做名称解析。`VariantTest`直接产生`I1`，tagged时比较discriminant，niche时按目标是unit还是payload variant选择null/non-null结果；`VariantPayloadProject`的result exact `LirType`来自同一variant-field ref，tagged时使用对应slot/field offset，niche payload时复用carrier表示。module validation必须同时检查operand exact enum、variant/field范围、result type、同operand/variant test true-edge基于稳定`Value` identity的支配关系以及managed/raw/code pointee provenance，不能按dump文本或block名称推断；
- M19 class allocation在进入任意initializer前必须使用exact concrete layout / TypeDescriptor清零完整payload、初始化header并登记object-start/size；initializing receiver立即进入普通managed root plan，尚未写入的managed leaf以全0非引用形态接受完整class `RefScan`。initializer、base/`this`调用与`super`方法使用独立typed managed direct target；LIR/codegen不得按`ctor` symbol、class name或receiver位置分类。每个初始化field store使用layout给出的typed offset和普通write-barrier插桩点，不能因对象“刚分配”而无证明省略；
- statepoint 的落地形态（M15修订）：LIR不直接包含LLVM intrinsic，但必须为每个managed poll/call/invoke输出完备typed root plan与非零`SafepointId`。普通poll/call的`StatepointLiveSet`逐项保存“post-site live source与可移动managed实参载体”的去重并集，以及其layout完成后的managed leaf path；LLVM 22.1会把direct AS1实参加入`gc-live`但不会递归发现aggregate leaf，所以上游必须同时表达两者。managed invoke另存normal/unwind后继liveness与实参载体的并集形成`ExceptionalRootSet`，且每项非可选地标出normal/unwind reload角色。Managed、NoGC、NativeSafe、NativeBorrowed使用不同typed target/callsite实体，不能用`CallEffect + Option<RootPlan>`表达可矛盾组合；这是对M14 `CallEffect`存储形态的替代，不允许旧enum与新callsite sum同时进入codegen。函数入口及每条循环回边由LIR lowering显式插入typed `ManagedPollSite`并在同一次backward liveness中定稿root plan；M22的普通body fallthrough与每条continue edge都必须经过对应header poll，可以共享header site但不能绕过。codegen不得发现CFG回边、补poll或重算live set，只把普通call/poll的ID写入`statepoint-id`并执行`rewrite-statepoints-for-gc`；
- 含引用aggregate不能依赖RS4GC递归发现：codegen按`StatepointLiveSet`在普通call前把每个managed leaf materialize为独立SSA value，让typed call实参消费同一materialized source，call后显式rebuild，使RS4GC生成并使用对应`gc.relocate`且不重复登记同一source leaf。managed invoke在invoke前把全部`ExceptionalRootSet` leaf spill到独立类型的显式compiler root frame，codegen直接发射actual-call operands完整但零`gc-live`的`gc.statepoint` invoke，normal/unwind按各自edge role reload并pop；原AS1 value不得跨invoke。不能让RS4GC改写带AS1实参的普通invoke，因为它会自动加入实参root并生成不可用的exceptional relocation；
- C ABI extern降为typed native-safe storage bridge call；Scoop ABI extern使用普通Scoop typed signature但降为typed native-borrowed call。两类调用都发布描述当前generated frame的typed caller-root frame，并把进入对应transition的architecture薄入口发射为带`SafepointId`但零`gc-live`的statepoint；薄入口捕获冻结segment的精确PC/SP/FP anchor。transition本身可能park并改写caller-root storage，因此入口返回后必须先从该storage重建所有含ref的direct/aggregate实参，实际native machine call才以这些新值作为普通nounwind调用；不得复用入口前求值的AS1 SSA实参。返回managed后当前frame只从已被collector更新的caller-root storage reload，不生成与其竞争的普通`gc.relocate`；外层managed frame由runtime从transition anchor按stack map更新。Scoop ABI root set还含全部direct-ref实参；含ref返回按return-convention sum携带调用前已清零并发布的result storage/scan。只有 C ABI bridge拥有 C type tree/`@CLayout` static-assert描述；Scoop ABI不得经过 byte storage bridge，也不得插入隐式 pin/unpin；
- LIR必须把managed ref、raw data pointer、code pointer与metadata pointer保留为不同pointer provenance，直到root liveness/codegen完成；不能因LLVM使用opaque `ptr`而提前合并。M15 codegen把Managed发射为`ptr addrspace(1)`，Raw/Code/Metadata发射为address space 0；不同kind只可经typed operation转换。普通LIR不得对managed value执行`PtrToInt`或address-space cast；只有TLAB object publication与card-index计算两个封闭codegen internal boundary携带kind-specific pointer-conversion metadata witness，post verifier拒绝缺失、错类或附着于其他instruction的witness。Scoop EH的`BeginCatch`作为独立typed operation调用runtime验证opaque unwind record，并直接产生已登记、稳定的AS1 exception payload ref，不通过address-space cast或暴露record layout。outbound C ABI及由语义保证不触碰managed storage的可能无界NoGC区间发布live caller-root leaves并进入native-safe；持有direct ref的Scoop ABI native调用即使声明`@NoGC`也进入native-borrowed。caller-root frame以可寻址value storage加递归scan descriptor表达含ref aggregate并spill live SSA temp；tagged enum使用spec 7.4的固定ref偏移，不读取tag。Scoop ABI含ref返回槽在push前清零并一并发布，native返回后在leave可能park之前写入、恢复managed后reload。未初始化slot/raw pointer不得混入；
- 每个LIR direct/indirect/runtime/extern call及invoke共享同一typed call模型。void/direct/indirect-result分别使用互不兼容的target/signature id家族；每个target实体原子地包含destination与layout完成后的完整signature/return convention，callsite variant再结构化地要求无result、必需out或必需result storage。effect/protocol使用互不兼容的Managed、NoGc、NativeSafe、NativeBorrowed target ref与callsite实体表达，并按前两条携带各自必需root plan；两类Native call均必带`SafepointId`和各自caller-root set，含ref return publication嵌入与return convention对齐的sum。local function在body lowering前由声明序registry一次性产生`ManagedLocalFunctionRef`或`NoGcLocalFunctionRef`；function-local dispatch store依据HIR/MIR提供的静态callee effect产生`ManagedDispatchSlotRef`或`NoGcDispatchSlotRef`。direct与dispatch destination只能携带对应ref，禁止先退化成无effect的`LocalFunctionId`/`DispatchSlotId`再用`from_view`、callee属性或symbol反向分类。不能使用`effect enum + Option<RootPlan>`、`Option<ReturnRoot>`、`out: Option<_>`或另放一份可能不一致的result scan。dispatch slot保存typed callable与对应target/signature；codegen不得根据symbol、实参、result temp或上下文推断/创建函数声明及root plan；
- compiler-owned static storage直接携带完整`RefScan`与封闭`LirStaticInitialState::{ZeroedForRuntimeUnit, EncodedStaticValue { template: CanonicalAllocationExtentBytes, relocations: Sorted<StaticImmortalRelocation> }}`，静态managed object携带immortal object记录；codegen据此发射typed storage/immortal descriptor table，不能按initializer、symbol或类型名决定是否登记。`CanonicalAllocationExtentBytes`只能由layout完成后的checked constructor建立，长度恰为`allocation_extent`，padding、ZST token byte及Recursive scan的全部8-byte pointer leaf为canonical zero；`StaticImmortalRelocation { pointer_offset, target: ImmortalObjectDescriptorRef }`按offset严格递增、无重复，offset对齐且命中logical payload内的Recursive leaf。GC-free storage以显式`RefScan::None`表示并仍有identity descriptor，只是不进入GC root集合；它不能携带relocation。storage descriptor同时携带logical `byte_size`与恰为`max(byte_size, 1)`的`allocation_extent`；零尺寸值强制`RefScan::None`，底层仍发射独立、address-significant、非common/非`unnamed_addr`的1-byte writable identity atom。除同一ODR member已经coalesce外，两个storage allocation range不得重叠；
- M21进一步把ordinary top-level/delegate storage、singleton published slot与initialization/root-entry failure slot全部作为typed compiler-owned static storage输出；显式`@Global`/`@ThreadLocal` raw storage仍是不同representation。需要initializer unit写入的property/delegate storage、published slot及两类failure slot只能构造`ZeroedForRuntimeUnit`，codegen把整个atom发射为canonical all-zero initializer；spec 9.1.3允许省略unit的值只能构造`EncodedStaticValue`，即使template全零也不改变variant，且不存在引用它的initialization-unit descriptor。Encoded atom的非pointer bytes逐byte等于template；每个非null Recursive leaf恰有一项actual object relocation和一项typed relocation record，二者target都是同一已登记immortal object start，其余leaf为null，禁止任意heap/interior ref。C record机械编码state tag、template span及relocation pointer/count；IR不得保留`Option<initializer>`或任意`GlobalInit::Storage.initializer`旁路。完整variant/template/typed target list进入`CanonicalLirDefinition`与RuntimeImage record key；`ObjectDefinitionPlan`覆盖writable atom、`StaticInitialTemplate { storage }` atom、非空时的`StaticInitialRelocationTable { storage }` atom及actual/record relocation，空sequence使用共享typed sentinel。ODR storage把这两个非空辅助atom列为同组member。object/link verifier从真实bytes/relocation table重建并逐项比较，variant、byte、offset或target不同必须在native coalesce前改变strong/ODR definition fingerprint并失败。每个init unit原子携带`PersistentInitializationUnitId`、仅诊断的coordinate/path、GC-free cell、generated initializer/ensure entry和对应owner-bound published/property/failure storage ref；schedule是封闭`EagerStartup { no_throw_gateway } | LazyAccess`，不能以可空gateway表示IR状态。codegen只在固定C ABI中把Lazy编码为zero fingerprint/null pointer，Eager编码为nonzero fingerprint/non-null executable pointer及已验证producer-table owner；v1没有per-Cone code range，不能要求runtime验证owner text区间。LIR发射static-storage/immortal/init-unit typed descriptor表，不能以nullable initializer symbol、命名约定或root表扫描反推unit kind；
- runtime registry按Rust类型隔离`ManagedEntryTargetRef`、`GeneratedNoGcLeafTargetRef`、`NativeBorrowedEntryTargetRef`、`RuntimeInternalId`与`ForeignCallbackEntryRef`。generated managed code通常只引用第一种并产生statepoint；唯一额外入口是LIR封闭`GeneratedRootFrameOp::{PushRecursiveRegion { stable_base, byte_extent, scan: NonEmptyRefScan }, PopRecursiveRegion}`引用的第二种。该leaf只链接/移除当前TLS root frame，保证NoGC、nounwind、有限时间、无allocation/park/handshake/callback，作为普通NoGc call留在同一managed segment且不产生statepoint；它不能承载任意runtime symbol或被源码/extern引用。private constructor与CFG verifier要求push支配随后受保护的managed entry、pop只匹配链顶同一frame，并在所有可返回/展开出口严格LIFO；boxing的push必须先于`scoop_rt_box_value` statepoint，pop在从可能更新的temp完成copy/返回后。Scoop ABI native header（`runtime/include/scoop_rt.h`）只导出native实现可用的对象布局、native root与native-borrowed入口；generated code使用的managed entry与上述NoGC leaf位于`runtime/src/generated_entries.h`，runtime internal implementation位于`runtime/src/managed_entries.h`。runtime内部只调用internal implementation；C trampoline只引用callback gateway。public header不得直接或间接暴露两个私有header，也不得按当前TLS mode或direct caller地址在一个symbol中猜入口类别；
- LIR中的pointer null必须携带`Managed`/`Raw`/`Code`/`Metadata` provenance；`Option<FunPtr>.None`的Code null、managed niche与metadata链尾不能合并成默认Raw null。裸`Ptr`/`FunPtr`在成功HIR中维持非零不变量：可证明的ULong零值`Ptr(0UL)`在HIR诊断，其他违反unsafe构造/算术前置条件或由声明为返回裸pointer的native函数交回null的程序行为未定义。layout、well-known String、TypeDescriptor parent/interface及dispatch entry全部通过typed id/ref连接，display/link symbol只用于最终发射，不作为semantic identity；
- foreign callback adapter作为managed entry保留GC strategy/statepoint，C trampoline、signature descriptor与删除context后的args/result storage描述作为独立反向bridge数据交给codegen。continuation原子状态降为显式`AtomicLoad/Store/CompareExchange`或等价LIR指令并携带内存序；
- 把 MIR 已显式化的 normal / unwind / cleanup CFG 机械映射为 landingpad + Scoop personality；`throw`、`BeginCatch`、`EndCatch`和rethrow分别接到typed runtime入口，`resume`继续映射为LLVM `resume` / `_Unwind_Resume`。M25 personality只接受codegen封闭生成的catch-all/cleanup LSDA形态，直接经Level I unwind context接口完成search/install，不委托C++或C personality。对suspend function的handler，进入可挂起的Scoop catch/finally代码前必须把exception payload物化为managed对象并结束native catch，任何native EH状态都不得跨挂起点；
- 输出 LIR type/function list，不再包含任何 Scoop 特有的内容，可以机械翻译成目标 IR 或其他格式。

**LIR meta**：每个Cone的LIR同时输出param-free导出exact类型的`ValueStorageLayout`、field offset/alignment、C/Scoop ABI分类、递归引用扫描、TypeDescriptor/parent/interface/callable typed ref，以及已materialize generic application的ODR layout record，随`.slib`导出（见2.6）。ZST status、`ElidedZst` ABI、`ArrayElementStorage`和static storage的`LirStaticInitialState`/typed immortal relocation sequence都是required wire variant并进入layout/definition fingerprint。LIR还把每条source extern contract经opaque target profile规范化为`NativeExternalContractRecord`：`PersistentNativeExternalSymbolId`由target profile与真实object linker-symbol bytes产生，contract fingerprint覆盖default/逻辑library requirement、kind/TLS/mutability、ABI、target calling convention，以及完整C storage/classifier或Scoop exact-type/physical ABI signature；完整record与origin进入LIR semantic fingerprint。param-free类型的layout/scan只在定义Cone计算一次；由上游generic template与下游local type组成的新application则在实际consumer Cone计算并进入同一specialization ODR group。下游引用已存在external exact实体时直接消费meta、不重算；结构上不能用可缺失字段把ZST、tagged enum、aggregate element、static初值或extern contract责任推迟给codegen。

LIR中String与Array的可变长度表示不因源码integer重命名而改变：两者都在object offset 16保存独立typed `u64` physical count，offset 24是InlineBytes的data start与InlineArray过对齐前的data boundary；Array的实data offset仍为`alignUp(24, element_alignment)`。源码Array size/index/iterator index全部是`Long`；实际size限于`0..=INT64_MAX`，index实参仍保留完整I64输入域并由bounds CFG拒绝负数或越界值。M24引入String length/index/slice表面时同样使用`Long`与该边界规则，M22只保留runtime的internal physical count。HIR/MIR只能用携带范围证明的checked conversion把非负I64 logical count转成LIR的internal u64 count。allocation、clone/互转、bounds与dynamic `RefScan::Array`都消费该internal count，但它不是源码`ULong`值且不能调用源码integer operation。

### 2.5 codegen

codegen只接收**本 Cone**的LIR output；object verifier/finalizer与packager消费其正式产物。M23共同约束如下：

root/init gateway在LIR中携带专用`NativeGatewayEntry`，强制入口poll使用本body的safepoint id并发布准确managed anchor，再执行调用/异常路径。runtime对每次C→gateway调用独立执行runtime spec 2.8的boundary/epoch enter-leave协议；`EntryPending`只证明尚无managed frame，不得把C PC当anchor。gateway须在返回GC-free status前发布failure root并EndCatch，编译器CFG verifier不能允许绕过入口poll或让异常跨C frame的出口。

packager的`scoop-code-v1`输入依次为有序final object member摘要、canonical native library requirements及完整`CanonicalNativeExternalContractSet`。contract set按`(symbol id, contract fingerprint)`排序并保存canonical key/payload，诊断origin不参与code fingerprint；仅contract改变、object bytes不变也必须使code/link key失效。完整编码与stage输入见M23设计4.6、5.3。

object verifier为每条undefined-symbol use产生封闭`UndefinedSymbolRequirement::{ScoopOwned(persistent_entity), SourceExtern(contract_id), RuntimeEntry(runtime_target), GeneratedBridge(bridge_id), TargetSupport(profile_capability)}`并交叉验证typed IR、extern contract、runtime ABI registry、C bridge plan或target compiler-support能力表。manifest保存完整index，consumer按同一target/runtime profile重验；不得用任意symbol前缀、C compiler来源或无类型allowlist豁免。bridge入口和后端memory/TLS/EH helper使用各自requirement及library依赖，只有`SourceExtern`映射源码contract；无分类、同一use多分类或无对应producer/capability均拒绝。公开runtime/target support symbol可与源码extern共用，但能力表必须提供完整canonical native ABI/library contract并与声明逐字段相等；compiler-private runtime、Scoop-owned和generated bridge symbol不允许源码extern占用。

codegen的具体职责为：

- 将 LIR output 机械翻译成目标 IR（本阶段为 LLVM IR），然后用 LLVM 编译成 `.o`；
- 对LIR `VariantTest`/`VariantPayloadProject`只按已经选定的tagged/niche representation发射LLVM比较或投影：test直接产生`i1`，projection复用既有typed aggregate/pointer安全物化机制并保持managed/raw/code address-space provenance。codegen在发射前防御性复核typed variant、field、result与pointee provenance，不按名称、FQN或使用场景补source语义分支，也不为这两个primitive增加runtime ABI；
- 只从driver给出的opaque typed target profile创建TargetMachine。M15的`DarwinAarch64` profile完整给出canonical triple/data layout、resolved CPU/features、relocation/code model、deployment/link配置、managed address space=1、LLVM 22.1 SelectionDAG/标准TargetMachine pipeline、stack-only statepoint root policy、stack-map v3 location capability、`frame-pointer=all`、disable-tail-calls、Mach-O object format、runtime platform bundle/source set、强制runtime C flags及最终linker args；M25再要求它非可选地给出Itanium/DWARF unwind model、Scoop LSDA subset、exception data register、unwind provider/link策略与artifact inspection能力。C bridge、runtime archive和最终链接都显式使用该profile的canonical target，关键flag不允许以`flag_if_supported`静默省略。除target registry外，codegen/driver不得match profile identity或散布host OS/arch条件，只读取完备capability；
- 为每个进入当前LIR layout/type closure或param-free exported LIR bridge的runtime-materialized `PersistentExactTypeId`生成`TypeDescriptor` registration（runtime spec 2.2：类型标识、封闭`FixedObject | BoxedValue | InlineBytes | InlineArray | AbstractRef` instance shape、`object_scan`与`inline_scan`、父类型与普通vtable/itable）；只存在于未替换Export HIR template/binder中的type不提前生成。`ValueStorageLayout`只描述未装箱value；`FixedObject`只描述class/closure，value exact type必须使用`BoxedValue`。其payload offset为`alignUp(16, value alignment)`、minimum为按instance alignment规范化的header+padding+payload，object scan由value-relative inline scan作checked offset translation；因此over-aligned value/ZST不能继续假设payload固定在`+16`。array TD的minimum object size/data offset与独立`ArrayElementStorage`写入不同字段，绝不能继续把一个`size`同时当instance size和element stride。interface/managed function/`Any`使用不可分配的`AbstractRef`；未来源码可命名的`Nothing`进入exact-type closure后也必须使用`AbstractRef`，该runtime契约不要求M22的jump statement提前物化`Nothing`类型或descriptor。`AbstractRef`不能靠`size == 0`与ZST混淆。每个generic application及tuple/raw/native pointer等结构exact type保留独立identity，后者用`StructuralType` ODR group跨Cone materialize；不按template、display string或相同layout合并。`Any`没有方法或固定槽，TypeDescriptor不含通用equals/hash/toString入口；
- ZST codegen只对真正需要place identity的参数/local/`this`发射满足alignment的1-byte stack token；同时存活的不同address-taken place不得共址。compiler-owned static及本地raw global遵守2.4/2.8同类token与linkage规则，C-boundary extern global/TLS仍由FFI classifier拒绝。普通ZST SSA value、field copy与return不发payload storage；box按`BoxedValue.inline_offset/minimum_size`分配，不能把ZST或普通over-aligned payload固定放在header后。`BoxPayload::ZeroSized`机械调用无payload参数的`scoop_rt_box_zst`；`NonZero`先把完整value写入跨调用地址稳定且按value alignment对齐的caller temp。若exact TD inline scan非空，codegen必须先以该scan push覆盖temp的NoGC native recursive-region root，再调用只接收该place的`scoop_rt_box_value`；push必须早于runtime managed-entry handshake/park，root贯穿handshake、allocation与copy，moving GC原地更新temp，返回后caller才按LIFO pop。runtime入口只验证该root已活跃，不能在入口内补登记；空scan分支可省略push/pop。codegen/root-plan verifier不得只保活拆出的旧AS1 SSA leaf、从push前副本复制或传入managed-object interior pointer。unbox同样分流到无destination的`scoop_rt_unbox_zst`或带destination的`scoop_rt_unbox_value`。四个入口的size/alignment/scan均只取自refined TD，旧`box(td,payload,size,scan)`不得继续发射。array codegen对`ZeroSized`分支只计算/保存logical count并执行bounds/evaluation，不做stride除法、pointer-progress、element GEP load/store、barrier、scan loop或零长`memcpy`；
- 发射M21 typed static-storage与initialization-unit descriptor表、generated initializer/ensure entry和singleton published/failure root。ensure/publish/fail走runtime spec 2.7的managed init-coordinator入口并使用普通statepoint/invoke root plan；codegen不执行initializer、不按名称选择object/property，也不为Option-omitted property生成late-init检查；
- M23为当前Cone发射由`ConeIdentity`派生、名称唯一的hidden strong `ScoopImageDescriptorV1`，内嵌canonical coordinate与`RuntimeImageFingerprint`，并按固定次序强引用static-storage/immortal/init/type-registration/safepoint-registration/callable-registration六张producer pointer表；普通external ref不进入producer表。每个`RegisteredCallableBody`均在同一`ProvisionalCodeObject(code.o)` finalization graph中发射callable record，保存body id、独立ObjectDefinition fingerprint与address-significant entry；`VerifiedBridgeObject(bridge.o)`不产生该record，也不需要在packager之后patch。不同body id禁止`unnamed_addr`、MergeFunctions/function alias folding，final-link profile禁用function ICF，只有同一已验证ODR callable member可coalesce。所有record严格镜像共享`scoop_runtime_metadata_v1.h`的magic/version/size/field order，codegen用LLVM `DataLayout`、C `_Static_assert`与object `offsetof` verifier锁定；不再导出固定`scoop_image_*`全局名，也不在每个Cone发射program descriptor或C `main`。root main和eager unit分别发射返回`Succeeded | Failed`、内部catch/物化并写registered failure root的C-callable no-throw gateway；gateway使用自己的body id，record中的gateway fingerprint必须镜像同一callable body fingerprint。C runtime不得直接调用可能展开的managed main/ensure；
- LIR非可选输出`CanonicalLirDefinition`、覆盖每个strong/ODR owner的`ObjectDefinitionPlan`及独立`DigestFinalizationPlan`。digest kind封闭为`SourceSignature | Layout | Scan | LirDefinition | ObjectSupport | ObjectDefinition | StackmapRecord | OdrDefinition | StrongRegistration | RuntimeImage`；前四种从canonical LIR metadata产生，其他种从受检object range或canonical runtime record产生。codegen发射所有graph-managed digest slot为零的`ProvisionalCodeObject`；`ObjectDefinitionPlan`只描述typed owner/role和primary/associated boundary，不保存digest offset，patch位置只能由`DigestFinalizationPlan`的typed `PatchSite`声明。独立object verifier解析真实Mach-O并输出`DefinitionAtomRange`、associated record与object leaf的`VerifiedObjectDefinitionIndex`；strong root/init gateway、param-free TypeDescriptor与strong registration不得绕过plan只相信LIR；
- finalizer严格按typed单向DAG工作。每个node只读取canonical source及`DigestInputRef`声明的直接input；object-backed hash的normalize视图只保留传递依赖slot，node自身及peer/descendant/无关slot归零，不能用“遍历时尚未计算”决定输入。允许边封闭：semantic/support leaf无依赖；stackmap依赖owner signature/support；object definition依赖semantic/support/associated stackmap；ODR依赖完整member的LIR/object/stackmap；strong registration依赖自己的LIR/layout/scan/source/object及适用stackmap；runtime image显式依赖每个canonical record key实际出现的definition/layout/scan/descriptor/gateway/callable/stackmap节点。callable registration的`body_definition_fingerprint`来自该body的ObjectDefinition，registration identity中的definition则仍来自StrongRegistration或OdrDefinition；root/eager gateway字段是同一body digest的镜像，不能另算第三个digest。交叉record只hash typed identity，除非其digest就是当前record字段。finalizer回填后重跑相同graph/object verifier并封装不可再改的`FinalizedCodeObject`；每个slot必须无relocation、固定32 bytes、恰有一个writer且初始为零。packager看到finalized `code.o`、verified `bridge.o`、canonical native library requirements及完整`CanonicalNativeExternalContractSet`后才以`scoop-code-v1`计算composite `CodeFingerprint`，随后计算member/manifest hash及`ArtifactFingerprint`；不能让codegen回写LIR meta或在pack后修改object；
- `DigestKind`的wire/hash tag按上述十种顺序固定为1..10；每个node id由`scoop-digest-node-id-v1`、kind及canonical persistent owner/role key产生，direct input按`(kind tag, node id)`严格排序去重并编码kind/id/digest。strong record必须按M23设计3.4的精确`scoop-strong-registration-v1`公式计算：canonical source是own-definition归零后的完整`RuntimeImageRecordKey` sum bytes，最外层sum tag唯一表示record kind；variant内registration不含kind，公式也不得另行前置第二份kind。它强制Strong linkage/零ODR id，只把自己的definition slot归零，保留其余已声明input digest与typed pointer role；不得以“domain-separated”占位、object地址或遍历顺序代替。RuntimeImage/Graph使用runtime spec 2.8的共同little-endian/tag/count encoder与跨Rust/C golden vectors；
- 展开登记表中归属 codegen 的 `@Intrinsic`（见 2.10）；
- 普通（非 suspend）extern 声明的符号发射与 calling convention 属性（spec 13.4）、`addressOf` 的 lvalue 语义（spec 13.10）；C ABI生成storage bridge source并由driver按同一target profile编译，Scoop ABI直接发射managed external call并接受direct ref。每个`code.o`/`bridge.o`中由源码extern目标产生的undefined relocation都必须由object/C-bridge verifier关联到唯一`NativeExternalContractRecord`，symbol bytes、调用/data kind与生成的ABI shape逐项一致；未使用声明仍保留record但可以没有relocation。codegen依赖HIR已排除suspend extern，不识别或发射hidden continuation FFI ABI。
- M13 按`(C signature, context index)`为实际导出的 managed callback生成/复用静态 C ABI trampoline：按真实C签名编组storage、排除context参数、携带signature descriptor调用runtime callback gateway；trampoline地址与runtime-owned opaque cookie配对使用，不生成每个closure实例的可执行代码。异常时trampoline按C返回类型产生全零值。foreign-thread attach/detach、generation cookie、异常handle及token retain/release由runtime实现，codegen只消费LIR中已定型的adapter/trampoline描述。多mutator下的card mark必须发射atomic monotonic store/RMW；
- M15在SSA construction/SROA之后运行`rewrite-statepoints-for-gc`，随后执行专用post-RS4GC verifier：普通managed call/poll的每个预期AS1 leaf必须有支配全部post-site use的`gc.relocate`，原root不得在可达post-site path继续使用（PHI按incoming edge判定）；每个managed函数入口及每条循环回边必须对应一个LIR poll/statepoint；invoke不得有exceptional relocate；NativeSafe/NativeBorrowed的唯一statepoint位于transition薄入口且`gc-live`/relocate必须为空，实际native call不得另有statepoint，当前frame跨transition只从显式root/result storage reload；managed aggregate不得未经拆叶live-through；AS1 derived pointer不得跨safepoint；Raw/Code/Metadata不得进入`gc-live`；kind-specific internal pointer conversion witness必须与instruction匹配。通过LLVM module verifier或存在stackmap section都不能替代这些检查；
- M25增加EH artifact verifier：每个含landingpad的function必须使用Scoop personality，LSDA只能含target profile声明的catch-all/cleanup encoding、call-site与action链，landing pad地址必须位于所属function。最终链接产物不得导入`__cxa_*`、gxx/gcc personality或C++ terminate，也不得加载libc++abi；Darwin/AArch64由默认`libSystem`解析允许的Level I `_Unwind_*`集合，linker args不含`-lc++abi`或显式`-lunwind`；
- LLVM 22.1 statepoint machine lowering是固定后端契约而不是artifact启发式：SelectionDAG保持`max-registers-for-gc-values=0`，标准TargetMachine machine pipeline在register allocation后运行`FixupStatepointCallerSaved`且保持`fixup-allow-gcptr-in-csr=false`。Scoop不向用户暴露或透传LLVM command-line option，不为statepoint设置`DeoptLiveIn`；若未来内部配置允许GC pointer进入vreg，仍必须由该post-RA pass把全部GC register operand改写为stack spill。codegen不能改用GlobalISel、自定义缺失该pass的machine pipeline或依赖hidden option的外部进程状态；
- 每个statepoint使用LIR的`SafepointId`设置callsite `statepoint-id`。object-level测试解析真实stack map并对照ID、前三个header location、零deopt输入、root count、location kind与return PC；只有GC base/derived pair必须是可写的8-byte `Indirect [SP/FP + checked offset]`，不能把deopt、普通stackmap location或live-out中的`Register`与GC root混为一谈。违反profile是compiler/toolchain invariant failure，object检查是防御性断言而不是编译到最后才做的能力协商；runtime以最终链接/ASLR relocation后的**原始return PC**作为查找主键，不做`PC-4`/nearest/range修正，也不以ID代替地址定位；

codegen **不需要任何上游 meta**：上游信息已逐层吸收进本Cone的LIR（布局经LIR meta、符号经MIR meta），对上游函数/TypeDescriptor的引用一律发射为external symbol，链接期解析。所有Scoop-owned linker-visible symbol都由kind-specific persistent entity/ODR id按版本化mangler产生；FQN、短名、arena序号和Cone-local overload discriminator不能进入跨Cone判等。链接层规则：

- **重复实例去重**：不同Cone可能各自单态化出同一个实例（如两个Cone都实例化上游的`foo<Int>`）。specialization封闭区分nominal、callable、delegated-property与按`PersistentExactTypeId`建立的structural-type group；由其产生的function、TypeDescriptor、vtable/itable、scan/layout constant、adapter/thunk、generic static/init storage、runtime registration及address-taken string/constant/按exact key重算的canonical diagnostic bytes必须按kind-specific member role完整列入同组，不得增加未在封闭specialization sum中的content-group旁路。Darwin/Mach-O为每个`OdrMemberId`发射同名`linkonce_odr`/`weak_odr` coalesced symbol，不依赖Mach-O不存在的原子COMDAT group；支持COMDAT的未来target可以把同组member放入COMDAT。两种策略都必须先比较完整member set与`OdrDefinitionFingerprint`，使逐member任意winner等价；仅ABI fingerprint相同不够；
- `OdrDefinitionFingerprint = SHA-256("scoop-odr-definition-v1" || group || 按member id排序的{role, LirDefinitionFingerprint, ordered object/stackmap leaf})`，其中`LirDefinitionFingerprint`从LIR meta保存的canonical typed payload以`scoop-lir-definition-v1`重算；最终ODR digest不得反向进入该payload或LIR own-layer。canonical relocation target使用封闭`NamedPersistentSymbol | OwningAtomOffset | AssociatedRecordOffset | SectionBasePair`，把LLVM正常生成的section-relative compact-unwind及`SUBTRACTOR(section base) + UNSIGNED(function)`EH pair映射为canonical section/record role与checked addend；raw section ordinal、temporary symbol和object-local index不得进入hash。`CurrentConeLir.ObjectDefinitionPlan`只保存typed owner/role及expected boundary/associated role；digest patch slot只在独立`DigestFinalizationPlan`，LIR meta不包含实际section range。Mach-O object必须设置`MH_SUBSECTIONS_VIA_SYMBOLS`并按plan发射stable start/end boundary；object verifier输出`VerifiedObjectDefinitionIndex`，manifest保存全部strong/ODR `DefinitionAtomRange`与可重放typed digest graph，且每个ODR record只引用自己的range子集，artifact reader再从canonical LIR payload、section/symbol/relocation table独立重算。不得因`nlist`缺少size就hash整个section或猜下一个symbol。padding规范为range末尾全零，AArch64/Mach-O relocation pair按一个有序typed relocation处理，unknown、跨range或越界addend失败；
- 任一function owner的associated record闭包同时覆盖`__gcc_except_tab` LSDA、`__eh_frame` FDE/CIE relation、`__compact_unwind`与LLVM stackmap function/callsite payload，并按typed strong/ODR owner与relocation归属；共享CIE等用canonical support fingerprint引用。safepoint registration的normalized fingerprint须与stackmap payload一致。group可typed-ref其他canonical group，但不能把自身产生的runtime identity漏在组外；object测试从真实Mach-O重算strong/ODR definition map/fingerprint并对primary atom和每类associated metadata做篡改测试，link后再验证TypeDescriptor与storage allocation range确实唯一；
- **符号可见性**：`internal`符号可本地化；被导出的generic body通过其既有typed dependency closure保留必要的可链接名字。导出default在HIR已被限制为只引用export/re-export实体，不得以强制导出内部符号补救非法可见性（spec 8.5、12.5）。

### 2.6 `.slib` 打包

M23的`.slib` v1是target-specific、bitwise reproducible的deterministic `ar` archive（spec 12.5），固定先包含`manifest.cbor`、`hir.meta.cbor`、`mir.meta.cbor`、`lir.meta.cbor`，再包含manifest列出的非空、有序`object_members`（规范生成器为`code.o`与可选`bridge.o`），最后可含`sources.cbor`诊断附件。archive timestamp/uid/gid/mode规范化；metadata使用RFC 8949 deterministic CBOR和显式整数field tag，不直接序列化当前Rust struct、enum discriminant、arena index或HashMap顺序。

codegen从LIR产生`code.o`和可选C bridge source；调用target C compiler把后者变成`bridge.o`是driver职责。两者都使用同一opaque target profile并分别先通过现有object/C ABI verifier，packager只接收验证后的`ObjectMembers`，不能假定一个Cone恰有一个object或在reader中临时编译源码。

manifest非可选地记录magic/container与三层wire schema version、language/runtime/identity/mangling ABI、canonical coordinate与`ConeIdentity`、kind、exact direct dependencies及三层semantic fingerprint、target/backend profile、每个非manifest member的kind/length/SHA-256、三层/code/runtime-image/artifact fingerprint、re-export/prelude摘要、ODR完整member/definition fingerprint、全部strong/ODR definition range及每组引用的range子集、runtime type/safepoint/callable body full-id映射、六类runtime registration摘要、完整typed `UndefinedSymbolRequirement` index、完整`NativeExternalContractRecord`表，以及target-tagged native **library** link requirements。两者是不同required字段：contract按`(symbol id, contract fingerprint)`排序并含canonical symbol key/payload/local origins；library requirement只携带逻辑库名、kind、顺序/分组与target条件。二者都不携带producer host绝对搜索路径，并与全部object member一起沿transitive link closure传播。`graph_fingerprint`只由最终program object保存。artifact fingerprint以domain tag、移除该字段后的canonical manifest bytes及有序非manifest member摘要计算，writer回填后重编码，reader按同一排除规则重算；各层派生digest严格遵守2.5的单向DAG与各自归零集合，manifest不得包含自身member hash或建立哈希自引用。

三层metadata分别为：`ExportHir`的public lookup、inheritance/slot、generic hidden support、interface dependency、source-interface/default与binding/re-export closure；MIR meta的exact executable/dispatch bridge；LIR meta的exact ABI/layout/scan/TypeDescriptor bridge。`LocalConcreteHir`是本Cone瞬时输出，绝不写入`.slib`。reader只能分别返回`ImportedHirSet`、`ImportedMirSet`与`ImportedLirSet`，不提供无类型metadata map或unchecked id cast。

reader按“受限archive读取 → manifest/hash/compatibility验证 → wire decode → 全图结构验证 → persistent typed id remap → semantic-world commit”执行；失败必须丢弃整个artifact。它验证member/count/size/nesting/depth上限、index与kind、identity重算、arity/owner/application、external origin、visibility用途/witness、跨层bridge、ODR、runtime type/safepoint id、source-relative span和target ABI；还重算每条native symbol id/contract fingerprint，验证record排序、origin、library requirement引用，以及每条object undefined-symbol use的typed requirement与`SourceExtern`到contract的一一关联。unknown required field/variant、重复key/member、indefinite CBOR、缺失section、损坏hash或同identity不同payload均为结构化错误，不得panic或以FQN/symbol补猜。

### 2.7 build driver

不属于编译器stage，但为必需组件。M23 driver读取`Cone.toml` v1与prebuilt manifest，解析只含exact version的静态graph；只对非core Cone注入trusted `scoop:scoop.core:0.1.0` direct dependency，core bootstrap root不依赖自身。driver验证coordinate/content唯一、library dependency、target/ABI/fingerprint、一组`group:name`只有一个version，并以SCC/typed edge给出cycle path。canonical order每轮只把“全部direct dependency均已输出”的剩余Cone放入ready set，再按coordinate byte order取最小；因此dependency必在dependent之前且不依赖edge存储方向。driver据此调度source discovery、pipeline、pack与最终link，不实现package registry下载、version range求解或动态loading。

生产Cone的源码集合是`src/**/*.scoop` regular file按normalized Cone-relative UTF-8 path排序；symlink逃逸、归一化重复、非UTF-8与空集合在parse前失败。各层用封闭`ConeOutputKind::{Library, Executable { local_entry }}`表示产物，不使用`Option<Entry>`拼装可矛盾状态。任何executable都不能成为dependency；build root为library时图中没有executable且无需entry，root为executable时图中恰有这一个executable，并必须有ordinary non-generic non-suspend `() -> Unit` top-level `main`，dependency中的同名函数不参与入口选择，且`Executable.local_entry`非可选。测试harness可用内部typed synthetic manifest迁移单文件fixture，但不能把它暴露成生产CLI或intrinsic authority旁路。

driver把当前Cone全部带`SourceIdentity`的parsed source、direct `ImportedHirSet`、transitive support map和trusted core capability交给HIR。HIR输出的`CrossConeUseSet`分为`LookupObservationSet`、`SelectedExternalSet`与其中typed-refined的`SelectedNativeExternalContractSet`：第一项记录查询过的binding/snapshot，包括空层、全部不适用候选、star surface与MSC rejected candidate；后两项才用于向MIR/LIR投影实际需要的上游meta与原始extern contract。当前Cone全部declared extern仍独立进入自身artifact，不因未选用而删除。三层semantic fingerprint都是Merkle fingerprint：除canonical own-layer payload外，还按typed support/re-export edge纳入对应origin artifact同层fingerprint。M23 v1的HIR compile key**强制纳入全部direct dependency HIR Merkle fingerprint**，直到完整observation闭包经测试证明可安全精确裁剪；MIR/LIR可消费selected set，或保守纳入全部direct dependency同层fingerprint。完整transitive code/native-library/extern-contract fingerprint与全部`OdrDefinitionFingerprint`进入link key；允许保守重编译，不允许因A的re-export bytes未变、负查询未记录、extern contract变化或winner未变而漏掉上游metadata变化。产物写入临时文件，完成round-trip验证后原子发布。

driver还拥有intrinsic声明的authority配置，默认且生产模式只能是`CoreOnly`。它把trusted sysroot locator中的reserved core `ConeIdentity`映射为不可由源码伪造的`IntrinsicAuthority::Core`；session-local `IntrinsicProviderId`只索引该映射，不使用路径、package或manifest自报身份。compiler unit/golden/fixture测试可通过内部`CompileOptions`传入`AllowListedForTesting { providers: Set<IntrinsicProviderId> }`：只对列出的provider跳过“必须来自sysroot”检查，不授权其依赖或其他输入，也不放宽registry name、target、shape/signature、annotation共存及provider唯一性。该配置不来自源码、环境变量、`Cone.toml`或稳定CLI，并且不写入HIR作为可影响语义的bool；intrinsic实体本身仍携带定义provider的typed relation，测试provider产出的`.slib`只能在消费方显式授权同一provider时加载，普通编译拒绝。

driver必须保留HIR warning直到最终结果：成功`CompileSuccess`携带typed warning列表；若后续codegen/link失败，则把warning附到已经确定失败的error report，而不能因`?`提前返回而丢失，也不能因warning非空改变成功/失败。CLI在成功编译时仍以零状态退出，并把warning渲染到stderr；`--emit`的stage dump和程序输出继续只使用各自既有stdout通道。fixture成功快照仍以AST/HIR/MIR/LIR开头，仅在warning非空时于LIR之后增加独立warning section，因此warning fixture保持成功编译并执行产物，空warning不会造成既有snapshot churn。

core由特殊bootstrap mode单独编译为library `.slib`，不依赖自身；普通Cone消费其typed public/prelude/well-known relation，绝不再把core source与用户AST合并。trusted Export HIR/LIR非可选输出`RuntimeCoreCapability::String { exact_type_id, layout_contract }`；linker要求program core binding与该relation相等，runtime再与共享header中的versioned String capability-kind常量`SCOOP_CORE_STRING_CAPABILITY_ID_V1`及24/8/None布局核对。该常量本身不编码runtime ABI；program Graph fingerprint另将`runtime_abi`作为独立输入。C runtime不得硬编码core source symbol或按同布局/名称选择类型。

M15起driver还负责把host triple规范化为opaque typed `TargetProfileId`，从唯一registry取得完备profile并选择匹配的runtime platform source set。当前只有`DarwinAarch64`；unsupported target在任何LLVM IR/object/runtime构建前诊断。driver同时验证编译器实际链接的LLVM为22.1，并选择封闭的LLVM 22.1 statepoint backend profile；这两项不是从host triple、`llvm-config`路径或已生成object反推。runtime profile由Mach-O image、Darwin thread/VM及AArch64 frame/anchor三个正交组件组成；Linux/AArch64或macOS/x86_64等新target复用已有维度，只补缺失组件。通用runtime不能用C预处理器选择多套平台行为，也不能用可空operation表示残缺platform bundle。新增target的允许改动面限定为registry映射、profile组合、缺失平台组件、build source set及artifact测试；通用codegen/collector通过依赖边界测试禁止导入具体profile，runtime单元测试使用fake platform bundle。

### 2.8 linker

最终linker按`ConeIdentity`去重resolved transitive closure，从每个已验证`.slib`提取`object_members`，并分别收集native library requirements与native symbol contracts。调用native linker前先按`PersistentNativeExternalSymbolId`合并完整contract closure：重算相同target/symbol key，要求default/逻辑library、function/data/TLS/mutability、C/Scoop ABI、calling convention及完整physical signature/storage逐字段相同；相同者去重，不同者以全部definition origin和首个差异字段诊断。随后才按target profile稳定合并library requirements；不能把“库名相同”当作symbol ABI一致，也不能让native linker任选冲突声明。link前还从真实object按已重算的atom/associated-record range比较同一`OdrGroupId`的完整member set与`OdrDefinitionFingerprint`；仅ABI fingerprint相同不构成可合并证明。任一member canonical definition、atom、LSDA/FDE/compact-unwind/stackmap payload或typed relocation不一致立即失败。

driver生成一个target object，以精确C声明`extern const ScoopProgramDescriptorV1 scoop_program_descriptor`唯一default-visible strong导出program record：magic/version/exact size、runtime/target ABI、排除自身计算的graph fingerprint、root image、no-throw typed entry descriptor、validated core bindings及canonical topological image pointer span全部非可选。每个image是hidden namespaced `ScoopImageDescriptorV1`，携带可重算canonical coordinate、runtime image fingerprint及按record-kind顺序排列的六类typed registration pointer table。program -> image -> table的强引用链必须保活普通descriptor record；M23 image只指静态链接logical Cone image，不含`dlopen`/卸载。

该pointer链**不能**保活无符号`__LLVM_STACKMAPS,__llvm_stackmaps`。Darwin/AArch64 M23 final-link profile必须拒绝`-dead_strip`，直到有经artifact测试证明的section retention/重写机制。Darwin linker把多个input stackmap section串接为多个完整v3 blob而不是合并header；final verifier/runtime parser从每个header的count/对齐计算精确长度、逐blob解析至section末尾，并把ODR重复site只在full site/owner/group/member、最终链接/ASLR relocation后的原始PC、location payload和normalized fingerprint全等时去重。只解析第一blob、让相同ID不同payload通过或假设一个native span只有一个header都不合法。

最终artifact verifier至少确认program/root entry唯一且ABI prefix/layout准确、expected image各一次且无意外image、coordinate/graph/runtime-image fingerprint可重算、六类registration producer ownership与ODR winner唯一、每个exact type到TypeDescriptor地址及反向地址到exact type一对一、`runtime_type_id == descriptor->type_id`、每个storage id及`[base, base + allocation_extent)`唯一（零尺寸payload也有1-byte token；同一ODR winner除外）、runtime type/SafepointId/body id到full key一对一、每个LIR `RegisteredCallableBody`与entry双向一一对应、全部stackmap blob通过canonical v3 schema覆盖去重全集、no-throw gateway body/fingerprint/failure-root关系完备、init cell/failure-root/owner-bound storage关系完备、每个undefined symbol有完备typed requirement且每个`SourceExtern`恰有一个全程序一致contract，以及target profile既有GC/EH/native依赖、禁function ICF和no-dead-strip门禁。只有全部通过才产生可运行executable。

### 2.9 虚/接口调用分派

- MIR 为每个具体类型建立 **vtable**（类层次分派）与 **itable**（接口分派）；标注 call kind 时，virtual / interface call 的 target 指向对应 table entry，direct call 指向具体函数符号。
- 表的内容由 MIR 定义，由 codegen 以数据形式发射，并从 `TypeDescriptor` 引用：TypeDescriptor 内嵌 vtable 指针与 itable 数组（见 runtime spec 2.2）。vtable从slot 0开始只包含真实virtual成员并允许为空；`Any`无成员，不预留equals/hash/toString前缀。`ToString`/`Hash`及interface operator equals走普通itable，open class equals走普通vtable。
- **装箱值类型的 this 调整**：值类型装箱后对象为 header + payload。vtable / itable 中对应装箱值类型的表项指向 MIR 生成的 **adjust thunk**；thunk 语义上从 payload 读取值，并用它初始化真正成员函数的按值 `this`。只有在不可观察的情况下，codegen 才可把它优化成对 payload 地址做 header 偏移后直接传递；需要取址或存在 interior mutability 时必须先复制到私有临时存储。
- **跨 Cone 的槽位识别**：初版 itable 采用（接口 TypeDescriptor 指针 → 方法表）的键值查找，调用点按接口 TypeDescriptor 地址查找，不需要跨 Cone 的全局槽位编号；槽位编号等优化留待后续。
- **generic exact application**：generic class/interface receiver始终携带参数完整的exact静态application。普通class继承或interface conformance只能到达声明中写出的exact base/interface application；调用继续使用该exact application对应的direct/vtable/itable路径，不存在按同template其他实参查找的view slot、bridge或wildcard table；
- **interface没有Self/object-safety分类**：`Self`不进入AST/HIR内建type kind；若源码使用该标识，只走普通名称解析。每个合法exact interface application都是普通reference type并拥有独立TypeDescriptor/itable identity，不输出`object_safe`、`requires_sized_self`或类似flag。interface方法签名只能引用普通类型及interface宿主参数；HIR在声明处拒绝方法自身的type parameter，因此每个合法method都有固定semantic slot/signature，经concrete、exact interface或bounded receiver均可调用，不能接受声明后再按receiver形态拒绝。未来开放method-level generic interface member前必须先定义跨Cone specialization/itable ABI；
- **其他泛型成员函数不参与虚分派**：class上的泛型成员必须为final，值类型成员本来即为final；open、abstract、override、覆盖既有virtual slot或充当interface实现都在HIR定义检查拒绝。exact owner调用标为direct concrete target，不是virtual slot。泛型宿主参数与方法自身参数使用export侧不同typed id空间，单态化键按“宿主参数在前、方法参数在后”携带完整实参，并生成不再含该参数空间的`ConcreteCallableId`；不能按名称或裸索引拼接两组参数，MIR也不能通过跳过table insertion来掩盖一个上游仍标为virtual的非法组合。
- **结构化表达式降级**：AST 在表达式位置直接表示 `if` / `when` / `try`。HIR lower 先确定所有正常分支的共同结果类型，再分配一个类型完备的隐藏结果 local，在每个可正常结束的分支尾写入该 local，并把原有 HIR 结构化语句追加到表达式的 desugaring sink；表达式本身成为该 local 的读取。结果为 `Unit` 时无需结果 local，但仍须保留分支尾表达式的求值。HIR 保留这些结构化控制语句；MIR lower 在内部完成结构化控制降级后，统一输出基本块 CFG，不新增内嵌 CFG 的表达式节点；LIR 只接收该 CFG。

### 2.10 intrinsic 的分阶段处理

不同的 intrinsic 在其**信息就绪的最早 stage** 展开，而不是集中在 codegen：

- 编译器内置一张 **intrinsic 登记表**：`name → （typed intrinsic id、合法annotation target、展开stage/representation owner、完整声明shape/signature约束）`。type target的shape还必须以非可选结构给出declaration kind、type-parameter arity/bound及fixed/generic-family representation；所有参数固定invariant，`Array<T>`/`MutableArray<T>`均要求一个无bound参数。target包括function/method及M14的compiler-represented struct/class。`@Intrinsic("name")`的字符串只存在于AST/HIR验证入口；name必须在表中且provider通过2.7的authority策略，否则HIR报编译错误。验证后的`ExportHir`/`LocalConcreteHir`保存封闭typed id/kind/application，不继续携带name字符串。
- **检查与展开分离**：无论在哪一阶段展开，类型检查、`value` / `ref` 约束检查、注解共存检查一律在HIR完成（与“所有源码语义错误在parser/HIR结束”一致）。
- 晚于HIR展开的intrinsic在`LocalConcreteHir`及后续IR中以“完全实例化的typed intrinsic/call target”形式存在；其type argument已全部确定，因此不构成generic节点，也不对MIR输入“不含generic”的不变量设例外。link symbol只能是该typed target的发射属性，不能反过来决定intrinsic kind或函数签名。
- 每个 intrinsic 恰好展开一次；其后的 stage 只看到普通 IR。

初始分类：

| 展开 stage | intrinsic | 理由 |
|---|---|---|
| HIR→LIR typed contract | intrinsic type declaration | HIR把源码nominal surface绑定到`IntrinsicTypeKind`；MIR原样传播typed kind，LIR按target穷尽生成representation/layout，不存在按名字展开的单一stage |
| HIR | `current_source_location` | 读取所在concrete expression通用的evaluation origin并折叠为`SourceLocation`值实例，其`line`/`column`使用`Long`（I64）；不读取default metadata，也没有default专用展开路径（spec 11.12） |
| HIR | `Ptr`的特殊nonzero-ULong构造、`FunPtr` native address、`ptr_to_ulong` / 其他`ptr_*` / `address_of` / `size_of` / `align_of`的源码使用 | 在core contract验证、候选决议和unsafe/lvalue/type/nonzero约束检查后正规化为类型化专用节点，不把intrinsic名称或公开representation传给下游 |
| HIR | `foreign_callback_register`及callback token retain/release/state/failure | 验证`ForeignCallbackCore`后直接生成类型化registration/token操作；registration以native函数类型和`Long`（I64）常量`contextIndex`派生managed closure expected type，不按`Any`普通调用lower |
| LIR | `size_of` / `align_of`、`ptr_load` / `ptr_store` / 指针算术、`address_of` | 依赖 2.4 的具体布局以及 address-taken local / parameter 的稳定存储；`size_of`/`align_of`将内部checked layout size物化为source `ULong`，pointer offset则从source `Long`精确降级，最终生成布局常量、带对齐的 raw memory 指令和局部地址 |
| codegen | typed integer算术/位运算及LIR raw pointer指令 | 按`IntegerKind`机械映射；wrapping不带overflow flag，division/shift只接收MIR已guard/normalize的typed operation；此时不再按intrinsic名称分派 |

### 2.11 IR输出完备性与typed identity

本节是所有stage的结构性约束，而不是debug assert约定。只要某项是下游正确转换所必需的信息，上游输出类型就必须使它非可选且类型化；禁止由下游根据context、arena内容、名称/符号、容器长度或默认值猜测/补齐。

- **expression type**：HIR与MIR的每个实际expression都直接携带非可选type id，包含Unit、synthetic、box/unbox、array/enum、closure/callback/coroutine节点。M22的Return/Throw/Break/Continue是jump statement，不是缺失type的expression；无正常完成路径由`ControlOutcome`封闭sum以及控制表达式分支的normal-completion状态表达，不得为jump伪造`Nothing` type id。未来加入源码可命名的`Nothing`与一般jump expression后，实际产生的每个`Nothing` expression仍必须携带非可选exact type id。generic expression只引用参数完整的exact application；LIR lowering不得提供`expr_ty`反推器或用expected type替代缺失类型；
- **function type canonical identity**：每个`FunctionTypeId`实体直接保存唯一`canonical_type: TypeId`，interning保证二者一一对应。Export与LocalConcrete使用各自id家族；消费者不得扫描type arena寻找反向映射或重新intern同形type；
- **compiler core identity**：只有编译器会脱离普通源码引用主动构造或调用的well-known实体，才在HIR一次验证并输出非可选typed结构。intrinsic type与function intrinsic分别使用封闭typed kind；provider authority只影响声明是否可进入HIR，不成为输出中的可选语义。M22把旧Int/UInt二字段结构替换为`IntegerTypeCore`对八个`IntegerKind`的total map，每个kind恰有一个canonical nominal owner；缺项、重复或kind/owner不符不能进入LocalConcrete。`CompilerExceptionCore`至少完整给出`Throwable`及编译器主动生成的`UnwrapException`、`ClassCastException`、`ArithmeticException`、`IndexOutOfBoundsException`、`IllegalStateException`类型/constructor；`IterationCore`完整给出Iterator template、next exact slot、Option template及Some/None variant。缺项不能进入MIR。`IllegalArgumentException`只由普通range core body调用，不因属于core就进入compiler结构。普通core能力不得因为由intrinsic type实现就建立专用旁路：`ToString`、`Hash`、全部普通operator、`print`/`println`及其实现都使用普通interface/member/extension、generic callable、conformance与call target实体；primitive/array/pointer operator可以在winner确定后按其typed intrinsic kind正规化，但候选能力只能来自源码声明。新增可由Scoop表达的intrinsic-type能力只修改core源码，不增加`FormattingCore`/`HashCore`/`EqualityCore`/`OperatorCore`之类的编译器结构；
- **call**：LIR call/invoke必须统一引用typed target。signature在layout完成后明确全部参数、calling convention及return convention；void/direct/indirect-result使用不同target/signature id家族和对应callsite variant，使缺失/多余out、storage或scan在类型上不可构造。M15进一步把Managed、NoGc、NativeSafe、NativeBorrowed target/callsite ref按Rust类型隔离：ManagedPoll/ManagedCall必带`SafepointId + StatepointLiveSet`，ManagedInvoke必带`SafepointId + ExceptionalRootSet`，NoGc无root plan，两类Native必带`SafepointId`、各自caller-root set及按return sum决定的result publication；不能保留`effect enum + Option<root plan>`让下游补齐。direct、runtime、extern及dispatch slot遵守同一规则；codegen只机械声明/调用，不按symbol或callsite推导签名/root；
- **pointer provenance**：所有LIR pointer value（包括null）都携带`Managed`/`Raw`/`Code`/`Metadata` kind；不同kind间转换必须是显式instruction。opaque LLVM `ptr`不构成在LIR中擦除kind的理由；
- **layout/metadata连接**：layout、well-known String layout、TypeDescriptor parent/interface、vtable/itable及callable全部使用typed id/ref。跨Cone实体用区分local/external的typed引用，link symbol只是external entity的发射属性；名称只用于显示/诊断；
- **persistent跨artifact identity**：每种可跨Cone引用的declaration、binding、slot、layout、static storage、immortal object、initialization unit、callable body与safepoint site分别使用不同persistent newtype。其值由domain-separated SHA-256对canonical definition/specialization key产生；key包含origin `ConeIdentity`、typed owner chain、kind及语言重复声明规则所需的normalized signature，但不含body、arena ordinal、host path或link symbol。concrete type统一使用封闭`ExactTypeKey::{Nominal, NominalApplication, Tuple, Function, RawPointer, NativeFunctionPointer}`产生`PersistentExactTypeId`；`Ptr`/`FunPtr`不能与普通nominal/managed function混用，TypeDescriptor直接登记exact type而不另建竞争identity。实际machine body统一以封闭`CallableBodyKey::{Strong, Odr, RootGateway, InitializationStartupGateway}`产生`PersistentCallableBodyId`；四个v1 tag固定为1..4，root gateway payload顺序固定为root Cone/main body，startup gateway只含unit。wire同时保存typed id与canonical key供reader重算，serialized table index只可作压缩索引；reader验证后再分配consumer-local arena id。同origin declaration经钻石路径复用一个world entity，tuple/function等结构exact type则只按其规范key intern，不按FQN/layout混并；
- **stable symbol/ODR identity**：所有Scoop-owned linker-visible实体由persistent entity/ODR id经唯一版本化mangler命名；runtime ABI与用户指定`@Extern` symbol除外。`runtime_type_id`与`SafepointId`从各自persistent full key以独立domain导出非零固定宽度值；driver允许同一full key的ODR重复经definition-fingerprint/address验证后去重，但不同full key映射到同一固定宽度值必须报碰撞，不同Cone各自从小整数开始编号不合法。generic/materialization specialization key以封闭sum区分nominal、callable、delegated-property与structural-type；前三者保存template origin及exact arguments，后者保存`PersistentExactTypeId`。generated role与typed owner path只产生group内`OdrMemberId`，整组member共享definition fingerprint，不能因role不同拆成多个group；
- **结构上排除非法组合**：read-only/mutable native global使用互斥access variant并分别携带完整bridge id；M21 logical property以stored/accessor-only/delegated/const/extern-raw外层sum配对合法storage，accessor-only再以Body/AbstractSlot封闭sum表示每个required accessor，read-only/read-write capability以不同variant携带必需target；object type/value/published root/init unit使用不同id；foreign callback有结果/无结果operation使用不同variant；caller root只能持有无法表示空扫描的`NonEmptyRefScan`；tagged enum field把type与offset放在同一`EnumFieldRepr`，不得使用平行Vec；call/function return不得使用`Void + result storage`一类可矛盾组合；class constructor以互斥sum区分`this` delegation与携带common initialization的terminal；call type argument使用`Explicit/Infer` sum且`_`只存在于source inference entry，成功IR只保存完整concrete argument，不能用nullable type或空argument Vec表示“以后再推断”。M22进一步要求integer constant与operation携带非可选kind、Break/Continue携带typed LoopId、loop target携带break/header/cleanup depth、pattern Impossible edge携带exhaustiveness proof、for/copy-update winner携带完整typed plan；不能以默认I32/I64、整数loop depth、可选variant或bool exhaustive替代这些关系。

未来加入GC-free release hook时，只有fully specialized concrete `ref` type可携带release policy；struct/enum/tuple等值类型必须在HIR拒绝，以免复制产生重复ownership。concrete type/LIR/TypeDescriptor的release policy必须使用完备sum：`None`与`GcFreeRelease`是互斥variant，后者非可选地携带已经验证为GC-free的payload layout、静态hook target及armed-state representation。HIR完成owner kind、non-suspend/non-throw/GC-free及payload闭包检查；LIR完成layout；collector只机械复制payload并提交非GC记录。任何stage都不能从方法名、注解缺失、字段形状或nullable function pointer反推release语义。该结构不得出现能够保存managed `this`或调用managed代码的finalizer variant。

typed id按实体类别隔离：type、function type、generic function、fully substituted generic request、concrete function、runtime function、extern declaration、dispatch slot、layout与TypeDescriptor不能共享裸整数或type alias。跨stage映射必须显式输出typed relation；FQN、short name和link symbol都不能作为id失败后的回退。
