# M31 性能记录

状态：2026-10-07 已完成。本报告评估生成程序的执行效率、实际机器代码与产物大小，以及 GC 工作量；构建耗时保留在原始 JSON，编译速度优化留待后续。

## 主要结果与回退

release 的实际机器代码节中位数相对 M30 分别减少 **27.6%（Darwin）、25.3%（GNU）、21.3%（musl）**。`aggregate` 的整体加速分别为 1.17×、1.16×、1.15×；小/中对象 `allocation` 分别为 **1.32×、1.98×、1.58×**。分配用例的 M31 full-only 已获得大部分改善，说明跨 line 分配等共同变化贡献较大，不能把全部收益归于 nursery。

`old-graph-large` 在 release/nursery 中追踪 196363 个对象，而同 profile 的 full-only 为 622233 个；full 次数从 10 降到 2，另外执行 8 次 minor。对固定 refill 压力，nursery 减少重复全图工作。相对 M30 的整体时间改善有限，GNU 这项反而慢约 6.0%；M30 的 full 阈值从 16 MiB committed 起步，与 M31 的 1 MiB nursery 不同。表中的同 refill 对照与 M30 整体比值承担不同问题。

高存活 `survivors` 的代价明确：NUC GNU 从 54.667 ms 增到 68.896 ms，**慢 26.0%**；musl 从 70.755 ms 增到 85.467 ms，**慢 20.8%**。Darwin 则从 66.839 ms 降到 61.533 ms。M31 该用例执行 6 次 minor 和 1 次 full，累计晋升 6815768 bytes，实际复制 6365264 bytes；同 revision 的 full-only 实际复制为 917672 bytes。第一次存活即晋升和更早触发收集在这种几乎全存活的年轻图上增加复制与收集工作，结果与这项机制代价一致。M30 没有同一统计入口，不推测它的实际收集次数或复制量。survivor 和自适应晋升仍属于后续设计。

密集旧数组写入也没有稳定的 nursery 优势：引用数组反复写脏，RN/RF 的追踪量几乎相同，RN 实际复制约 384.47 KiB，RF 约 0.56 KiB。少量脏边的旧图与这种写入模式有不同代价。`collections` 的部分小幅变化与样本波动重叠，不将其解释成稳定的优化收益。

`primitive` 在 Darwin/GNU 相对 M30 分别为 1.88×、1.09×，但 musl 从 130.007 ms 增到 151.564 ms，**慢 16.6%**。两种 collector 的收集次数都为零，因而这项回退不能归因于 nursery。对现有程序做独立的 CPU 0、三次 `perf stat` 诊断，得到：

| user-mode 硬件计数（每次均值） | M30 musl | M31 release musl |
| --- | --- | --- |
| retired instructions | 3070923303 | 2740898397 |
| cycles | 562540968 | 673593067 |
| branches | 676959064 | 626965066 |
| branch misses | 117303 | 117317 |

M31 指令减少约 10.7%，周期却增加约 19.7%，分支误预测基本不变。单独的 topdown 分组观测到 frontend-bound 约从 17.6% 升到 33.7%，backend-bound 约为 4.1% / 4.0%，memory-bound 约为 1.4% / 1.5%。这些诊断使用 PMU 分组和 multiplex scaling，独立于主表计时，百分比只用于定位瓶颈。

汇编显示 release 已消除无效局部运算，使用寄存器循环和乘法/移位实现常量余数；GNU 与 musl 的 release 循环指令序列相同，仅地址不同。每轮仍调用一次 safepoint，现有 safepoint 与 thread poll 的热路径指令在 M30/M31 之间也相同，仅链接地址不同。取指相关计数没有显示大幅 cache/TLB miss 增长。因此目前将回退定位到该热点循环/调用链的 CPU 前端供给效率，具体布局或带宽因素尚未分离，不能断言某一个 cache 冲突。保留正常 poll 与 GC 契约，后续可针对热点调用链和代码布局继续优化；本批不按单个基准调整函数摆放。原始计数、实际命令与诊断边界见 [诊断记录](M31-MUSL-PRIMITIVE-DIAGNOSTIC.json)。


## 测量口径

M31 生产代码为 `c3ea0d7d2`，M30 对照为 `6e62514da`；NUC 使用 `c4714125c` 源码快照，其生产代码与 `c3ea0d7d2` 相同。三个 target 分别在自己的实际运行环境内比较；历史 [M30 Darwin](M30-DARWIN.json)、[M30 GNU](M30-LINUX-GNU.json)、[M30 musl](M30-LINUX-MUSL.json) 六项报告保留，但本次比值使用同环境、同输入重新测量的八项 CONTROL 报告。[早期 OrbStack 测量](orbstack/README.md)单独保留，不与 NUC 时间合并或相除。

| target | 实际环境 |
| --- | --- |
| aarch64-apple-darwin | Apple M3 Ultra，32 核、512 GiB；macOS 27.0.1 / Darwin 27.0.0；Apple clang 21.0.0 |
| x86_64-unknown-linux-gnu | NUC12，Core i7-12700H，14 核/20 线程；原生 Linux 7.0.0-38；GCC 15.2.0、glibc 2.43 |
| x86_64-unknown-linux-musl | 同一 NUC 与 GCC；musl 1.2.5，通过 musl-gcc 构建 |

Darwin 外部 LLVM 为 22.1.8，NUC 为 22.1.2，Rust 均为 1.99.0。NUC 的内核 MemTotal 为 64025176 KiB。Linux 使用 `ssh nuc12`，源码快照、工具副本、工作目录与 `TMPDIR` 均位于 `~/repos/scoop/tmp/m31-final/`，两份源码使用独立 Cargo 产物目录。完整版本信息见 [环境记录](M31-PERFORMANCE-ENVIRONMENT.json)。

本任务的功能测试和其他编译结束后才开始计时。每个宿主的测量串行执行，每组依次处理八个程序；完整九组包含 600 次程序运行。每个 profile 对每个程序执行一次首次构建和一次相同参数的热构建，再运行五次；M31 每轮交替运行 nursery 和 full-only。运行结果保存中位数、最小值、最大值和全部五个样本，构建时间各为一次观测。运行计时包含进程启动、输出及退出；这些是短程序，启动、CPU 调频和宿主噪声的影响不能忽略。

NUC 的初次短程序测量存在组间与样本间波动，因此在全部构建结束后，用原有 executable 追加固定 CPU 的对照：测量进程及其子进程绑定原允许集合中的最小 CPU，即 CPU 0；没有重新编译，也没有选择最快的 CPU。按 GNU→musl、每个程序依次 M30→M31 debug→M31 release 运行，每种模式仍为五次，共追加 400 次执行。主表使用这组 `affinity_control` 数据与 Darwin 原有数据，共 600 个样本；原先 NUC 的 400 个未绑核样本仍在各 JSON 顶层保留。绑核不固定 CPU 频率，也不排除宿主调度和系统活动的影响。

Darwin 的多项程序首次运行明显慢于后续，而对应 GC 停顿与后续接近。每轮先运行 nursery，再运行 full-only，因此前者的第一轮承担首次启动；原始样本全部保留，中位数仍按五次计算，没有删除或重采慢样本。`primitive` 和 `aggregate` 的两种模式都没有发生收集，它们之间的计时差异不作为 nursery 收益；小幅变化也不能据这五次短进程测量断言稳定改善。

每组使用新的工作目录与空的 compiler/runtime 缓存。八个程序在该组内共享缓存，所以排在首位的 `aggregate` 首次构建包含 core/runtime，其他程序的首次构建只表示该 root 首次构建；没有清除操作系统文件缓存。产物大小记录实际 executable 与 root `.slib` 字节数。

DF→RF 观察 release 相对 debug 的额外编译优化，DF→DN 观察 nursery，DF→RN 观察两者组合。四组共同包含 M31 的 ABI、ODR 物理选择、跨 line 分配、Scoop 局部清理及必要 GC lowering，不能把 DF 称为完全未优化的 M30。M30→RN 的整体变化另外列出。

full-only 是在 M31 的 1 MiB refill 处请求 full 的诊断对照，其分配器和触发策略与 M30 不同。由此测得的 nursery 相对 full-only 收益，不等于整个 M31 相对 M30 的收益。

M31 debug 使用 SROA、mem2reg、SCCP 和不可达块清理；release 另使用 InstCombine 的 `no-verify-fixpoint`、early CSE、DSE、ADCE 及 machine O2。Scoop machine/generated-C 分别按 debug/release 使用 O0/O2，runtime 保持 O2。每个 profile 的两个 collector 使用同一个 executable；`SCOOP_GC_FULL_ONLY=1` 使相同 refill 请求执行 full，nursery 为 1 MiB、首次存活即晋升。脚本清除继承的 GC stress 开关，核对输出一致、full-only 的 minor 次数为零，以及停顿直方图与收集次数一致。

## GC 指标含义

`allocated_bytes` 为累计分配，`copied_bytes` 为 minor/full evacuation 实际执行 GC 搬迁的字节数；`promoted_bytes` 包含 pin block 与 full 中年轻对象的原地晋升，两者不能互相代替。`old_reference_slots` 只计 remembered-set 扫描，full-only 中为零不表示 full 不扫描旧图；完整图追踪另反映在 `traced_objects`。`committed_bytes` 是报告时的堆 committed accounting，不是进程 RSS，也不是峰值 RSS。

停顿从 mutator 已停稳之后计时，不包含等待其他线程停稳的时间。直方图上界依次为 10、50、100、500 微秒，1、5、10 毫秒和无上界；五次运行合并直方图后只能报告 p95 所在桶，不能据此给出精确分位数。

旧图用例的总时间和 GC 统计包含初始造图与两次显式 full。扩大八倍的旧图会增加这些工作，因此不能仅用总时间或累计旧槽数声称稳态 minor 与旧图大小无关。脏区范围的独立正确性证据见 [nursery_test.c](../../runtime/tests/nursery_test.c)：无脏边的 minor 不增加旧槽扫描，两张脏卡仅扫描 128 个引用槽。

M31 运行启用 `SCOOP_GC_STATS=1` 保存诊断，M30 没有同一统计入口。M30 报告不推测扫描量、复制量或停顿；整体耗时比较包含 M31 诊断输出的开销。

## 原始报告与复现

八个工作负载的输入和所有样本都保留。生成代码的效率由运行时间、实际机器代码节和 GC 工作量共同描述；不通过修改输入规模或删除慢样本改变对照结果。

| 环境 | M30 同环境对照 | M31 debug | M31 release |
| --- | --- | --- | --- |
| Darwin | [CONTROL](M30-DARWIN-CONTROL.json) | [DEBUG](M31-DARWIN-DEBUG.json) | [RELEASE](M31-DARWIN-RELEASE.json) |
| GNU | [CONTROL](M30-LINUX-GNU-CONTROL.json) | [DEBUG](M31-LINUX-GNU-DEBUG.json) | [RELEASE](M31-LINUX-GNU-RELEASE.json) |
| musl | [CONTROL](M30-LINUX-MUSL-CONTROL.json) | [DEBUG](M31-LINUX-MUSL-DEBUG.json) | [RELEASE](M31-LINUX-MUSL-RELEASE.json) |

报告保留实际 build records、输入源码路径、产物路径、所有运行样本、stdout 和逐次 GC JSON。代码节大小通过 `llvm-size --format=sysv --radix=10 <executable>` 读取 Darwin 的 `__text` 或 ELF 的 `.text`；读取前核对文件大小与对应运行报告一致。使用配套的 `scoop`、`scoopc`、`scoop-link`，例如：

```sh
mkdir -p tmp
export TMPDIR="$PWD/tmp"
cargo build --release -p scoop -p scoopc -p scoop-linker --bins
python3 tests/benchmarks/measure.py --tools target/release \
  --sysroot sysroot --runtime runtime --work tmp/m31-benchmark-debug \
  --revision c3ea0d7d2 --profile debug --runs 5 --gc-stats --compare-full
```

然后使用另一个新工作目录及 `--profile release`。Linux 追加 `--build-arg=--target`、对应 target、`--build-arg=--cc`、实际 C compiler，以及该 target 的 `--unwind-prefix`；具体参数保留在各 JSON 的 `build_args`。M30 使用同宿主上从 `6e62514da` 构建的三工具和对应 sysroot/runtime，省略 `--gc-stats --compare-full`，仍以五次运行和新工作目录测量。不要在计时期间运行其他本任务的测试或构建。
