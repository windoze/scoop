# 基于 profiling 数据的缺省 release 优化分析

日期：2026-11-14。分析基于 profiling / PGO 首版实现 `ae0e3c1ac4`，结合[已有验收数据](VALIDATION.md)、普通默认 release 的补充对照、MIR/LIR 和优化决策报告。本次只增加分析文档，没有修改优化实现或默认配置。

后续进展：已按讨论实现“默认内联先执行、PGO 只追加”，Long hash 的默认展开与性能已恢复，复测见 [VALIDATION.md](VALIDATION.md) 的追加内联记录。下文保留首版分析口径；精确上下文传播仍待实施，Boolean hash 另已观察到反馈标记阻止 poll 分块的结构差异。

**结论。** 当前最有依据的改进是消除“拼接结果只用于读取 `byteLength`”的临时字符串。默认 release 已正确内联算术热点中的小 helper；现有数据不支持全局放宽内联阈值、把默认系统库改为 full，或调整默认 GC 参数。PGO 的嵌套内联热度传播另有明确问题，应单独修复，不能将它的回归解释为普通 release 的缺陷。

**比较口径。** 前一轮为隔离 PGO 的效果，普通与反馈构建均使用 Release/full 系统库和 full 根产物。这里补建真正的默认 release：仅使用 `--release`，不传 `--export-ir` 或 `--system-library-root`，消费普通系统库。对照组复用前一轮无反馈的 Release/full binary；两组均无探针。

环境为 Apple M3 Ultra、Darwin AArch64、LLVM 22.1.8。每组预热一对，再执行五对 AB/BA 交错运行，完整标准输出逐次相等；计时期间没有本任务的构建或压缩。算术、调用点、字符串使用既有 native helper 的内核时间；GC 程序使用完整进程墙钟。沿用一个 GC worker、增量模式、nursery 上限 64 MiB，以保持比较条件一致，这些实验设置不是对产品默认值的建议。表中为中位数，未作统计显著性推断，也没有将本机性能结论外推到已完成正确性验收的其他五种目标。

| 程序及输入 | 默认 release / ms | Release/full / ms | full 相对变化 |
| --- | ---: | ---: | ---: |
| 调用点常用分支，1,000 万次 | 110.995 | 111.747 | +0.7% |
| 调用点另启稀疏分支，700 万次 | 79.074 | 80.037 | +1.2% |
| Long hash，5,000 万次 | 43.170 | 43.165 | 约 0% |
| Boolean hash，3,000 万次 | 18.651 | 18.640 | −0.1% |
| 字符串 chain，2,000 万次 | 191.650 | 191.124 | −0.3% |
| 字符串 shared，1,200 万次 | 214.671 | 214.975 | +0.1% |
| GC：262,144 节点链表，完整进程 | 11.382 | 11.543 | +1.4% |
| GC：1,100 次完整收集，完整进程 | 5.957 | 6.079 | +2.0% |

不同轮次的绝对时间有变化；只在同组交错运行中比较，不把本表与上一轮的绝对时间直接相减。这些小幅差异没有显示 full 的明确吞吐收益。前三类 binary 从约 816.9 KB 增至 850.2 KB，均增加 33,312 字节；其 `__text` 均增加 5,788 字节。GC 程序的文件大小只增加 32 字节，但 `__text` 增加 2,236 字节；文件大小受段布局影响，不能替代机器正文大小。

**优先改进：长度使用不应要求物化整个字符串。** [字符串基准](../../tests/benchmarks/scalars/concat.scoop)的 chain 每次计算 `(left + " / " + "[" + right + "]").byteLength`，shared 每次先计算 `part = left + right`，再读取 `(part + part).byteLength`。两者都没有把拼接对象交给程序其他部分。

两种 release 的热点决策相同。现有 [string-fusion](../../compiler/mir-lower/src/optimization/strings.rs) 已将 chain 的四次二元拼接合为一条 `StringConcat(left, " / [", right, "]")`；shared 因 `part` 被读取两次而保留两条 `StringConcat`。`String.byteLength` 的 getter 已内联，但最终 MIR/LIR 仍是先拼接、再读取新对象的长度。getter 内联会引入直线后继块，因此只匹配同一基本块内相邻指令会漏掉当前真实样例。

当前 [常量折叠](../../compiler/mir-lower/src/optimization/constants/strings.rs) 只能从已知 `Constant::String` 折叠 byte length，没有从动态 `StringConcat` 投影长度。[codegen](../../compiler/codegen/src/function/instruction/strings.rs) 在复制前本来就会取得所有片段的字节数并检查总长度，之后仍分配、写长度并复制内容。纯字面量的 constant 分支在本次最终 LIR 中也仍有单片段 `string_concat`，不能把“融合成一个字面量片段”视为已消除分配；该分支没有单独做本轮收益测量。

为估计收益空间，在仓库外复制同一程序，只将 chain 内核改为 `left.byteLength + 5L + right.byteLength`，shared 改为先计算两段长度之和、再加两次。输入仍为原程序的两个固定字符串，其他代码和默认构建参数保持相同。它是针对这些固定输入的手工收益探针，不是已实现的编译器优化，也没有证明任意输入下可以直接删除原有检查。

| 内核 | 默认 release / ms | 手工长度计算 / ms | 耗时下降 | 默认累计分配 / bytes | 长度计算累计分配 / bytes |
| --- | ---: | ---: | ---: | ---: | ---: |
| chain，2,000 万次 | 190.864 | 4.212 | 97.8% | 960,000,144 | 144 |
| shared，1,200 万次 | 215.217 | 2.531 | 98.8% | 1,344,000,144 | 144 |

这是另一组独立配对，其默认列与前表不同。chain 的五次默认内核在 189.780–191.883 ms，长度计算在 3.968–4.221 ms；shared 分别在 214.355–218.199 ms 与 2.517–2.552 ms。chain 输出均为 `440000000`，shared 均为 `408000000`；还核对了四个字符串分支在 0、1、1,000 次迭代下的输出。计时之外采集 GC stats，chain 的 minor 次数从 919 降到零，shared 从 1,288 降到零，144 字节来自内核外初始化等工作。

这两个微基准特意只消费长度，因而收益很大；不能据此承诺一般字符串应用也获得同样比例。它们证明了默认优化缺少一种有实际价值的变换。建议在现有 MIR 优化中按以下顺序实现：

1. 处理来源明确、创建点支配使用、结果只用于长度读取的 `StringConcat`，包括 getter 展开后的直线后继块。复用现有局部使用／别名和支配信息，将物化替换为受检查的长度计算；只读长度不需要拷贝字符串内容。
2. 覆盖纯字面量片段和稳定局部复制，再处理 shared 这类重复片段：保留 `part` 对应的长度值，避免为了读取两次长度创建两个对象。不能仅因语法上重复出现就重求原输入表达式。
3. 先修订相应实现规范，再实现变换及必要测试。保留原片段求值次序、异常前副作用、每一级拼接的长度上限检查；控制流、别名或其他使用不满足现有消除条件时保留分配。对于实际返回、传递或消费字符串内容的情况，继续沿用现有融合。

验收重点应是最终 MIR/LIR 无对应临时分配、固定负载的分配和吞吐变化，以及零迭代、UTF-8 字节长度、共享输入、异常顺序、长度边界和逃逸结果的正确性。无需为这项局部变换增加通用框架，也不需要调整全局内联分数来触发它。

**保持当前默认内联尺度。** [调用点样例](../../tests/benchmarks/profiling/call-sites.scoop)的两处 `mix` 在默认和 full 构建中均使用静态循环热度 4，收益分数 96，展开代价 135，因此保留调用。已有 profiling 数据区分出 500 万次与零次调用；PGO 将热位置内联，机器正文增加 172 字节，但训练分支和未训练稀疏分支均未显示明确净加速。该内核由整数乘加与移位的依赖链组成，减少一个调用不一定缩短主要执行路径。当前证据不支持提高所有循环的热度或降低全局内联门槛。

[算术基准](../../tests/benchmarks/scalars/operations.scoop)在真正默认 release 中已经将 `Long.hash → coreLongHash → coreULongHash` 三层全部内联，最后一层的收益分数 96 高于代价 30；Boolean hash 的相关小函数也已内联。默认与 full 的决策及吞吐接近，调用点和 Long hash 程序均只分配 80 字节且无 GC。因此，这些热点不需要先扩大系统库模板范围。

现有 [内联估价](../../compiler/mir-lower/src/optimization/inline/policy/score.rs) 已区分调用、ABI、常量简化和对象字段投影收益。后续可继续以实际暴露出的消除机会改进局部估价；本次没有足够数据重新校准通用的调用收益或代码增长系数。

**PGO 热度传播应单独修复。** 上一轮 Long hash 的约 63% 回归有具体原因：外层热调用展开后，内层仍按原 callee 的 `5,000,000 / 5,000,000` 归一化为 1，收益分数降至 24，低于代价 30，最终 helper 没有内联。普通 release 沿调用点循环上下文继续使用 4，反而作出了更合适的决定。

建议将消费方外层调用频率与 callee 内部的局部相对频率组合，使内联后位置保持其真实上下文，再使用既有热度截断和增长策略；缺失或零入口数据继续静态回退，已执行函数中的真实零次调用仍表示冷位置。不能用“所有反馈至少等于静态循环热度”掩盖问题，否则会丢失已经采到的冷路径信息。先用同一组已训练／未训练输入确认决策和吞吐，再评价修复效果；本次未实现此修复，不预报加速幅度。此前 Boolean hash 的反馈时间变化尚未充分归因，也不作为修改默认策略的依据。

**暂不调整默认 GC 参数或全面启用 full。** 在独立 stats 运行中，默认 chain 的累计 GC pause 为 1.262 ms，shared 为 2.397 ms；相对于约 191／215 ms 的内核，直接暂停只占很小部分。GC 还有分配和屏障等成本，这些数字不是全部 GC 开销；但结合长度探针，可优先消除分配和复制，缺少先调 nursery 或 worker 数的证据。

链表程序主动执行完整收集和增量推进，fill 主动执行 1,100 次完整收集，主要用于验证记录与 GC 正确性。它们不能代表普通应用的存活率或收集触发分布，不能据此改变正常触发策略。

full 仍适合作为 PGO 独立组件的模板覆盖策略；普通默认导出已经覆盖本次算术和字符串热点。完整组件约 1.22 GB 下载、1.96 GB 安装，包含两套全量系统库及配套资源，这与单独改变一个库的导出模式不是同一种成本。若后续应用出现“热调用因没有模板无法优化”，再针对具体库和函数评估默认剪裁；本次不建议全部系统库默认 full。

**下一轮顺序与证据留存。** 先做字符串长度投影及其必要组合测试，再修复 PGO 内联上下文热度；保持普通 release 的全局内联尺度、默认 IR 导出策略和 GC 参数。之后用真正会消费拼接内容的程序、实际容器／调用链及未参与训练的输入验证收益，避免只优化这些微基准的观测方式。
