# Profiling / PGO 验收与性能边界

日期：2026-11-14。实现与设计见 [DESIGN.md](DESIGN.md)，分批提交和针对性测试见 [PROGRESS.md](PROGRESS.md)。原始进程日志、计数、逐次测量 JSON 和发行归档均保存在仓库外。

基于这些数据对普通默认 release 的补充对照、具体优化机会及建议顺序见 [RELEASE-ANALYSIS.md](RELEASE-ANALYSIS.md)。

下述六目标闭环及首版性能数据对应首版实现；本次追加内联的本机复验与新性能结果见文末“保留默认内联、PGO 只追加”。

**原生闭环。** 使用真实目标 compiler-rt、普通与 profiling runtime、两套 full core/std，执行 GC 时间线和 profiling/PGO 正式 fixture。每个完成目标覆盖 2 项、13 次外部进程调用，PGO 子流程另含 16 次命令操作；没有把跨目标对象生成当作原生运行。

| 原生目标 | LLVM | 结果 |
| --- | --- | --- |
| Darwin AArch64 | 22.1.8 | 通过 |
| Linux x86-64 GNU | 22.1.2；compiler-rt 源码 22.1.8 | 通过 |
| Linux x86-64 musl | 22.1.2；compiler-rt 源码 22.1.8 | 通过 |
| Windows x86-64 MSVC-UCRT | 22.1.8 | 通过 |
| Windows x86-64 MinGW-UCRT | 22.1.8 | 通过 |
| Windows x86-64 MinGW-MSVCRT | 22.1.8 | 通过 |

确定计数包括两次 main、6 次 choose、8 次 worker、8,004 次 leaf 和未执行递归函数的零记录。测试同时覆盖多线程、中文／空格／百分号路径、正常与非零退出、退出写出失败、合并、外部采集、换 cwd 后参数复用、workspace 默认成员改变、输入更新和缓存命中、覆盖诊断、损坏或缺失数据、失败保留原输出，以及反馈程序无探针。跨 Cone 的 off/default/full 语义组合另在 Darwin、GNU、MinGW-UCRT 验证。

GC 定向程序保留 262,144 节点链表，执行完整收集、三次真实增量推进和完整收集，核对 cycle/slice 身份、重启、时间边界、嵌套阶段和任务／字节／CPU 汇总。另一个进程执行 1,100 次完整收集：固定缓冲保留 8,192 个事件，报告 608 个 dropped，累计 GC 指标仍完整。

Windows 短 GC 任务的 CPU 差值可能因 `GetThreadTimes` 粒度为零；验收严格检查逐片与累计值相等，不要求短任务必然得到正数。Python 探测脚本固定输出 LF 状态行，业务程序仍按原始字节比较标准流与退出码。

**独立组件。** Darwin 组件实际包含两套各 44 个系统 Cone 的 full `.slib`、44 份训练映射和四种 profiling runtime，压缩包 1,220,497,376 字节，安装后 profiling 目录 1,959,654,927 字节。使用真实 host 工具、core/std 基础库与完整 profiling 组件进行本地 HTTP 安装验证：基础安装不下载该组件，缺少组件时训练明确失败；独立安装后 instrument/optimize 成功；卸载后普通 release 构建与已生成程序仍可运行；再次安装复用下载缓存。该检查验证完整 profiling 组件，没有重复构建和打包未改的全部普通系统库。

**性能方法。** 本机 Apple M3 Ultra，Darwin AArch64，LLVM 22.1.8；使用 release 优化。基准开始前结束本任务的构建与压缩。每组先预热一次，再进行五对 AB/BA 交错运行，逐次核对完整标准输出。固定一个 GC worker、开启增量模式，nursery 上限 64 MiB。表中报告中位数，未做统计显著性推断。

普通 release 和 PGO release 都使用同一组 Release/full 系统库及 full 根产物，避免将模板范围变化计入 PGO 收益。训练程序使用 Profiling/full 系统库，保留默认行表。另用同一份普通 release `.slib` 只更换 profiling runtime，测量 runtime 记录与退出写出的整体开销；其 LLVM 计数段为空，不把它当作完整训练程序。

训练输入为调用点样例的常用分支 500 万次、Long hash 500 万次、字符串 chain 200 万次，以及 GC 链表。验证增加迭代数，并额外运行未训练的稀疏调用点、Boolean hash、字符串 shared 和 1,100 次完整 GC。算术、调用点与字符串的时间来自既有 native helper，仅包围内核；GC 行报告完整进程墙钟，包括退出。所有比较的标准输出均一致。

| 负载及验证输入 | 普通 release / ms | PGO release / ms | PGO 变化 | Profiling / 配对 release |
| --- | ---: | ---: | ---: | ---: |
| 调用点：常用分支，1,000 万次 | 99.623 | 100.050 | +0.4% | 1.98 倍 |
| 调用点：另启稀疏分支，700 万次 | 70.710 | 69.770 | −1.3% | 1.95 倍 |
| Long hash，5,000 万次 | 38.206 | 62.180 | +62.7% | 26.72 倍 |
| Boolean hash，3,000 万次 | 18.374 | 21.016 | +14.4% | 55.22 倍 |
| 字符串 chain，2,000 万次 | 183.280 | 180.286 | −1.6% | 2.65 倍 |
| 字符串 shared，1,200 万次 | 191.393 | 190.113 | −0.7% | 1.40 倍 |

Profiling 比例使用它自己那一组交错配对的 release；普通和 PGO 两列使用 PGO 配对组，不能用跨组绝对时间反推另一组比例。数毫秒 GC 进程的启动和调度占比较大，小幅变化不作为稳定收益或回归结论。调用点及字符串结果也没有显示明确的净加速。

**决策和生成代码。** [调用点样例](../../tests/benchmarks/profiling/call-sites.scoop)中，两处 `mix` 的静态循环热度均为 4，收益分数 96、展开代价 135，普通构建均保留调用。反馈得到热位置 `5,000,000 / 1`、冷位置 `0 / 1`，热度分别截断到 32 和 1/8；热位置分数升为 768 并内联，冷位置分数为 3，保留调用。可执行文件的 `__text` 从 324,608 增到 324,780 字节，增加 172 字节；实测吞吐基本持平。稀疏分支在训练中未执行，验证时仍正确运行。

Long hash 的回归已经对应到具体决策：`Long.hash → coreLongHash → coreULongHash` 的最后一层在普通构建中继续内联，收益分数为 96；反馈沿原 callee 入口归一化，内层 `5,000,000 / 5,000,000` 的热度变成 1，收益分数降为 24，低于代价 30，保留了 helper 调用。其 `__text` 从 325,288 减到 324,844 字节，代码更小但循环更慢。当前反馈模型没有把原函数归一化热度与消费方的外层内联上下文合并；这是下一阶段 cost 模型改进的具体输入，本次没有为单个基准调整阈值或加入自动调参框架。

字符串 chain 的报告有一个真实 string-fusion 反馈消费者，最终决策与机器正文没有变化，`__text` 均为 326,688 字节；其分配量也相同。Boolean hash 的原正文零入口位置正确回退到静态热度；本次观察到的时间变化尚未单独归因到最终布局或上层决策。反馈的匹配数量与是否实际消费分别报告，不能据此承诺加速。

**采集开销。** 下表为完整进程 CPU 和峰值 RSS，CPU 包括启动与退出写出；性能比较时未启用额外的 GC 标准错误输出。

| 负载 | Release CPU / ms | Profiling CPU / ms | Release RSS / MiB | Profiling RSS / MiB |
| --- | ---: | ---: | ---: | ---: |
| 调用点常用分支 | 102.068 | 199.572 | 3.203 | 3.547 |
| Long hash | 40.580 | 1,064.617 | 3.219 | 3.516 |
| 字符串 chain | 186.560 | 459.879 | 4.281 | 5.234 |
| GC 链表 | 8.764 | 13.292 | 12.328 | 12.609 |
| 1,100 次完整 GC | 3.703 | 8.519 | 3.312 | 4.281 |

频繁执行的原子计数会显著扰动非常短的算术内核。四个代表程序的训练 binary 约 1,175,472 字节，普通和 PGO binary 约 850,160 字节，训练文件增幅约 38%；`__text` 增幅约 64%，另含约 64 KiB 计数、28 KiB 记录和 32 KiB 名字段。精确值随程序而变；训练行表的独立调试文件未计入 binary 大小。反馈 binary 没有这些 profiling 段。

只更换 profiling runtime 时，前三类内核中位数相对配对 release 在约 ±2% 内。1,100 次完整 GC 的进程墙钟从 5.800 ms 增到 10.329 ms，约 1.78 倍，包含 8,192 条事件的退出序列化和文件 I/O，不能解释为 STW 增长比例。此模式 `__text` 增加 10,728 字节，完整文件增加约 18 KiB；固定事件缓冲在使用时影响 RSS，普通 runtime 不包含它。

在计时之外打开已有 GC stats，普通／PGO 调用点与 Long hash 均分配 104 字节且无收集；字符串 chain 均分配 960,000,168 字节、919 次 minor GC；链表分别分配 6,291,736／6,291,712 字节，均有 2 次 minor、2 次 full，晋升和复制字节相同。上述算术回归由调用决策解释，未出现新增分配或 GC。

## 保留默认内联、PGO 只追加

2026-11-14 在相同 Darwin AArch64／LLVM 22.1.8 环境重新构建三个代表程序。普通与反馈构建均使用相同 Release/full 系统库、full 根产物和现有 native 计时 helper；反馈直接复用首版训练数据。先执行默认最多三轮，再追加最多三轮反馈选择，两阶段共用模板、内联 ancestry 及累计增长。没有改变普通 release 阈值，也没有重训、修改输入或引入新的命令参数。

真实优化报告确认 `Long.hash → coreLongHash → coreULongHash` 三层均在默认阶段以循环热度 4 展开；Boolean hash 的两个默认展开也保持。`mix` 在默认阶段仍因收益不足保留调用，反馈阶段仍将热位置按热度 32 追加内联。默认展开的 heat 不含 profile，且不计入反馈消费者；增长争用回归检查确认进入追加阶段后不会重新获得已消耗的 caller 额度。

每个输入预热一对，再进行五对 AB/BA 交错测量；表中为 native helper 内核时间中位数，标准输出逐次相等，计时期间没有本任务的构建。GC 设置沿用一个 worker、增量模式和 64 MiB nursery 上限，仅用于保持比较条件。百分比不是统计显著性结论，也不外推到其他原生目标。

| 输入 | 迭代次数 | Release/full / ms | 追加 PGO / ms | 耗时变化 |
| --- | ---: | ---: | ---: | ---: |
| 调用点常用分支 | 10,000,000 | 108.507 | 108.955 | +0.41% |
| 调用点未训练稀疏分支 | 7,000,000 | 77.922 | 76.724 | −1.54% |
| Long hash | 50,000,000 | 42.502 | 42.142 | −0.85% |
| Boolean hash，未训练 | 30,000,000 | 17.692 | 21.005 | +18.73% |
| 字符串 chain | 20,000,000 | 187.238 | 186.476 | −0.41% |
| 字符串 shared，未训练 | 12,000,000 | 212.001 | 211.754 | −0.12% |

另用保留的旧 PGO binary 在同轮做五对 Long hash 对照：普通构建 42.363 ms、旧 PGO 68.414 ms，仍慢 61.49%。新策略保住默认展开后，这一退化不再复现；其余接近 1% 的变化不足以宣称稳定加速。计时之外，Long hash 两组均分配 104 字节、无 GC；chain 两组均分配 960,000,168 字节、919 次 minor GC。

Boolean hash 的回退仍需处理。比较最终 LIR，普通构建包含 `poll.chunk` 和无逐轮 poll 的分块正文，反馈构建没有分块，循环保留逐轮 poll。反馈的 `Profile` 标记落入当前标量区域识别的不支持分支，阻止了原有转换；标记还引入独立控制流块。默认内联已经相同，因此不能再把该现象归因于“PGO 取消默认内联”。此处记录已确认的结构差异，未做隔离消融来量化它对全部 18.73% 差距的贡献。标记对既有优化的透明性与精确上下文反馈一并列入[后续第一批](NEXT-STEPS.md)，本次没有扩大到修改循环或 GC 契约。

**实现与警告清理验收。** 格式化及 `cargo clippy --workspace --all-targets -- -D warnings` 通过，未关闭 lint。HIR、identity、MIR-lower 和文档测试合计 1,446 项通过，其中 MIR-lower 223 项；补齐 Mach-O LLD 搜索路径后，linker／toolchain 83 项通过。按普通开发配置重建命令，完整 profiling fixture 再次通过 9 次外部调用，包含 instrument → merge → optimize → run、配置与缓存更新、失败保留输出和无探针验证。macOS debug 编译器的 unwind 表尺寸警告按用户要求保留。

全 workspace 执行记录为 6,446 项通过、53 项失败，不能作为全量通过结论。其中两项是本分支 schema 演进后遗留的 wire golden／未知 tag 期望，十项依赖本机 Mach-O LLD 搜索路径，修正后分别纳入上述复验。其余为 18 项旧 TaskContext 布局快照、22 项 core descriptor 测试辅助逻辑失败，以及一项 Windows statepoint return-PC 检查。主线 `b59f7fc1db` 的 `lowers_hello_world` 与 `actual_core_sources_produce_closed_mir_and_lir_export_tables` 分别复现相同的布局快照和 `CoroutineStartWork` descriptor 缺失；本机 Homebrew LLVM 未包含项目要求的 Windows statepoint 补丁。原生六目标首版验收使用配套工具链的结论保持原有范围，本轮没有为这些失败放宽断言或修改无关实现。

独立 bug fix PR #131 合并后，将主线 `306c818a04` 合入 PGO 分支。本机重新格式化、执行 workspace Clippy（`-D warnings`）并按普通开发配置构建命令；dump 2 项、linker 18 项全部通过，完整 profiling fixture 再次通过 9 次外部调用（115.20 s）。这一轮确认主线修复与 PGO 链接、训练和反馈流程可以组合使用。
