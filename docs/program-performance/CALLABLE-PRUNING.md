# 不可达 callable 与 stackmap 裁剪

相对 `723ab3eb3`，最终链接在 ODR 选择之后沿实际物理符号引用保留可达 callable。删除函数时，其机器码、EH、stackmap、callable／safepoint 登记、私有常量与 Context cells 随同一个物理 member 一起移除；最终 image 的表只收集保留项。输入 `.slib` 仍保存完整候选，供不同 consumer 使用。

所有 profile 默认启用，无独立开关。不改变函数 ABI、接口表布局、对象表示、runtime ABI 17 或 metadata ABI 9；没有新增运行时代码、诊断代码或 GC roots。

## 选择范围

- 保留现有非 callable 物理 member：root entry、类型／完整接口派发表、静态存储、immortal、初始化记录与 generated-C bridge。其真实引用作为函数可达性的起点，函数地址、default／override、release hook、callback、eager／lazy 初始化和跨 Cone 调用均沿普通符号关系处理。
- runtime 引用和已声明 native 输入中的 Scoop 符号引用同样保留目标。native archive 的已读候选引用保守地保留对应 Scoop 函数，不因此提前抽取 native archive member。
- 先按现有规则选定完整 ODR 实现，再遍历选中 member 的定义／引用；完整接口数组与父表 alias 仍然同选。无外部入口的自递归或相互递归函数组可以整体删除。
- 不把候选 image 的完整 callable／safepoint 表当作保留起点。更细的类型／静态元数据裁剪未包含在本项，因此仍会保留只被这些现有记录引用的函数。

实现直接使用 Link 输入已经保存的物理成员、定义和符号使用，不展开 HIR、重建另一套语言调用图或重新扫描机器对象。native 输入原本为符号选择读取的索引复用于此处。

## 产物合同

原 `link-identity-closure/18` 的 field 5 从 legacy undefined requirement 子集投影，遗漏了另行分类的跨 Cone callable／shape 引用；完整保留函数时隐藏了这一问题。现在直接投影生产阶段已经解析的 relocation，保存全部跨物理 member 的 `(member, symbol)`，去重后落盘，对象内部已闭合的引用不重复保存。

该完整引用合同使用 `org.scoop-lang.lir/link-identity-closure/19`；wire 项仍为 member 和 symbol 两个字段。旧产物及相应缓存需要重建，不能通过最终链接补扫机器对象兼容。实际验证中，新链接器在 profile fingerprint 检查处拒绝了旧版本输入，未发布可执行文件。机器对象与语言实体身份保持。

诊断／测量仍只由既有 `--enable-startup-stats` 显式编入。默认产物继续排除报告标记、计时错误字符串和专用计数查询符号，普通计时与统计运行分别测量。

## 定向验证

- 两机相关 crate 的格式／Clippy 和 4 项 Link closure 单测通过，新增回归确认同 Cone 与跨 Cone callable 引用均被保存。
- 三目标各运行 4 组正式 fixture、7 个变体：`callable-pruning`、`odr-selection`、`reference-array-roots`、`startup-stats`。覆盖 debug／release、无入口递归组、父接口视图、default／override、跨 Cone 泛型与 Context、装箱、引用数组、异常清理、native callback、moving／minor／survivor GC 和两种最终链接入口。
- 新产物专测确认三个不可达函数的符号和原始 body ID 同时消失，活跃分派与 main 仍存在；保留的 site 数与实际 stackmap record 数一致。普通程序和显式统计／stress 重链接均输出正确初始化顺序与结果。
- 六个代表程序在三个目标保留的物理机器对象均可在各自基线中找到相同内容摘要；普通最终产物排除启动诊断代码的标记与专用符号。

首轮跨 Cone 缺符号通过上述完整引用表修正闭合；Linux 首轮快照时间戳导致 Cargo 复用旧编码实现，修正验证环境后重建工具及四个使用到的系统库，重跑失败步骤通过。新 fixture 的声明语法问题也已闭合。没有运行全量验收或扩大到无关编译器改动。

## 测量方法

使用同一基线源码、runtime 和各目标本机 LLVM 22.1，对照工具及其配套版本的系统库。最小程序与 JSON 解码程序均输出 `7`；默认启动每组 3 次预热、31 对交错 AB／BA，统计版另外运行同样的组合。默认程序没有编入启动统计，阶段时间只比较各自的统计版。

dispatch／trees／strings／strmap 沿用用户基准的仓库内副本，String API 已同步；两侧均使用默认 nursery 自适应（上限 32 MiB），survivor 保持默认关闭。每组 1 次预热、3 对交错运行。Linux 程序运行固定 CPU 4；构建计时使用正常的 CPU 配置，期间不并发其他构建或测量。

构建成本分别测已生成 `.slib` 的最终链接，以及消费预编译系统库的完整源码编译加链接。每组 1 次预热、3 对交错运行；后者每次使用独立 cache／target，并确认确实启动了编译子进程。系统库准备不计入这组 consumer 编译成本。

## 稳态对照与默认策略

四个原始负载的完整进程耗时变化如下：

| 目标 | dispatch | trees | strings | strmap |
| --- | ---: | ---: | ---: | ---: |
| Darwin ARM64 | −0.85% | +0.56% | −0.52% | −3.61% |
| GNU x86_64 | +1.79% | +0.43% | −4.53% | +0.59% |
| musl x86_64 | +1.70% | +1.56% | −1.84% | −2.74% |

保留这些小幅回退与波动；本项的确定收益来自删掉实际不可达代码和登记，而没有改变存活函数的算法或 GC 策略。代表程序的启动与体积收益一致，编译／链接成本下降，因此采用所有 profile 默认启用。仍保留的类型及静态元数据是后续可单独测量的裁剪范围。
