# 宽数组元素的重复引用写入

基线为 `124a982a1`。release 默认优化真实 typed ArraySet 中 **stride 大于 16 B、恰有一个 managed leaf** 的元素；不按函数、类型名称或 extern 符号选择。对象、接口、scan、`.slib` 和 runtime ABI 保持，没有新增诊断代码或公开开关。

## 实现与边界

从已经完成的数组布局取得 stride 和引用 offset，写前读取该槽的旧引用，完整写入元素后比较新引用。只有 `new != null && new != old` 才执行原页表查询、卡置脏和卡组登记。LLVM 可以转发写后读取，并删除已知同引用／null 的屏障及无用旧槽读取；标量字段、itab、tag 和 padding 仍完整写入。

引用比较发生在实际 setter 的成功路径，入口 poll 和 bounds checks 之后；读取、写入、比较及屏障之间没有 safepoint、用户调用或发布。旧引用仅用于此次比较，不增加根或跨 GC 保存。已存在的 old→young 边及 survivor 保留卡继续由原 remembered set 维护，省略重复标记不清卡。规范见运行时 3.6、实现 2.19。

单／双字引用数组保持已有有界循环的页表提升与批量卡标记；多引用元素保持范围屏障。字段、原子、native 写入、数组 literal／clone／assembly 和年轻对象初始化沿用原路径。debug 不生成此比较。这是当前按实际成本选定的范围，没有建立第二套布局或通用屏障策略框架。

strmap 的泛型数组 setter 是应用中独立生成的 callable，原调用边界仍在；本项在真实写入处工作，也能用于已单独编译的 setter。本次重建的 core／std／test／json 在三目标均与基线逐字节相同，可直接复用；已经保存的其他 setter 机器正文需重新生成才能采用此优化。

## 正确性和机器码

两机先格式化、workspace release Clippy，再各通过 13 项数组测试和 5 项字段屏障测试。新增 IR 回归检查引用 offset 非零、完整存储顺序、动态比较、普通优化后的同引用／null 消除，以及 debug、小元素和多引用回退。保留原字段缓存、原子发布与年轻数组初始化组合。

Darwin ARM64、Linux GNU／musl 各通过 `interface-ssa` 与扩展的 `reference-array-roots`，合计三个变体、12 次进程调用。覆盖宽元素中的 class、可空泛型接口、父投影、MaybeUninit、重复写回后的标量更新、跨 card／64 KiB、越界异常、清空后的实际回收，以及 moving／minor／survivor。原接口组合继续覆盖装箱和并发收集；诊断确认各目标确实发生搬迁与 minor。没有运行完整验收。

ARM64 setter 在完整写入后用 `cmp/ccmp/b.eq` 绕过四级 acquire 查询、卡写入和登记；x86_64 使用普通引用读取、比较和条件跳转，四级查询仍具原 acquire 语义。两架构的 setter 栈帧均未增大，入口 poll、byval 参数及根恢复保持。常量清空路径的整个屏障被删除。八程序的 MIR／LIR 均逐字节相同；dispatch、lambdas、List<Long>、接口数组／父投影和 class 跨调用循环的指令、根 spill／恢复与栈访存数量保持，没有重复计算此前接口 SSA 的收益。

## 运行结果

M3 Ultra／LLVM 22.1.8，nuc12 i7-12700H／LLVM 22.1.2 的 GNU／musl 实机；固定源码、同一套 runtime 和逐字节相同的四个系统库。正常 release，一对预热、五对 AB／BA，不固定 CPU。strmap 中位数分别为 **0.905289→0.644457 s、1.361955→0.996422 s、1.954185→1.577553 s**。

八程序的分配、minor／full 次数、搬迁／晋升字节、根扫描和追踪对象数保持。strmap 仍分配 777,411,704 B，259 次 minor／9 次 full，复制 12,695,360 B，扫描 18,672 个根槽；三个目标的累计脏卡由 1,566,600 降到 118,346，旧代引用槽扫描由 **33,414,853 降到 2,522,732（−92.45%）**。单对独立 GC 诊断中，remembered 扫描时间为 ARM64 199.462→19.614 ms、GNU 282.631→28.138 ms、musl 290.407→28.950 ms；引用更新分别为 88.674→18.544、133.118→28.225、138.704→29.989 ms。这些阶段计时不替代上述普通 release 对照。

[十种写入内核](../../tests/benchmarks/arrays/writes/README.md)每种写入 8,388,608 个元素，一对预热、五对交替，逐项核对输出。阶段内反复写同一引用／清空的耗时减少 ARM64 62.94%～67.25%、GNU 49.84%～62.56%、musl 57.94%～60.86%；混合更新分别减少 31.37%～31.47%、17.69%～31.17%、27.73%～33.73%。同引用 class／interface 的整进程耗时减少 37.43%～51.39%。

每次更换非空引用会承担额外比较：class／interface 的阶段耗时变化为 ARM64 +0.16%／+2.47%、GNU +0.92%／−27.52%、musl +2.79%／+0.73%。ARM64 的 interface 增量约 0.056 ns／元素。Linux 短样本波动较大，无引用对照也出现 +9.79%／+11.07%；其 452 条函数指令保持，位置移动 32 B。仅对四种模式补一次 CPU 4 固定 affinity 的五对对照，没有锁频：无引用对照为 −0.55%／−1.97%，同引用为 −59.38%／−36.55%，两类更换引用模式均下降。此补充不替换初测，不把更换引用场景的下降简单归因于跳过屏障，也不承诺任意布局和调度条件下消除回退。

## 空间与编译成本

strmap text 减少 ARM64 512 B、GNU／musl 576 B；Linux `.eh_frame` 各减少 8 B。十模式内核 text 增加 88／128／128 B。全部完整二进制文件大小保持，四库逐字节相同，无对象、接口表或根存储增长。

三对独立冷 consumer 构建，每对合计 strmap 和接口数组（含链接、不 dump），墙钟中位数为 ARM64 5.715→5.692 s、GNU 7.611→7.615 s、musl 7.601→7.650 s；CPU 变化 −1.15%／+0.13%／+0.66%，每对最大 RSS 变化 −0.66%／+0.14%／+0.08%。没有明显编译成本增长，不把小幅负差作为编译加速结论。

该范围的比较数量固定，目标负载收益稳定，作为 release 默认采纳；没有推广到会破坏批量标记或需要扫描多个引用槽的情况。原始日志、IR、机器码和逐次样本保存在两机仓库外 `scoop-performance-results/2026-10-26/reference-write-guards`；本机保留 Linux 结果副本。临时构建在仓库 `tmp/program-performance/reference-write-guards`，target/release 分别为 4.3／4.1 GiB，没有多余旧 codegen 测试产物，未清除可复用缓存或 IDE 的 debug 产物。
