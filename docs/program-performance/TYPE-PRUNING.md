# 类型与 shape 元数据裁剪

相对 `1d0dd6972`，在已有 callable 可达性选择上移除类型、布局和派发表的无条件保留。不可达类型及其递归引用环可以整体删除，同时删除只被它们引用的方法、EH、stackmap 和登记记录。输入 `.slib` 仍保存完整候选，供不同 consumer 使用。

最终链接和新的物理分组对全部 profile 默认生效，无独立开关。对象、接口值、接口表内部布局和调用 ABI 保持；runtime ABI 17、metadata ABI 9、`link-identity-closure/19` 不变。没有新增 runtime／诊断代码、对象字段或 GC roots。

## 实际分组和保留规则

- 普通 Strong 的 TypeDescriptor 与同一完整 exact type 的 TypeRegistration 放入一个独立物理 member。两者必须同选，合组减少对象头、目录和符号记录开销；配对使用完整泛型实例身份，不以布局相同代替。
- Layout、ScanProgram 和 dispatch 数据按实际定义独立划分。同一完整接口数组与父表 alias 继续同组，不拆开父接口视图，不改变 override、default 或 adapter。
- ODR 沿用原有独立数据分组，先选定完整实现，再做可达性选择。callable 的代码、EH、stackmap、登记、私有常量和 Context cells 继续同选。
- root entry、静态存储及根登记、immortal 及登记、初始化 cell／登记、generated-C bridge 保留。runtime 引用、typed runtime data alias 的目标，以及已读 native 输入的 Scoop 引用也是起点。native archive 候选引用仍保守保留目标，不提前抽取 native member。
- 每个活 TypeDescriptor 必须保留同一 exact type 的登记。关联使用 Link 输入已有的完整 typed entity；父类型、接口、相关类型、scan、release hook 和方法等继续沿实际符号引用闭合。候选 image 的完整登记表不作为保留起点。

实现复用 `.slib` 已保存的物理 member、定义、实体和完整符号使用表；不重新扫描机器对象或恢复另一套语言调用图。最终 image 只汇集保留项。静态存储、初始化和 immortal 的进一步裁剪不属于本项，它们仍可能保活相关类型与函数。

较粗物理分组的已有版本 19 输入可以直接重链接，删除粒度受原有分组限制。本机未重编旧库的代表程序，类型登记从 2096 降至 1237，callable 从 1036 降至 867，site 从 3207 降至 2671；重新生产库后才能获得下述完整收益。本项不增加格式迁移要求。

## 定向验证

- 两机相关 crate 的格式／Clippy 与各 13 项对象划分单测通过，包含真实机器对象发射、完整分组、owned registration、stackmap 和清理。
- 三目标完成 `type-pruning`、`interfaces-artifacts`、`reference-array-roots`、`startup-stats` 四组、七个正式变体。覆盖 debug／release、跨 Cone 父接口与菱形视图、泛型／default／override、空接口、装箱、引用数组、native callback、moving／minor／survivor、初始化顺序和两个最终链接入口。
- 新产物专测检查未使用普通类型、泛型实例和递归类型环的符号消失；存活的 class、泛型接口和实例继续保留。真实写入全局槽的接口与装箱值跨过 GC 后仍可调用和取回，site 计数与实际 stackmap record 一致。
- 六个代表程序、三个目标的 callable 物理对象内容摘要均与各自基线一致；默认程序排除启动统计标记、计时错误字符串和专用计数访问符号。

本机先完成接口／GC／启动组，合并同选的 TD／登记对后只复跑受影响的对象划分和新增产物专测；Linux 两目标验证最终分组。新用例的声明与符号期望、Linux 部分快照缺少 Rust 测试输入的问题均已闭合。没有全量验收或无关实现改动。

## 测量方法

复用同一份最小程序、JSON 解码程序和用户提供的 dispatch／trees／strings／strmap 源码。两侧均使用默认 nursery 自适应上限 32 MiB，survivor 默认关闭。M3 Ultra 使用 LLVM 22.1.8，NUC i7-12700H 使用 LLVM 22.1.2；各目标均与本机同工具链的基线比较。

默认启动每组 3 次预热、31 对交错 AB／BA；统计版单独执行同样组合，阶段时间不与默认程序混算。四种稳态负载每组 1 次预热、3 对交错运行。Linux 程序固定 CPU 4；构建计时使用正常 CPU 配置，期间不并发其他构建或测量。

构建成本分别测已有 `.slib` 的最终链接、消费预编译系统库的源码编译加链接，以及 core／std 库自身的冷构建。每组 1 次预热、3 对交错运行；源码构建每次使用独立 cache／target，并确认确实启动编译子进程。库生产成本在两种宿主架构上测量，Linux 使用 GNU 目标；musl 另有实际产物、consumer 构建和链接测量。

| 负载 | Darwin | GNU | musl |
| --- | ---: | ---: | ---: |
| dispatch | -2.89% | -1.10% | -0.62% |
| trees | +0.29% | -0.43% | +0.62% |
| strings | -6.47% | -1.79% | -1.66% |
| strmap | -2.09% | -2.27% | -2.02% |

CPU 变化为 −6.59%～+0.46%；测得峰值 RSS 为 −26.71%～0%，大树负载降低不到 0.5%。保留 Darwin／musl trees 的小幅墙钟回退；这项优化的主要收益是启动、最终链接和产物规模，未对上述热点另加函数或场景特例。
