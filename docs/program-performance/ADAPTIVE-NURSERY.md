# Nursery 自适应容量与分块搬迁计划

普通运行从 1 MiB nursery 开始，默认最多增长到 32 MiB；debug／release 使用相同策略。`SCOOP_GC_NURSERY_MAX_MIB` 接受正的十进制 MiB 上限，例如 16、32、128；1 固定容量为 1 MiB。容量是按需分配的触发上限，不会在初始化时预先映射全部空间，也不是进程 RSS 上限。较大对象图可以提高上限；内存或暂停敏感的运行可以降低上限。

## 调整规则

- 每轮收尾复用原 nursery block 容量和已有的年轻存活／晋升字节统计。实际使用达到容量的四分之三、存活至少四分之一时，最多翻倍至上限；连续四轮存活低于十六分之一时减半。没有年轻分配的显式 minor 不计入样本。
- full 后用回收后活跃 block／large mapping 容量的一半更新 nursery 基准，按 32 KiB 对齐并限制在上下限之间。缩容不低于该基准，避免一个仍有较大存活图的阶段因几轮短命分配过早退回 1 MiB；后续 full 确认存活堆变小后，基准随之降低。这不新增空闲时强制 GC，实际页归还仍由既有 full 回收完成。
- full 的增长压力只计已提交旧代容量，年轻 block 受 nursery 容量单独约束，避免扩容后仍被原总容量阈值提前打断。旧代 block／large mapping 的请求计入压力；minor 晋升越过阈值时，随后分配慢路径仍触发 full。full 后保持原来至少 16 MiB、存活容量两倍的阈值，不在 minor 时抬高它。
- mark worker 选择使用本轮实际候选容量：minor 看年轻 block，full 看活跃堆。不足 4 MiB 默认串行，其余沿用最多四个 worker；显式 worker 设置仍有效。moving／minor stress 和 full-only 对照保持原固定触发策略。

调整只发生在原 STW／heap lock 内。成功的 TLAB bump、对象表示、allocation context、roots、接口／装箱 ABI 和 `.slib` 都保持；runtime ABI 仍为 17、metadata ABI 仍为 9。策略复用已有统计，没有新增测量计时、统计报告、测量专用代码、逐对象年龄字段或持久对象引用。survivor／晋升年龄仍是独立的后续优化。

## 搬迁计划的内存成本

直接扩容的初版暴露了 native 临时数组的代价：Darwin 上 32 MiB 上限的 trees 峰值 RSS 约 1.61 GB，反而高于 128 MiB 上限。现场 `vmmap` 显示中途有约 478.5 MiB resident 位于已空闲的 malloc large 区；强制一个 mark worker 仍有相同问题。连续搬迁计划反复倍增、复制和释放大数组，放大了分配器保留空间。

现在使用固定 256 项的 native 分块顺序追加；每项仍为原来的 48 B source／destination／大小／block 信息。每块增加 16 B 链接与计数，结构开销约 0.13%，另有最多一个未填满的尾块和分配器自身开销。预留全部目标空间后才复制、发布 forwarding 和更新 roots；失败回退及成功出口都释放所有分块，不建立持久缓存。

Darwin 相同 32 MiB 上限的两轮调优中位数中，分块后峰值 RSS 降至约 496 MB，耗时仍约 5.4 秒。分块方案在所有 profile 和目标使用同一实现；它解决了本次扩容暴露的连续数组成本，较大 nursery 本身的空间与暂停代价仍需计入。

## 验证方法

对照基线为 `3346c8999` 的固定 1 MiB runtime，已包含脏卡组和新的 String API。使用用户提供的 trees（depth 20）、strings、strmap，strings 仅按新 API 将 `.length` 改为 `.charLength`。每个目标使用同一编译器、同一源码和相同预编译 `.slib`，只替换 runtime 后重链接。

普通性能测量为一对预热、三对交错独立进程，另用现有 `SCOOP_GC_STATS` 跑一对诊断；时间和 RSS 取普通进程的中位数，GC 次数和最大暂停取独立诊断进程。128 MiB 上限单独与固定 1 MiB 基线对照。最大暂停是本组运行观察值，不是延迟保证；不同轮次的堆布局和基线峰值可以变化。

本机格式化与相关 Clippy、native GC 测试通过，覆盖存活链扩容、可配置上限、释放后缩容、旧代压力、无年轻分配的显式 minor、nursery 竞争、并发旧卡写入、晋升预留失败转 full、full-only 和稀疏 region 搬迁。Linux 通过相关 Clippy 和四项 native GC 专测，新增自适应用例含默认与指定上限两种配置。本机另核对固定 1 MiB 的实际执行，以及零／溢出配置的初始化错误。

两组正式 GC 专测为 nursery-block-reuse 与 reference-array-roots；三个目标各通过 5 个变体、19 次进程调用，含 debug／release、moving／minor 和精确接口视图，没有完整验收。原始源码、产物、vmmap、逐次测量和日志保存在两机仓库忽略的 `tmp/program-performance/adaptive-nursery/`。

## 128 MiB 上限的 trees 对照

`SCOOP_GC_NURSERY_MAX_MIB=128` 使用同一二进制，初始容量仍为 1 MiB。三目标均为 256 次 minor、6 次 full，晋升约 446 MB。

| 目标 | 固定 1 MiB → 自适应 128 MiB，秒 | 峰值 RSS，MB | 单次最大暂停，ms |
| --- | --- | --- | --- |
| Darwin ARM64 | 12.84465 → 3.38408（-73.65%） | 482.4 → 522.5 | 75.80 → 72.09 |
| Linux GNU | 19.10186 → 5.08861（-73.36%） | 361.6 → 453.4 | 125.75 → 113.52 |
| Linux musl | 21.79654 → 5.31858（-75.60%） | 395.2 → 462.9 | 148.30 → 131.23 |

32 MiB 与 128 MiB 对照各自包含独立基线进程；并行标记和堆布局使基线 RSS 有波动，保留各自原始样本。更大的 nursery 可能减少晋升、full 和 native 临时空间，其 RSS 与上限并非单调关系。Darwin 另做了 16／32／64／128 MiB 的定向调优，分块后 trees 中位数分别为 6.945／5.402／4.062／3.409 秒，RSS 为 425／496／492／523 MB；每档一轮预热、两轮测量，仅用于选择策略，不替代三目标正式对照。

## 静态空间与构建成本

三目标的三个 consumer `.slib` 都与各自基线逐字节相同；使用同一编译器，无需重新生成调用、TLAB 快路径或 stackmap。原有对象表示保持，region metadata 为 72 B、block metadata 为 144 B。heap 私有状态增加 32 B：Darwin 800→832 B，GNU／musl 776→808 B；不增加每对象开销。

| 目标 | 三程序 text 增量 | 完整文件增量 | 普通 runtime 冷构建墙钟 | CPU 变化 | 构建峰值 RSS 变化 |
| --- | --- | --- | --- | --- | --- |
| Darwin ARM64 | 528 B | 144～16656 B | 4.480 → 4.519 s（+0.86%） | +2.75% | -0.14% |
| Linux GNU | 640 B | 128～136 B | 5.037 → 4.956 s（-1.62%） | -1.99% | +0.30% |
| Linux musl | 704～768 B | 32～4128 B | 5.091 → 5.054 s（-0.72%） | -0.98% | +0.27% |

Darwin 的 strmap 因 `__TEXT` 跨越 16 KiB 段边界，完整文件增加 16,656 B；实际指令只增加 528 B。Darwin 常量段合计增加 8 B，stackmap 段大小保持；Linux 的 Scoop metadata 段大小保持。新增环境配置的解析和 GC 策略属于正常 runtime 功能，未引入诊断生成开关或新的程序测量代码。

冷构建使用同一 builder 和 vendor 输入，每轮独立空缓存，共三对交错测量，比较本项实际变化的普通 runtime C 构建；没有重复整套编译器或 consumer 源码冷构建，也不将小幅负差作为编译优化收益。
